# facility-remote.py — `facility/remote.py`

> [!abstract] Role
> Everything machine-specific for a remote **Slurm or PBS** cluster, behind one [[facility-base|Facility]]: the SSH transport, the per-facility `MachineProfile`, the `globus-compute-endpoint` CLI driver, and `SlurmFacility` (bootstrap / provision / teardown / config template). Despite the name, `SlurmFacility` drives **both** schedulers — the template split, not the class, is scheduler-specific.

## The pieces

- **SSH transport** — `SshTarget` (`:72`) + `ssh_exec()` (`:187`): `BatchMode` (never prompts), reaps the child on timeout/cancel (no process/FD leak), and gives ssh `/dev/null` for stdin when there is no payload: the server's own stdin is the MCP channel, and an ssh that inherited it either read the agent's next request or set the pipe non-blocking so the server read end-of-input (2026-10-15; `tests/test_subprocess_stdin.py` keeps every subprocess off it). **Identity defers to `~/.ssh/config`** — `user`/`key_path` are optional; absent ⇒ a bare `host` so OpenSSH resolves `User`/`IdentityFile` **and `ProxyJump`** itself (`-i`/`IdentitiesOnly` only with an explicit key). That `ProxyJump` deferral is why a **bastion two-hop** (ALCF Aurora: `bastion.alcf.anl.gov` → login node) is transparent — no new code ([[Aurora (PBS + bastion) bring-up]]). Also drives the un-indexed [[discovery]] probe (`ssh_exec` on a bare target, pre-endpoint). The control channel of [[Two-channel architecture]]; see *Persistent SSH* below.
- **Interactive-auth hand-off** — `is_interactive_auth_failure` (`:221`) recognises a `BatchMode` denial where the server *offers* `password`/`keyboard-interactive` (vs a plain `publickey` refusal or a dead host); the probe raises `NeedsPreauth` (`:256`), which the server turns into `phase="needs_preauth"` carrying `SshTarget.preauth_command()` (`:152`) — the `ssh -fN -o ControlMaster=yes …` line the **user** runs in their own terminal, on the same `%C` ControlPath, so the server's later calls multiplex over the master they opened ([[MFA and interactive SSH auth]]).
- **Per-facility data** — `MachineProfile` (`:322`): host, `env_setup` (module + venv), `interface`, partition, account, scratch, plus **`scheduler`** (`slurm`/`pbs`), **`cpus_per_node`** (PBS) and **`account_required`** (the entry's flag; `SlurmFacility.account_required` exposes it to the server's account floor, as `MEPFacility` does — False for a bring-your-own facility or a profile built by hand) — supplied by the [[Facility catalog|catalog]] (`profile_from_catalog_entry`, `:349`, which derives `endpoint_name` = `hpc-bridge-<id>` when a seed omits it and resolves `{user}` / `$USER` / `{venv}`), no longer hardcoded per machine.
- **hpc-bridge's endpoint venv** — `RemoteEndpointCLI.venv` is the `ManagedVenv` parsed from env_setup (None for a hand-written one). `ensure_venv` (`:480`) runs `endpoint_venv.ensure` once per process, from `bootstrap` after the web reuse check and from `provision`; `use_working_venv` (`:503`) serves `teardown`, which never builds and runs the CLI where the endpoint was STARTED: `teardown` passes the endpoint's own worker_init when `adopt_endpoint` read it or `provision` started it, so a reconnect that emptied or rewrote env_setup (live on globus1, 2026-10-13: `command not found`, the manager left running) does not lose the CLI. A hand-written started line, or none, is used as given with no search; hpc-bridge's line activates the first working candidate (its keyed venv, its unkeyed one, the default `$HOME/hpc-bridge/gce-venv`, then any `-endpoint-*`; `_env_prefix` (`:467`)). A search that can't tell, or finds nothing of hpc-bridge's when nothing says the endpoint is ours, falls back to the started line, else env_setup. None of hpc-bridge's runs for a line of hpc-bridge's ⇒ it cancels the blocks and reports that no CLI is left. The choice lasts one teardown: `end_teardown` runs in the teardown's `finally` and at the start of every `ensure_venv`. `profile_from_catalog_entry` (`:349`) applies the upgrade-on-read (`migrate_env_setup`) and refuses an unsafe `{venv}` for hpc-bridge's line. See [[facility-endpoint_venv]].
- **Blocks run their manager's venv** — every task's config carries `worker_init`; `adopt_endpoint` (`:1189`, called by `warmth._provision` before the first runner) reads the endpoint's OWN configured one from its published template (`facility.base.endpoint_metadata`, shared with the MEP; `configured_worker_init` (`:1107`) parses our template line's default, encoded once or twice) and `dispatch_uec` (`:1226`) sends it. Unreadable ⇒ the profile's; only a successful read is cached. After a `start` it did itself, `provision` marks the endpoint adopted with the profile's own line and reads nothing (a same-id restart re-registers seconds later, so the web would still serve the old template). `worker_init_note` says when it differs from the facility's env_setup beyond the upgrade-on-read, with a WARNING when hpc-bridge's line was replaced by an empty or hand-written one on the running endpoint.
- **gce driver** — `RemoteEndpointCLI` (`:440`): runs `globus-compute-endpoint` over SSH via `_gce` (`:462`); also `login_exec` (`:561`, backs the `login_shell` tool), `seed_storage_db` (`:638`, [[Credential seeding]]), `configure`/`start`/`stop`, `clean_uep_pidfiles` (`:793`, removes stale per-UEP `daemon.pid` files scoped to the endpoint UUID so a rebuilt worker doesn't hit "Another instance is running" → exit 73 — [#37](https://github.com/globus-labs/hpc-bridge/issues/37); `provision` calls it before a restart), `cancel_blocks` (`:816`, scheduler-aware — `scancel`, or `qdel` via `_cancel_blocks_pbs` (`:852`)), and `close` (`:920`, drops the ControlMaster).
- **Orchestration** — `SlurmFacility` (`:1139`): `bootstrap` (`:1297`), `provision` (`:1387`), `config_template` (`:1232`, picks `_SLURM_TEMPLATE` (`:959`) / `_PBS_TEMPLATE` (`:1012`) by `profile.scheduler` — [[MEP & templated endpoints]]), `teardown` (`:1444`), `manager_online` (`:1539`, web), `find_online_endpoint` (`:1546`, web reuse).

## How a stand-up flows

`bootstrap` (`:1297`) is the entry point, and it is **reuse-or-SSH**: it first asks the Globus *web* service whether we already own an online endpoint (`find_online_endpoint`, `:1546`) → reuse over AMQP, **zero SSH**. Only if none is online does it seed credentials (when needed) and call `provision` (`:1387`): `configure` if absent → write the engine-free manager `config.yaml` + the scheduler's UEP template → `start` (detached) → capture & **pin** the login node. See [[Standing up the endpoint]] — including how the server rewrites a refused first SSH into `NO SSH ACCESS to <host> as <user>` for a newcomer (`_explain_provision_error`, [[server]]).

> [!note] A compute user endpoint per block request, which exits when idle (#24, 2026-10)
> Both templates open with a compute-only block: `idle_heartbeats_soft: <Profile.uep_idle_heartbeats>` (20 × 30 s = 10 min after its last task; the hard idle limit then applies too) and a comment naming `hpcb_block`, the token [[warmth]] `_fresh_block` changes per block request. The web service keys a user endpoint on its config, so each block request gets a fresh compute user endpoint and its pilot is that endpoint's first — a first pilot a stop cancels, or one that dies before it connects, fails our queued check instead of being replaced (live 2026-10-16, `queued_check_relaunch`). The number also reaches that user endpoint's OWN log: `endpoint_setup: "true hpcb_block={{ hpcb_block | default(0) | int }}"` (both templates, compute branch) is a no-op that globus-compute-endpoint 4.18 logs at the user endpoint's start (`Endpoint._run_command`: `running endpoint_setup command: …`, `BLOCK_REQUEST_LOG`; a block request is a number only by `block_number` (`remote.py:1079`, below `BLOCK_MAX`), the one rule [[warmth]] and [[scheduler_ops]] read it by), rendered `| int` so only digits ever reach that shell, whatever a config carries. Nothing else in a user endpoint's directory names its config: the rendered config reaches the process on stdin and its log only under `debug: true` (core_endpoint.py:1353), `endpoint.json` holds only its own id (endpoint.py:558), and the uuid in `uep.<eid>.<uuid>` is the service's. That line is how a stop finds the user endpoint a check of ours went to ([[server]] `_settle_by_evidence`). `compute_init_blocks` (`compute_init_blocks()`: the compute branch's `init_blocks` default, `@@EAGER@@`, read once or None) says how many blocks each new compute user endpoint starts by itself — 0 in batch mode, 1 in interactive; the stop's evidence runs only at 0. `logs_block_requests` says whether the bound endpoint's template has it — `provision` sets it when it writes the template, `adopt_endpoint` reads it from the published one (`logs_block_requests()` `:1099`); an endpoint configured before it keeps fresh user endpoints but gives a stop nothing to match there. The login user endpoint is unchanged. `fresh_ueps` says whether the bound endpoint's template is such a one: `provision` sets it when it writes the template (with a heartbeat count above 0), `adopt_endpoint` reads it from the published template (`gives_fresh_ueps` (`:1105`), zero-SSH, once per endpoint; unreadable ⇒ False). An endpoint configured by an earlier plugin keeps one compute user endpoint (one per block request would never exit there) until it is torn down and connected afresh. Each user endpoint leaves a directory on the login node (`~/.globus_compute/uep.<eid>.*`: logs, runinfo, submit scripts) that stays until the endpoint's teardown — one per block request now; removing them is a follow-up, not done here.

> [!note] `strategy_period: 5` — the first result's latency (2026-10)
> Both templates (`_SLURM_TEMPLATE` `:959`, `_PBS_TEMPLATE` `:1012`) set `job_status_kwargs: {max_idletime: <profile>, strategy_period: 5}`. 5 s is Globus Compute's own default; the templates had 30 s from when idle-release landed, with no latency reason recorded. **Only new endpoints get 5 s.** An endpoint configured before this change and still running keeps 30 s: reuse (`bootstrap`'s web reuse, `provision`'s early return for a running endpoint) never rewrites the template, so it changes only when the endpoint is torn down or its manager is restarted. `warmth._IDLE_GRACE_S` is sized to the 5 s pass; a test ties it to the rendered templates. `strategy_period` is how often parsl's `JobStatusPoller` runs the scaling strategy. A new user endpoint cannot submit a block before the first pass that knows its executor, one period after the UEP starts: the poller's timer fires its first pass inside its constructor, before `GlobusComputeEngine.start` calls `add_executors`. A first SSH result starts two UEPs (login shape, then compute), so 30 s cost about a minute. UEP start → first scale-out measured 30.5 s on the fake cluster and 30.9–31.0 s on globus1, while sbatch → worker answering took ≤ 5 s.
> The period is **not** the scheduler query rate. A pass calls the provider's `status()` only once per `status_polling_interval`, which parsl fixes at 60 s for Slurm/PBS/Torque (`squeue`/`sacct`/`qstat`). For `LocalProvider` it is 5 s, an in-process `os.kill(pid, 0)`. Otherwise a pass counts outstanding tasks in memory, and `sbatch`/`scancel` run only on a scale-out or scale-in. Idle-release timing: [[Cost control]]. A facility MEP's period is the facility's (the fake MEP's template has 15 s); hpc-bridge never writes it.

> [!warning] Login-node pinning
> The manager lives on ONE login node, but HPC SSH aliases round-robin. `start` (`:708`) captures the FQDN *in the same SSH connection* that launches the daemon (a separate probe could resolve a different node), records it via [[state]]'s `LoginNodeStore`, and the CLI `rebind`s (`:912`) straight there next session. **`_routable_pin` (`:289`) first drops a FQDN that isn't reachable from the client** — an internal suffix (`.local`/`.internal`), a single label, or a **management-plane** name (`hostmgmt`/`cm`/`mgmt`/`ipmi`/`bmc` labels, e.g. Aurora's `aurora-uan-0009.hostmgmt.cm.aurora.alcf.anl.gov`) — falling back to the alias, so a non-routable pin can't break teardown/reconnect ([#33](https://github.com/globus-labs/hpc-bridge/pull/33)).

> [!warning] PBS cancel reads bare `qstat -f`, never `-u`
> Slurm block-release matches `squeue -u`, but PBS Pro's `-u` filter suppresses full-format output entirely — so `_cancel_blocks_pbs` (`:852`) uses bare `qstat -f` (unwrapping its 80-col line continuations) scoped by the endpoint-unique `uep.<eid>` marker → `qdel`. A `-u` filter would silently no-op and let the block burn to walltime (caught in live Polaris validation, [#28](https://github.com/globus-labs/hpc-bridge/issues/28)). The marker scoping means it never touches another endpoint's jobs, same as the Slurm path.

> [!warning] `gce list` parsing is fail-loud
> `status`/`endpoint_id` parse `gce list`'s ASCII pipe-table via `_parsed_rows` (`:596`); a gce version/format change **raises** rather than being misread as "no endpoints" (which would trigger a wrong re-provision). See [#8](https://github.com/globus-labs/hpc-bridge/issues/8).

> [!warning] A `list` that fails says why (texttable 1.7.2, 2026-10-20)
> texttable 1.7.2 broke `list` itself (a traceback ending `AttributeError: 'Texttable' object has no attribute '_width'`; the pin and the venv check's repair are in [[facility-endpoint_venv]]). `endpoint_id` raised `remote list failed: <the whole traceback>`, and the notice keeps a message's first 500 characters, so the agent read only "Traceback (most recent call last): … line 12, in". `_cli_said` (`:421`) now turns a traceback into its last line (the exception) plus the frame that raised it, keeps a short message (an ssh verdict the notices classify) as it is, and adds one line saying what this break is and its fix: hpc-bridge repairs the venvs it builds; in an environment it does not manage (a hand-written env_setup, a facility's own install) `pip install 'texttable<1.7.2'` there. `status` still reads a failed `list` as None (teardown's re-checks rely on it never raising) but keeps its words in `last_list_error`, which a refused `start` quotes — gce's second-start refusal is exit 73 with no output, so before, that error said only "no output". How the endpoint id is found is unchanged (reading `endpoint.json` instead is #8's follow-up, out of scope here).

> [!note] Persistent SSH (ControlMaster) — authenticate once
> `SshTarget.argv` (`:101`) appends `ControlMaster=auto` + a `%C`-keyed `ControlPath` + `ControlPersist` (configured by `_control_settings`, [[server]]) when a socket dir is set, so all of a facility's SSH — the ~10-call cold bootstrap *and* the [[discovery]] probe — rides **one authenticated connection**. On a key facility the master opens non-interactively; on an MFA facility the user pre-opens it once (one Duo) and the server's `BatchMode` calls multiplex over it. `close` (`:920`) tears it down (`ssh -O exit`); `ControlPersist` self-reaps regardless. *(Honest nuance: the post-`start` `rebind` to the pinned node means a cold bootstrap ends with two masters — alias + node — so 2 auths, not 1; still decisive vs ~10.)* The socket dir is kept **short** by `_short_control_dir` ([[server]]): ssh checks the whole expanded `ControlPath` against the Unix socket cap (~104 bytes on macOS), so a deep `HPC_BRIDGE_STATE_DIR` would fail every SSH with `ControlPath too long` before authentication ([#50](https://github.com/globus-labs/hpc-bridge/issues/50)).

> [!note] Endpoint reuse (zero-SSH reconnect)
> `find_online_endpoint` reuse is the keystone that lets a reconnect session avoid SSH **entirely** — one of two MFA mitigations (the other is persistent SSH, above) ([#3](https://github.com/globus-labs/hpc-bridge/issues/3)). It gates on `manager_online` **alone — no liveness probe** (a probe can't tell a dead ghost from a cold-starting fresh worker); a dead "online" ghost is instead recovered downstream, where the robust [[Warmth, the canary & cold-start|canary]] maps its shut-down Executor to `provisioning` ([#37](https://github.com/globus-labs/hpc-bridge/issues/37)). See [[Two-channel architecture]] and [[Discovery today]].

## Issue #39 — the "registration lag" that was a wrapped table (fixed 2026-09-04)

`globus-compute-endpoint list` renders an 80-column table when there is no TTY (how `_gce` runs it over SSH) and wraps
an Endpoint Name longer than ~27 characters onto a second row. `_list_rows` parses per line and matches the name cell
exactly, so `hpc-bridge-<fqdn>` names (and the harness's per-run names) were never found: the first `details=` connect
failed with "could not find endpoint … in `list` output", the retry's `status()` missed too, re-ran `start` and hit
"Another instance is running". Recovery only worked because `find_online_endpoint` asks the web service by name.
Measured live on globus1 (gce 4.13); reproduced hermetically with the captured table (`tests/test_remote_facility.py`,
the `test_39_*` tests). Three changes in `RemoteEndpointCLI`: `_gce` exports `COLUMNS=400` (honoured without a TTY);
`start` polls for the UUID for up to 30 s (the detached daemon registers ~3.6 s after `start` returns) via
`_await_endpoint_id`; a refused `start` whose manager is already running adopts it instead of failing (gce 4.13 exits 73 with
NOTHING on either stream, so the check is `status(name) == "running"`, not the "Another instance" text). The robust follow-up remains issue #8: read `endpoint.json` / the pid file instead of parsing the table.

## Host trust (security review 2026-09-04)

`SshTarget.argv` no longer overrides `StrictHostKeyChecking` (it was `accept-new`): hpc-bridge trusts exactly what the
user's own `ssh` trusts — OpenSSH's default refuses an unknown host under `BatchMode`, and any relaxation in
`~/.ssh/config` applies. An unknown/changed key surfaces as `UNKNOWN HOST KEY` (notices) with the remedy in the user's
own terminal; while a pin is in use the pin is dropped like `CANNOT REACH`. A login-node PIN (`rebind`) sets
`HostKeyAlias=<resolved HostName of the alias>` (via `ssh -G`, because known_hosts is keyed by the resolved name, found
live) so a pin can never redirect the seeded credential to a machine whose key differs. `--` precedes the destination
in every argv; hosts are allowlisted at the model boundary (`models.SAFE_HOST`) and again in `SshTarget.__post_init__`;
`preauth_command` is shell-quoted. `teardown(wipe_credentials=True)` is what `teardown_endpoint` now calls.

`teardown()` (2026-09-04, live): stop → cancel blocks → `delete --yes` (directory + registration) → remove the
`uep.<uuid>.*` dirs → wipe the token store only if we seeded it → drop the endpoint record; it RETURNS what it did and
`_teardown_endpoint` composes its notice from that. Before, it only stopped: the endpoint stayed registered and the next
connect re-adopted it, while the tool claimed 'deleted'. The endpoint record is now written even with no routable pin,
so the seeded-credentials flag survives connect rebuilding the facility object. **0.1.18:** that write keeps the previously stored `login_host` when the handle has none (an adopted, already-running endpoint), and `seed_storage_db` refuses on the node itself when a `storage.db` is already there (`RemoteTokenStoreExists`, quoting the failed `whoami`) — `whoami` failing does not mean there is no store, and a store we did not create is never replaced or wiped.

## Teardown reports what was measured (2026-09-05)
`SlurmFacility.teardown()` returns `{stopped, deleted, credentials_wiped, ssh_closed, ssh_failed, error}` — every
key from the remote op's own result (`stop` → `(rc, stderr)`, `wipe_storage_db` → bool, `close` → bool). An rc 255
from the first op (ssh itself failed: no connection, or a one-time-code facility whose master expired) aborts the
rest with `ssh_failed`; the `LoginNodeStore` record survives unless the delete happened. The tool (`server._finish_teardown`)
answers `up` + "TEARDOWN FAILED …" for `ssh_failed`/not-stopped/raised, keeps the endpoint bound so a retry can
finish, and arms the one-time-code handoff when the denial offers a second factor. The teardown gate no longer
depends on the curated `auth_method`: with no master open it probes once (`_probe_login_node`, BatchMode `true`) —
rc 0 proceeds, a second-factor denial hands off, anything else is a failed teardown. (Review 2026-09-05, Fix-now #1.)
