# earlier

> [!abstract] Role
> Billed blocks an EARLIER hpc-bridge server process started: each billed block request is recorded in the [[ledger]] when its spend is confirmed; a later process checks the records against the scheduler, names what is still there, reuses a block on the same terms, asks before a second one, and — with nothing bound — releases them on `stop_endpoint`.

## Why
Each chat session typically runs a fresh server process against the same state directory, so a restart is the normal case between sessions. What a process knew of its blocks (its shape runtimes, `left_blocks`, `ssh_left`) ended with it, while the block it confirmed ran on until its idle-release or walltime. Free agent chains on the fake cluster (2026-11, `default`, SSH bring-up; each phase a new server, no teardown between) showed four symptoms:

| Before | Example |
|---|---|
| A new session's `connect_facility` reused the endpoint and said "Nothing is started or billed yet" while the earlier block ran | job 40 |
| Its next billed start (`ensure_endpoint_up`, a batch's yes) submitted a second block beside it | 40+41, 9+10, 25+26 |
| Its `stop_endpoint` before any connect answered `down`, "no endpoint was up", releasing nothing | job 33 billed on |
| A stop after a connect released both ("released 41 40"): the release reads every block of the endpoint by its `uep.<eid>` marker — the cold stop never got that far (nothing bound, no endpoint id) | 40+41 |

## How it works
- **The record** (`record_request`, from [[warmth]] `_provision` once a NEW block request's number is drawn and before its check is sent; `record_up` where the block is first confirmed warm). The ledger's `block` table, keyed (endpoint, block request): the request is the block's `hpcb_block` on an endpoint this plugin stood up (one compute user endpoint per request), else `cfg:` + the hash of the config it sends (a facility endpoint, an endpoint of an earlier plugin: the config is the user endpoint). It holds how to reach the endpoint again (the facility id and the catalog entry the binding was built from: connect's `AppCtx.bound_entry`, else a startup pin's, [[binding]] `_PINNED_ENTRY`), the scheduler, the hash of the config as sent (`wire_hash`, through `dispatch_uec`), partition, account, walltime, when spend was confirmed, the scheduler job and when it came up, and the server that asked (`session_token`, host, pid, start time, and on Linux its pid namespace). The same request asked again takes the record over: an OPEN record keeps its job and age (the block a later server reuses), an ENDED one is a new block's and loses them (review round 1: a facility endpoint's `cfg:` record re-opened with the ended block's job and age, and was closed as past its walltime before the new block answered). Closed (`end_endpoint` / `end_request`) by a stop's confirmed `down` (its release cancelled every block of the endpoint, by its marker), a teardown, a rejected submission ([[warmth]] `_void_rejected`), and the checks below. Writing it is best-effort: a ledger that cannot be written is said once on stderr, never a failed call; a network filesystem (where the [[ledger]] refuses to open) records nothing.
- **Whose.** `_whose`, by one rule (review round 3; the spec is a table, tests/test_restart_block_record_r3.py `test_b_the_liveness_spec`, run over every combination): a record of this server's session is "mine"; one of THIS machine — both machine ids known and equal (`_machine_id`: Linux `/etc/machine-id` or D-Bus's copy, macOS `IOPlatformUUID` from `/usr/sbin/ioreg`, else `ioreg` on PATH; read once per process, recorded as `owner_machine`; a missing, slow, garbled or undecodable read is unknown), or, either id unknown, the same hostname — AND the same pid namespace or none on either side, is "live" while its server runs (`Ledger.holder_alive`: the pid alive and started when the record says) and "earlier" once it is gone. Anything else is "elsewhere": a known different machine id; unknown ids and another hostname; another namespace, or a namespace on one side only (round 3: "unknown is this machine" and a namespace test that needed both sides released a live block across a Mac and a Linux container sharing the state dir — the project's image has no machine-id). Only "earlier" is named, reused or released from here. A live or elsewhere server's block is never reused or released from a cold process; its own stop does that. An elsewhere record is still READ against the scheduler (`verify` reads it, then names only the earlier ones; a cold stop reads it first through the scratch's login shape): one whose block is gone is closed, one still listed is named with the user's own cancel. (Round 2 dropped the hostname for a laptop that renames itself on a network change: with both ids known it is not consulted.)
- **Checked against the scheduler** (`verify`; `refresh` reads again when the last read is older than `VIEW_TTL_S`, 60 s, and only while an earlier server's record is open there — otherwise a ledger read and nothing else). [[connect]] calls it once the login shape is up (forced), [[server]] `_ensure_up_once` before a spend question or a billed start (off the lock), and `_export_handoff` before its terms. On an SSH endpoint it is ONE login-shape command, [[scheduler_ops]] `_pilot_status_cmd`: the endpoint's pilots by its marker, live and finished, each with the user endpoint it belongs to and the block request that user endpoint was started for. A record matches its job, or a pilot of its block request (one the endpoint started again for it). One whose block is gone — its job no longer listed, a pilot of it finished, or no pilot of it `YOUNG_S` (600 s) after it was asked for — is closed quietly. With no read (a facility endpoint, an endpoint not reachable from here) a record closes only once its block cannot still run (`_latest_end`): past when it came up plus its walltime, or — never seen up — past when it was asked for plus `QUEUE_ALLOWANCE_S` (three days of queue) plus its walltime; a walltime not on the record counts as `UNKNOWN_WALLTIME_S` (two days). Review round 1: a never-up record used to close after a day whatever its walltime. A listing that cannot be read names the records unverified. A RECORD that cannot be read (the ledger: "database is locked" past its busy timeout) fails closed (review round 4): the view keeps the last good read's blocks, unverified, and is `record_unread` — connect says the record could not be read and that an earlier block may still bill (`unread_note`, never "Nothing is started or billed yet"), a spend question says the same, `refresh` reads it again on the next call whatever its age, and the billed start's choke point (`unread`) stops every yes there with `_EARLIER_UNREAD` until a good read clears it (a facility endpoint's bind, `mep_left`, too). Round 3 had stored an empty view that read as a clean one: a verified job 40 was wiped, and a yes on other terms started job 41. A facility endpoint has no scheduler channel: its records are named unverified, from the record alone.
- **One choke point before a billed block** (review round 3): `unread`, in [[warmth]] `_provision` once the bring-up knows the endpoint id and before the reuse decision — by THAT endpoint id, whatever path led to it (a connect, a startup pin, a connect whose login bring-up failed, a fresh session). A record of another server open there that this process has not read since it knew the endpoint stops the yes (`rt.earlier_unread`, spend unconfirmed again, nothing requested); [[server]] `_ensure_endpoint_up` reads it off the lock (`refresh`, forced) and runs the call once more, which then reuses, asks (`must_ask`), or starts a fresh block. Round 2 read it only for a startup pin whose facility STRING matched the record's, and only via its own pre-bring-up: a failed connect (`app.machine` set, no endpoint id) and a pin by the entry's subject (`example:mine` against a record of `mine`) both started a second block unread. That pre-bring-up (`pinned_records`, `reach_pinned`, `unverified_pin`, server `_pinned_records_first`) is gone. Before the endpoint id is known a spend question only NAMES the session's facility's records, unverified (`_name_unbound`: by the recorded catalog entry — the subject connect bound, or one the pin names via [[binding]] `_names_machine` — never a facility string), and brings nothing up; `must_ask` waits for the endpoint id. A pinned facility endpoint's id is the facility's own (`bound_eid`).
- **Named** (`notices._earlier_note`, `_earlier_mep_note`). connect_facility's answer leads with it, and its terms note then says "Nothing new is started or billed by this connect", never "Nothing is started or billed yet". Each block by its jobs in its scheduler's own words (RUNNING, PENDING with its reason, held), its terms, what becomes of it (idle-release or walltime; a held one never starts), that stop_endpoint cancels it, and whether a yes to the next block's terms reuses it. The spend question (`ensure_endpoint_up`'s and run_shell's `needs_confirmation`) leads with the same words (`spend_lead`).
- **Reused on the same terms** (`reuse_for` / `adopt`, in `_provision` in place of `_fresh_block`). A new block request whose config, with the earlier record's block request in it, hashes to the recorded one takes that request: its check goes to the same user endpoint, so it lands on that block — no second block. Only a block read from the scheduler on an SSH endpoint, none of its pilots held or refused as submitted. Its age comes with it (`AppCtx.job_seen_since` seeded from when it came up: its walltime is presumed right), its spend is billed from this confirmation (session_spend is per session), and the record is this server's now. The answer says so (`receipt` → `_earlier_reused_note`), and its bound on a task is what is left of the block's walltime from that age ([[notices]] `_block_left_s`; the Anvil live test of 2026-11-10 read "a task runs up to ~880s (the block walltime)" on a block 5 min into its 15).
- **Asked before a second block** (`must_ask`, at `_provision`'s spend floor). A yes while an earlier block bills there that this yes would not reuse — other terms, a held pilot, an unverified record — and that no spend question of this process named (`AppCtx.earlier_told`) answers `needs_confirmation`, naming it, and says this yes came before that was said. The next yes starts the second block knowing; its answer says the earlier one still bills beside it. On a facility endpoint a block on the same config is not asked about: the facility sends the check to it itself. The connect's naming does not count as told — the conservative choice: the yes must come after a spend question that named it.
- **A stop with nothing bound** (`stop_cold`, from the top of [[server]] `_stop_endpoint`, with the call's own `jobs=` and `handoffs=`). Under the session's lock throughout (a connect and a yes meanwhile cannot have their new block released under them), the records of this server and of earlier ones that are gone are reached again: the facility is built from the recorded catalog entry ([[binding]] `_facility_from_entry`: no SSH), or is the bound one when it is that facility (a startup pin); the Globus login is checked first (`login_required`: the SDK must never prompt on the MCP transport). Each endpoint gets a scratch `AppCtx` bound to it for this call alone and the WHOLE stop a bound endpoint gets — `server._stop_endpoint(scratch, jobs, handoffs)`: the handoff question and its release scope (`RELEASE_KEEP`), the Jobs-mode keep/cancel, the busy refusal, the release by marker, the evidence. What any endpoint would ASK (`server._stop_question`, read only) is asked first, for all of them, and then nothing changes anywhere. Review round 1's blocker: the release alone had run, past the handoff question, and cancelled a handoff consumer's pool (`uep.<eid>.<consumer>`) while its record stayed live. Its answer leads with what the record named and what happened (it reached the endpoint, or tried); it is `down` with `spend_stopped` true only when that stop's was. Not reached (no login, no entry, an offline endpoint — whose orphaned `down` is not a confirmation here), or not confirmed: `draining`, with the user's own `squeue -j` / `scancel` for the recorded job; a record not reachable from here is named "recorded, not reachable from here" and stays until `_latest_end` — bounded, never dropped unseen. A facility endpoint's records become `LeftBlock`s (`how="session"`) and get the facility stop's NO CANCEL answer (`spend_stopped` false). Another live server's block: named, left to it, `draining`. Another machine's: read first (above); still listed, named with the user's own cancel, `draining`; gone, closed — and with nothing else on record the stop answers as an unbound one. A record that cannot be read fails closed (`draining`) — at the top, and when the read again after another machine's records were checked fails (round 3: a "database is locked" there had dropped every row and answered `down` "no endpoint was up" while job 40 ran) — and so does one endpoint's stop that raised (that endpoint's part, with the reason; the others are still answered). One endpoint's ASK that failed (its read of what can still bill timed out) asks nothing: its stop still runs and is answered unconfirmed (`draining`), as a bound stop whose read times out is (review round 2: it had been left unreleased while the others were released). A question changes nothing: the session's own facility-endpoint stop (`_stop_mep`, which pauses batches) is added only to an answer that is not `needs_confirmation`, and the combined answer keeps every part's `jobs` and `handoffs` (round 2). Several endpoints: one answer, `down` with `spend_stopped` true only when every one is.
- **The release itself** only ever matches the endpoint's own `uep.<eid>` marker (spared consumer user endpoints aside), so the user's own jobs, a `submit_job` job (its own directory under the scratch root) and another endpoint's blocks are never touched.
- **export_handoff** reads the record first too, and its terms (and the call that sends its billed canary) name an earlier block still billing beside the one the canary starts (`handoff_note`).
- **A resumed batch on the earlier block** ([[batch]], [[ledger]]): its rows the dead server sent hold a slot only while their own sender runs, or until task_walltime_s + `HOLD_MARGIN_S` past their admission — never because the batch's new lease holder is alive (live 2026-11-06, `batch_restart_resume`: Globus answered every REST pull with a 500, the killed server's three ended rows held the reused block's whole window for ten minutes, and the block's idle end then read as a reap of the resumed batch's own block. On a facility endpoint a gone server's row keeps its slot as before (`by_sender` False: a late delivery there can still run; review round 2) — by design: a resumed batch whose window such rows fill admits nothing until a stop or `cancel` ends the wait, and its `status` says so (round 3).

> [!warning] A cold stop is `down` only on its scratch stop's confirmed `down`
> The orphaned stop's `down` (an endpoint whose manager is offline: "a block without its manager exits on its own") is NOT a confirmation for a recorded block: from a cold process it is `draining`, naming the job and the user's own cancel. A stop that answers `down` while a recorded block may still bill is the failure this module exists to remove (job 33).

## Not covered
- `teardown_endpoint` with nothing bound still answers "no endpoint was up" (out of scope).
- A cold stop reaches an endpoint through a block record: one whose only leftover is a handoff (our own block already released) is not found from a process with nothing bound — connect_facility first, then `stop_endpoint(handoffs="cancel")`.
- With nothing on record, a stop with live Jobs-mode jobs answers as before (`jobs.stop_without_channel`).
- Two new servers reusing the same dead server's block both ride it (accepted, review round 1).
