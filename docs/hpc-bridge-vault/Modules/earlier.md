# earlier

> [!abstract] Role
> Billed blocks an EARLIER hpc-bridge server process started: each billed block request is recorded in the [[ledger]] when its spend is confirmed; a later process checks the records against the scheduler, names what is still there, reuses a block on the same terms, asks before a second one, and — with nothing bound — releases them on `stop_endpoint`.

## Why
Each chat session typically runs a fresh server process against the same state directory, so a restart is the normal case between sessions. What a process knew of its blocks (its shape runtimes, `left_blocks`, `ssh_left`) ended with it, while the block it confirmed ran on until its idle-release or walltime. Free agent chains on the fake cluster (2026-11, `default`, SSH bring-up; each phase a new server, no teardown between) showed four symptoms:

| Before | Example |
|---|---|
| A new session's `connect_facility` reused the endpoint and said "Nothing is started or billed yet" while the earlier block ran | job 40 |
| Its next billed start (`ensure_endpoint_up`, a batch's yes) submitted a second block beside it | 40+41, 9+10, 25+26 |
| Its `stop_endpoint` before any connect answered `down`, "no endpoint was up", releasing nothing | job 33 billed on |
| A stop after a connect released both ("released 41 40"): the release reads every block of the endpoint by its `uep.<eid>` marker — the cold stop never got that far (nothing bound, no endpoint id) | 40+41 |

## How it works
- **The record** (`record_request`, from [[warmth]] `_provision` once a NEW block request's number is drawn and before its check is sent; `record_up` where the block is first confirmed warm). The ledger's `block` table, keyed (endpoint, block request): the request is the block's `hpcb_block` on an endpoint this plugin stood up (one compute user endpoint per request), else `cfg:` + the hash of the config it sends (a facility endpoint, an endpoint of an earlier plugin: the config is the user endpoint). It holds how to reach the endpoint again (the facility id and the catalog entry the binding was built from: `AppCtx.bound_entry`), the scheduler, the hash of the config as sent (`wire_hash`, through `dispatch_uec`), partition, account, walltime, when spend was confirmed, the scheduler job and when it came up, and the server that asked (`session_token`, host, pid, start time). Closed (`end_endpoint` / `end_request`) by a stop's confirmed `down` (its release cancelled every block of the endpoint, by its marker), a teardown, a rejected submission ([[warmth]] `_void_rejected`), and the checks below. Writing it is best-effort: a ledger that cannot be written is said once on stderr, never a failed call; a network filesystem (where the [[ledger]] refuses to open) records nothing.
- **Whose.** `_whose`: this server's own (the session token), another server that still runs (`Ledger.holder_alive`: the pid alive and started when the record says — that session's block, never reused or released from a cold process; its own stop does that), or an earlier one that is gone. Only earlier ones are named here; this server's own are what its in-process state already names.
- **Checked against the scheduler** (`verify`; `refresh` reads again when the last read is older than `VIEW_TTL_S`, 60 s, and only while an earlier server's record is open there — otherwise a ledger read and nothing else). [[connect]] calls it once the login shape is up (forced), [[server]] `_ensure_up_once` before a spend question or a billed start (off the lock). On an SSH endpoint it is ONE login-shape command, [[scheduler_ops]] `_pilot_status_cmd`: the endpoint's pilots by its marker, live and finished, each with the user endpoint it belongs to and the block request that user endpoint was started for. A record matches its job, or a pilot of its block request (one the endpoint started again for it). One whose block is gone — its job no longer listed, a pilot of it finished, or no pilot of it `YOUNG_S` (600 s) after it was asked for — is closed quietly. A record past its walltime (+120 s) or never seen up for a day is closed without a read. A listing that cannot be read names the records unverified. A facility endpoint has no scheduler channel: its records are named unverified, from the record alone.
- **Named** (`notices._earlier_note`, `_earlier_mep_note`). connect_facility's answer leads with it, and its terms note then says "Nothing new is started or billed by this connect", never "Nothing is started or billed yet". Each block by its jobs in its scheduler's own words (RUNNING, PENDING with its reason, held), its terms, what becomes of it (idle-release or walltime; a held one never starts), that stop_endpoint cancels it, and whether a yes to the next block's terms reuses it. The spend question (`ensure_endpoint_up`'s and run_shell's `needs_confirmation`) leads with the same words (`spend_lead`).
- **Reused on the same terms** (`reuse_for` / `adopt`, in `_provision` in place of `_fresh_block`). A new block request whose config, with the earlier record's block request in it, hashes to the recorded one takes that request: its check goes to the same user endpoint, so it lands on that block — no second block. Only a block read from the scheduler on an SSH endpoint, none of its pilots held or refused as submitted. Its age comes with it (`AppCtx.job_seen_since` seeded from when it came up: its walltime is presumed right), its spend is billed from this confirmation (session_spend is per session), and the record is this server's now. The answer says so (`receipt` → `_earlier_reused_note`).
- **Asked before a second block** (`must_ask`, at `_provision`'s spend floor). A yes while an earlier block bills there that this yes would not reuse — other terms, a held pilot, an unverified record — and that no spend question of this process named (`AppCtx.earlier_told`) answers `needs_confirmation`, naming it, and says this yes came before that was said. The next yes starts the second block knowing; its answer says the earlier one still bills beside it. On a facility endpoint a block on the same config is not asked about: the facility sends the check to it itself. The connect's naming does not count as told — the conservative choice: the yes must come after a spend question that named it.
- **A stop with nothing bound** (`stop_cold`, from [[server]] `_stop_endpoint_blocks` when no endpoint is bound). The records of this server and of earlier ones that are gone are reached again, every endpoint at once (each stop bounded on its own, as every stop is): the facility is built from the recorded catalog entry ([[binding]] `_facility_from_entry`: no SSH), or is the bound one when it is that facility (a startup pin); the Globus login is checked first (`login_required`: the SDK must never prompt on the MCP transport); then the stop every bound SSH endpoint gets runs on a scratch `AppCtx` bound to that endpoint for this call alone (release by its marker, the record of our checks on disk, the evidence) — nothing stays bound in the session. Its answer leads with what the record named; it is `down` with `spend_stopped` true only when that stop's was. Not reached (no login, no entry, an offline endpoint — whose orphaned `down` is not a confirmation here), or not confirmed: `draining`, with the user's own `squeue -j` / `scancel` for the recorded job. A facility endpoint's records become `LeftBlock`s (`how="session"`) on a scratch context and get the facility stop's NO CANCEL answer (`spend_stopped` false). Another live server's block: named, left to it, `draining`. A record that cannot be read fails closed (`draining`), and so does a stop there that raised. Several endpoints: one answer, `down` with `spend_stopped` true only when every one is.
- **Jobs and handoffs first.** `stop_endpoint` still asks about Jobs-mode jobs (`submit_job`) and endpoint handoffs before anything is released, as before; the release itself only ever matches the endpoint's own `uep.<eid>` marker, so the user's own jobs, a `submit_job` job (its own directory under the scratch root) and another endpoint's blocks are never touched.

> [!warning] A cold stop is `down` only on its scratch stop's confirmed `down`
> The orphaned stop's `down` (an endpoint whose manager is offline: "a block without its manager exits on its own") is NOT a confirmation for a recorded block: from a cold process it is `draining`, naming the job and the user's own cancel. A stop that answers `down` while a recorded block may still bill is the failure this module exists to remove (job 33).

## Not covered
- `teardown_endpoint` with nothing bound still answers "no endpoint was up" (out of scope).
- A startup-pinned server's first billed start (no endpoint id until its bring-up, under the lock) does not check the record first; its connect-less stop does.
- A stop with live Jobs-mode jobs and nothing bound answers as before (`jobs.stop_without_channel`), releasing no block.
