# context

> [!abstract] Role
> The server's runtime state as pure data: `AppCtx` (one per server, shared by every tool call), `ShapeRuntime` (per resource shape: Executor, warmth/canary, spend clock, the sticky no-account verdict), `TaskHandle` (a command still running past the sync-wait), and `DEFAULT_SHAPE`, plus the derived reads on them (`_supported_shapes`, `_has_login_shape`, `_no_facility_bound`, `_idle_release_s`). No behaviour lives here.

Split step 1 of the [[Review 2026-09-03 — code quality|code-quality review]]'s plan (2026-09-03): a leaf module so the modules that follow (config, notices, warmth, tasks, …) can import the state without importing `server`. `server` re-exports the four names, so `from hpc_bridge.server import AppCtx` — every test and tool — keeps working. Field-level rationale comments moved with the fields. `TaskHandle.client_cancelled` marks a command whose call the client cancelled mid sync-wait. It is tracked like any running task, and the flag only lets the notices explain a task id the agent never received. `TaskHandle.runtime` is the shape runtime the task was dispatched on. A task whose block was released under it is noted nowhere else (never on a rebuilt or newer runtime). `TaskHandle.reset` marks a `reset_session`, for its notices. `AppCtx.released_inflight` holds compute runtimes dropped while a call was still in its sync-wait on them. A stop still sees that call while the endpoint it went to is the bound one. `LeftBlock` / `AppCtx.left_blocks` record the blocks (or a queued check) a facility-MEP stop, detach, reconnect or switch let go without a cancel (no cancel channel there, [#178](https://github.com/globus-labs/hpc-bridge/issues/178)) — job, kind, latest end, when and how, partition and account, whether hpc-bridge confirmed it — ONLY so later notices still name them, never to bill them again; `AppCtx.billed_to` is the per-(endpoint, job) high-water mark of what a stop's bank has counted, so a later tail for that job adds only what is beyond it; `AppCtx.worker_user` is the local account the last check ran as (the facility's identity mapping), for `squeue -u`.

`_no_facility_bound(app)` (`context.py:157`) is true while the facility is the server's implicit local default (no machine pinned or connected, local dev not opted into: the `implicit` mark that [[binding]] `_default_local_facility` sets, never the facility's type). `AppCtx.proposed_facility` (`:114`) is the id the LAST `connect_facility` answered with `proposed_facility_details`; the no-facility notice names it, and every connect clears it first ([[connect]]).
