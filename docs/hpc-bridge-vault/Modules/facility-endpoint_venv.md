# endpoint_venv.py — `facility/endpoint_venv.py`

> [!abstract] Role
> hpc-bridge's own endpoint venv on an SSH facility: the short `env_setup` line that only activates it, the Python-side build that checks it and, when it fails, builds a relocatable venv beside it and renames it into place, the teardown's search for a working CLI, and the upgrade-on-read of lines earlier versions generated. Why it is built this way: [[Standing up the endpoint]] § *The endpoint's own venv*.

## The pieces

- **The line** — `short_env_setup` (`:150`, tail `_LINE_TAIL` `:133`): `__hb_b="{venv}"; __hb_v="$__hb_b-endpoint-<gce>-py<X.Y>"; unset PYTHONHOME; …; export VIRTUAL_ENV="$__hb_v" PATH="$__hb_v/bin:$PATH"` — what `bin/activate` does, about 460 characters. It falls back to the unkeyed `{venv}` only when the keyed DIRECTORY is missing. Inside a batch job (`${SLURM_JOB_ID:-}${PBS_JOBID:-}` set) it runs the entry point's `version` and on failure prints one line, `WORKER_SAID` (`:146`): `hpc-bridge: endpoint venv <path> (built on <arch>) does not run on <host> (<arch>)`, then `exit 1`. It never builds. Paths are quoted; `shell_path` (`:105`) turns a leading `~/` into `$HOME/`.
- **Parsing it back** — `managed_venv` (`:183`) recognises the line at the end of a resolved env_setup and returns a `ManagedVenv` (`:161`): the site prefix before it (`module load …; `), the unkeyed base, the gce version and Python in the key. A hand-written env_setup returns None and is never built. `keyed_venv` (`:98`) names the venv; `safe_base` (`:120`) admits only an absolute or `$HOME/` path the shell would not rewrite.
- **The build** — `ensure` (`:539`) takes a `Run(step, script, timeout)` callable, so it never imports the SSH transport. Its steps:
  - `check` (`check_script` `:278`, parsed by `parse_check`/`problem`; it also reports the node's uv, its version and whether its `uv venv` knows `--relocatable`) → `check unkeyed` (only when the keyed venv is missing).
  - `build` (`build_script` `:436` in `build_dir` `:432`, wrapped by `_wrap_build` `:449`): first removes our own `<keyed>.build.*` dirs hours old (`_SWEEP` `:428`); where the node has no uv installs one (`_BOOTSTRAP_UV` `:416`: astral.sh's installer with `UV_NO_MODIFY_PATH=1`, so no shell profile is edited, else pip in a throwaway venv) and runs uv by its path. A node's uv too old for `venv --relocatable` (before 0.2.31) is named in the error (`_method` `:394`) instead of building.
  - `verify` → `claim` (`claim_script` `:494` running `_CLAIM_PY` `:462` with the build's own python: the broken venv is moved aside to a per-bring-up `.broken.<ts>.<token>` only if the path still holds the inode the check saw, and the moved directory's inode is checked again — another bring-up's venv renamed in at that instant goes back, and ours has lost; only ENOTEMPTY/EEXIST read as a lost race, any other rename error is reported and the verified build kept) → `re-check` if the claim was lost → `cleanup` (`cleanup_script` `:500`) for a build that did not claim. A failed build is moved to `.failed.<ts>` before the error is written, so the message names the copy only when there is one.
  - Errors the user acts on are `EndpointVenvError` (`:65`), which `notices._explain_provision_error` shows as they are; an ssh-level failure (rc 255) is a plain RuntimeError, so the usual NO SSH ACCESS / handoff classification still applies.
- **Teardown** — `find_working` (`:697`, script `find_script` `:662`) returns a `Found`: `cli`, the first candidate whose `version` runs, and when none did, whether that is `unknown`. The candidates are: the keyed venv, the unkeyed one, each of `extra_bases` (the caller passes `HOME_VENV` (`:45`), `$HOME/hpc-bridge/gce-venv`, so the default is searched whatever the line's base), then other `<base>-endpoint-*` dirs of every base (newest version first, `sort -V`), each once, skipping `.build.*`, `.broken.*`, `.failed.*`, `.lock`. Each candidate is capped at 6 s and no new one is tried 18 s after the LOOP starts (a slow login profile does not count), inside the 30 s teardown budget. A candidate that only ran out of time (`HPCB_SLOW`), or candidates the deadline left untried (`HPCB_UNTRIED`), make it `unknown`, never "none works": the stop is tried. Which line it searches from — the one the endpoint was started with, not the facility's current env_setup — is [[facility-remote]]'s `use_working_venv`.
- **Upgrade-on-read** — `migrate_env_setup` (`:224`) replaces an env_setup that EXACTLY matches a line hpc-bridge generated up to 0.1.23 (discovery's guarded uv/pip lines, with or without a module prefix, templated or resolved; the bootstrap form the Expanse seed holds) with the short line, keeping a module prefix and the venv base. It also re-keys hpc-bridge's own line to this client's gce and Python. Anything else is returned unchanged.

> [!warning] Check through the entry point
> `python -c "import globus_compute_endpoint.cli"` raises IndexError on every real install: gce 4.12–4.18's `cli.py` reads `sys.argv[0].rsplit("/", 1)[1]` at import. Every check here runs `<venv>/bin/globus-compute-endpoint version` (which may create an empty `~/.globus_compute`, and fails if it cannot).

> [!warning] Relocatable, uncached, copied, claimed by rename
> The build is `uv venv --relocatable`: its entry points find their python relative to themselves, so the venv still runs after the rename that puts it in place (checked with uv 0.12.9 in a clean container, including parsl's `process_worker_pool.py`). Its `bin/activate` does NOT work under sh/dash after a move, which is why the line activates by itself. uv venvs are hardlinked into `~/.cache/uv`, so a corrupted cache entry would survive a rebuild: every build passes `--no-cache` (and `--link-mode=copy` to `uv pip install`). `os.rename` refuses a non-empty target, so of two concurrent builds exactly one claims the keyed path. A scenario that plants a break must replace a file with `mv`, never edit it in place.
