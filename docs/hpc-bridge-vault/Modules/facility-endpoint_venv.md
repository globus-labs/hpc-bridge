# endpoint_venv.py — `facility/endpoint_venv.py`

> [!abstract] Role
> hpc-bridge's own endpoint venv on an SSH facility: the short `env_setup` line that only activates it, the Python-side build that checks it and, when it fails, builds a relocatable venv beside it and renames it into place, the teardown's search for a working CLI, and the upgrade-on-read of lines earlier versions generated. Why it is built this way: [[Standing up the endpoint]] § *The endpoint's own venv*.

## The pieces

- **The line** — `short_env_setup` (`:169`, tail `_LINE_TAIL` `:152`): `__hb_b="{venv}"; __hb_v="$__hb_b-endpoint-<gce>-py<X.Y>"; unset PYTHONHOME; …; export VIRTUAL_ENV="$__hb_v" PATH="$__hb_v/bin:$PATH"` — what `bin/activate` does, about 460 characters. It falls back to the unkeyed `{venv}` only when the keyed DIRECTORY is missing. Inside a batch job (`${SLURM_JOB_ID:-}${PBS_JOBID:-}` set) it runs the entry point's `version` and on failure prints one line, `WORKER_SAID` (`:165`): `hpc-bridge: endpoint venv <path> (built on <arch>) does not run on <host> (<arch>)`, then `exit 1`. It never builds. Paths are quoted; `shell_path` (`:124`) turns a leading `~/` into `$HOME/`.
- **Parsing it back** — `managed_venv` (`:202`) recognises the line at the end of a resolved env_setup and returns a `ManagedVenv` (`:180`): the site prefix before it (`module load …; `), the unkeyed base, the gce version and Python in the key. A hand-written env_setup returns None and is never built. `keyed_venv` (`:117`) names the venv; `safe_base` (`:139`) admits only an absolute or `$HOME/` path the shell would not rewrite.
- **The build** — `ensure` (`:631`) takes a `Run(step, script, timeout)` callable, so it never imports the SSH transport. Its steps:
  - `check` (`check_script` `:343`, parsed by `parse_check`/`problem`, and `shadowed` (`:439`) for a texttable from outside the venv; its one python call, `_PY_PROBE` `:309`, reports the major.minor and whether the venv's texttable does what the endpoint's `list` does with it — see *texttable 1.7.2* below; it also reports the node's uv, its version and whether its `uv venv` knows `--relocatable`) → `check unkeyed` (only when the keyed venv is missing; an unkeyed venv that fails is never changed — it may be the user's own — and the keyed one is built, the reason and any build error saying `<base> was not used: …`).
  - `build` (`build_script` `:526` in `build_dir` `:522`, wrapped by `_wrap_build` `:541`): first removes our own `<keyed>.build.*` dirs hours old (`_SWEEP` `:518`); where the node has no uv installs one (`_BOOTSTRAP_UV` `:506`: astral.sh's installer with `UV_NO_MODIFY_PATH=1`, so no shell profile is edited, else pip in a throwaway venv) and runs uv by its path. Either way the ONE `uv pip install` carries the endpoint, the co-pinned globus-sdk and `TEXTTABLE_PIN` (`:60`, quoted: `<` is a redirect). A node's uv too old for `venv --relocatable` (before 0.2.31) is named in the error (`_method` `:481`) instead of building.
  - `verify` → `claim` (`claim_script` `:586` running `_CLAIM_PY` `:554` with the build's own python: the broken venv is moved aside to a per-bring-up `.broken.<ts>.<token>` only if the path still holds the inode the check saw, and the moved directory's inode is checked again — another bring-up's venv renamed in at that instant goes back, and ours has lost; only ENOTEMPTY/EEXIST read as a lost race, any other rename error is reported and the verified build kept) → `re-check` if the claim was lost → `cleanup` (`cleanup_script` `:592`) for a build that did not claim. A failed build is moved to `.failed.<ts>` before the error is written, so the message names the copy only when there is one.
  - Errors the user acts on are `EndpointVenvError` (`:84`), which `notices._explain_provision_error` shows as they are; an ssh-level failure (rc 255) is a plain RuntimeError, so the usual NO SSH ACCESS / handoff classification still applies. Three of them are the configuration's own (2026-10-20): `EndpointVenvConfigError`, also a [[facility-base]] `ConfigStepFailed` — the check stopped in the site prefix before its frame, the build failed (not by running out of time, nor reaching the network — uv's or pip's fetch, curl's install of uv: DNS, route, a refused connection — nor a write the filesystem refused: `_BUILD_NOT_THE_CONFIG`, read from the build's last lines), and "no uv, no curl and no python3" after the prefix. A venv in the way, an old uv, a slow filesystem or a shadowing texttable stay `EndpointVenvError`. [[connect]] drops a `details=` config only for the former.
- **Teardown** — `find_working` (`:807`, script `find_script` `:772`) returns a `Found`: `cli`, the first candidate whose `version` runs, and when none did, whether that is `unknown`. The candidates are: the keyed venv, the unkeyed one, each of `extra_bases` (the caller passes `HOME_VENV` (`:48`), `$HOME/hpc-bridge/gce-venv`, so the default is searched whatever the line's base), then other `<base>-endpoint-*` dirs of every base (newest version first, `sort -V`), each once, skipping `.build.*`, `.broken.*`, `.failed.*`, `.lock`. Each candidate is capped at 6 s and no new one is tried 18 s after the LOOP starts (a slow login profile does not count), inside the 30 s teardown budget. A candidate that only ran out of time (`HPCB_SLOW`), or candidates the deadline left untried (`HPCB_UNTRIED`), make it `unknown`, never "none works": the stop is tried. Which line it searches from — the one the endpoint was started with, not the facility's current env_setup — is [[facility-remote]]'s `use_working_venv`.
- **Upgrade-on-read** — `migrate_env_setup` (`:243`) replaces an env_setup that EXACTLY matches a line hpc-bridge generated up to 0.1.23 (discovery's guarded uv/pip lines, with or without a module prefix, templated or resolved; the bootstrap form the Expanse seed holds) with the short line, keeping a module prefix and the venv base. It also re-keys hpc-bridge's own line to this client's gce and Python. Anything else is returned unchanged.

> [!warning] Check through the entry point
> `python -c "import globus_compute_endpoint.cli"` raises IndexError on every real install: gce 4.12–4.18's `cli.py` reads `sys.argv[0].rsplit("/", 1)[1]` at import. Every check here runs `<venv>/bin/globus-compute-endpoint version` (which may create an empty `~/.globus_compute`, and fails if it cannot).

> [!warning] texttable 1.7.2 broke `list` (released 2026-10-18)
> globus-compute-endpoint 4.18's `Endpoint.print_endpoint_table` calls texttable's private `_compute_cols_width()` and then reads `_width`; 1.7.2 makes that method return the widths and sets `_width` only inside `draw()`, so `list` raises `AttributeError: 'Texttable' object has no attribute '_width'` whenever an endpoint is configured (with none it prints "No endpoints configured!" first). The endpoint leaves texttable unbounded (the SDK's `texttable>=1.7`), and [[facility-remote]] finds the endpoint's id with `list`, so every SSH bring-up on a venv built since then failed at "remote list failed" — and `version` still ran, so the check passed it. Now every build pins `texttable<1.7.2` (`TEXTTABLE_PIN`), and the check's python call runs the same calls `list` makes (`_PY_PROBE`): a venv whose texttable fails them is rebuilt like any broken venv (built beside, verified, renamed in, the old one kept as `.broken.<ts>`). A venv with no texttable at all passes (its endpoint cannot be reading it). Why a rebuild, not an in-place `uv pip install 'texttable<1.7.2'`: the build is the module's only way to change a venv — whole, verified, claimed by one rename, so two bring-ups at once need no lock and none sees a half-swapped package — and it never touches the unkeyed venv, which may be the user's. It costs one full build, once per venv. The pin and the probe's texttable calls come out TOGETHER, once the endpoint stops reading `_width`: the probe tests texttable alone, never the endpoint, so a build without the pin would take 1.7.2 and fail its own verify on every bring-up (`test_the_pin_and_the_probe_go_together` holds them to that). Driving the venv's own `Endpoint.print_endpoint_table` instead would retire the probe with the endpoint's change, but it imports the whole endpoint module on every bring-up (0.3–0.5 s measured on a local disk, more than `version` itself) and leans on private endpoint internals. The probe runs the calls through `draw()`, as `list` does. It also reports where the texttable it imported lives: one from OUTSIDE the venv's own prefix (a site module's PYTHONPATH) that breaks `list` is not the venv's to mend, so `problem` passes it and `shadowed` raises an error naming the file; nothing is built (a first build is still claimed, so the next connect says so at its check without building again). A verify that finds 1.7.2 inside a build that asked for the pin says the node's uv overrode it (`UV_OVERRIDE`, `UV_CONSTRAINT`, a `uv.toml`). The probe is folded into the python call the check already made (no extra interpreter start) and sent as `exec(<repr>)`, so the check stays one line; it has no f-strings, so an old python still reports its version.

> [!warning] Relocatable, uncached, copied, claimed by rename
> The build is `uv venv --relocatable`: its entry points find their python relative to themselves, so the venv still runs after the rename that puts it in place (checked with uv 0.12.9 in a clean container, including parsl's `process_worker_pool.py`). Its `bin/activate` does NOT work under sh/dash after a move, which is why the line activates by itself. uv venvs are hardlinked into `~/.cache/uv`, so a corrupted cache entry would survive a rebuild: every build passes `--no-cache` (and `--link-mode=copy` to `uv pip install`). `os.rename` refuses a non-empty target, so of two concurrent builds exactly one claims the keyed path. A scenario that plants a break must replace a file with `mv`, never edit it in place.
