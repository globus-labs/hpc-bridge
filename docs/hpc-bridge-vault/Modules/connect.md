# connect

> [!abstract] Role
> The connect flow the agent drives: the Globus login gate FIRST, the resolution ladder (explicit details this session → the registry → the local BYO cache → the SSH probe that proposes a config), the switch of shapes/state to the bound facility, the identity-blind MEP attach or the SSH bootstrap, the allocation listing over the free login shape. Also `_commit_proven_facility` (a BYO config is cached only once the login-shape canary answered), `_drop_failed_details` (a BYO config whose bring-up failed on the login node before that is dropped, not run again — below) and `_drop_dead_pin` (an unreachable login-node pin is forgotten).

The login gate is [[login_gate]] `_stored_login`, the same as `authenticate`'s: a missing login and a stored one Globus refuses to renew (revoked or expired) both answer `needs_login` before ANY route runs — registry, local cache, a session's own entry, details=, the MEP attach, the bootstrap — so nothing copies the token store to a login node on a dead login (it did, live 2026-10-14's failure mode on an SSH facility); a check that cannot reach Globus carries on. A login that lands during the gate's wait calls `warmth._forget_identity_verdicts` first, as `authenticate` does — the cached identity label and the runners built on the old token are dropped — so "Globus login landed as …" names the NEW identity. `_connect_mep`'s attach error names a dead login (`_hpc_bridge_error`, [[notices]]).

Split step 10 (2026-09-03) — the last. The login-shape channel is injected (`run_login`) as in [[scheduler_ops]]; `server._connect_facility` is a thin wrapper supplying `server._login_runner(app)`, so the many tests that call it and patch `server._run_shell` keep working. `connect._connect_facility` is itself a thin wrapper around the flow, `connect._connect` (it opens an answer with a dropped config's failure, below). Tests that patch the probe patch `connect.discover_facility_details` / `connect._propose_or_ask`. A proposal binds nothing: `_propose_or_ask` records the facility id in `AppCtx.proposed_facility` so a `run_shell` made meanwhile is told to finish the connect with `details=…` ([[server]], No facility bound). `_connect` clears it first thing, so it always describes the LAST connect. A probe that answers `needs_preauth` sets the resume to `connect_facility(<id>, ssh_host=<host>)`: without the host an un-catalogued facility resolves to nothing and the resumed call answered `needs_facility_details` (review 2026-10-10). The account preset (`HPC_BRIDGE_ACCOUNT`) is passed to `binding._facility_from_entry` only for the facility `HPC_BRIDGE_MACHINE` names ([[binding]]); when a preset is set but not used, the bound result's notice opens with one clause saying so (`notices._unapplied_presets_note`: the variable and why — another machine, a facility endpoint, or a partition given in `details=` — never its value). `_prior_note` names a block a facility endpoint lets go of with `notices._left_block_clause`, the words a switch uses too. At the bind it records `AppCtx.terms_origin` (`binding._terms_origin`; `_discovered_partition` (`connect.py:137`) tells a bring-your-own partition the probe proposed, and details= kept, from one the details changed). Every bound result (`needs_account`, an SSH `provisioning`) states the next block's terms before any spend: `_next_block_terms` (`:144`) builds them from the config a new compute runtime would get (`warmth._seed_uec`, nothing built or started) into `block` and `notices._connect_terms_note` — the default queue and its source, the account needed (with the hint) or not, size and walltime, and the one question to ask, whose yes is the confirmation sent with the answer in one call (spend terms, 2026-10-14). On a MEP the terms are read before the facility's notes, so what fitting the config to its schema drops is said at connect. The warming notice promises "your allocations" only where the entry lists them, and an empty listing is said as one. The question never asks about a partition or account the facility would drop (`notices._dropped_term_notice`). A cached BYO config whose `scheduler_options` sets the account or queue is refused with that reason (`binding.TermsDirectiveError`). Concepts: [[Happy path]], [[Discovery today]], [[Facility catalog]], [[In-terminal Globus login]].

## A details= that failed is not run again (2026-10-20)

Live 2026-10-16 (free sweep, fake `lmod`, `lmod_bootstrap`, Hermes): the agent's first connect carried a made-up `env_setup` (`module load gcc/10.2.0`) and the remote configure failed with Lmod's "module(s) are unknown". The refusal it got next (a `details=` without `env_setup`, no proposal) said to call `connect_facility(…, ssh_host=…)` without details for a proposed config; it did, and got the same Lmod error back. The `details=` branch stores the entry in `AppCtx.session_facilities` before the bring-up (it must: a connect while it is still `provisioning` polls it, and a one-time-code handoff resumes it with `connect_facility(<id>)`), and the no-details branch took that entry first, so it re-ran the failed config.

**Which failure drops a config — decided positively, by type (review round 1, 2026-10-20).** Every poll of a config still coming up re-runs the bootstrap's SSH steps (each connect resets `app.state`), so a rule read off the explanation's words dropped configs to a slow registration, a 503 from the manager check or a dropped connection, and kept ones whose own failure happened to quote "Permission denied". Now only `ConfigStepFailed` ([[facility-base]]) can drop one: raised by the steps that run through the config's `env_setup` — `configure`, `start` and `list` in `RemoteEndpointCLI` (`base.step_error`: never for ssh's own exit status 255), and the endpoint venv's check that stopped in the site prefix, its build (not a timeout) and "no uv, no curl and no python3" (`EndpointVenvConfigError`, [[facility-endpoint_venv]]) — and only when the step's LAST meaningful line (`ConfigStepFailed.said`, `base.last_said`: a traceback's exception, a command's final error — never a login banner or a frame before it; review round 3 found a banner's "idle sessions timeout", a `sock.settimeout` frame and a `globus_sdk` path keeping real config errors) names none of `notices._NOT_THE_CONFIG_WORDS`: a timeout (`\btimed out\b`, `timeout ?error`), a Globus error (`globus_sdk\.…error`, `GlobusAPIError` …), a lost ssh connection, an endpoint still registering, the login node out of processes or on a stale NFS handle, or its filesystem refusing a write (`_REMOTE_FS_REFUSED`: globus-compute-endpoint's own Errno 13 or read-only file system under `~/.globus_compute`, a full disk or quota — explained as REMOTE FILESYSTEM, as before 2026-10-20). A negative exit status (the local ssh killed) is ssh's, like 255. A venv build that could not reach PyPI or astral.sh, or whose write was refused, stays a plain `EndpointVenvError` (`endpoint_venv._BUILD_NOT_THE_CONFIG`, read from the build's last lines). `notices._failure_of_the_config` is that rule; `_explain_provision_error` no longer applies its SSH and network categories to a `ConfigStepFailed` (ssh got through, so a "Permission denied" there is a file `env_setup` reads, not sshd). And a config whose bring-up got past `start` this session (`AppCtx.details_started`) is never dropped: each poll re-runs the venv check, whoami and list through env_setup, and a flaky node must not cost a config that started. Every branch of `_explain_provision_error` is pinned, with the decision, in `tests/test_failed_details.py`.

The states of a facility's `details=` config, and what a connect without details does in each:

| State | Kept in `session_facilities` / `pending_facility_cache` | A connect without details |
|---|---|---|
| coming up (`provisioning`: it got past `start`) | yes / yes | polls it (unchanged) — no failure of a later poll drops it |
| came up (login shape warm) | yes / no — cached to `facilities.json` | reconnects with it, zero SSH (unchanged), even after a later bring-up of it fails |
| equal to the config `facilities.json` holds as proven for that host | yes / yes | reconnects with it, as a proven config |
| failed for anything but the config — ssh, a host key, a timeout, Globus (service or login), registration, the remote filesystem, a token store, a venv in the way, an old uv | yes / yes | runs it again: what those answers' "call connect_facility again" asks for (unchanged) |
| one-time-code handoff (`needs_preauth`) | yes / yes | the resume runs it (unchanged) |
| **refused on the login node on its first bring-up** (`_failure_of_the_config`) | **no / no** (`_drop_failed_details`) | **resolves the facility afresh**: the registry if it lists the id, else a config already proven for that host, else a probe that proposes one (the host the dropped config named, when the call names none); never the dropped config |

Dropped rather than marked: every reader of `session_facilities` (the no-details rung, `_without_details`, [[scheduler_ops]]' pilot probe) keeps one meaning — a config the session keeps is coming up or proven — and none has to learn to skip a mark. What failed is kept apart, in `AppCtx.failed_details` (the host and the failure's notice), so the error stays visible. The failure's own answer ends with what a connect does next, in one piece with any "connect_facility again" before it ("This configuration (details=) is not kept[. So, to connect_facility again as above]: connect_facility(<id>, ssh_host=<host>) without details resolves the facility afresh — … — and does not run this one; with details= it runs the configuration given — this one again, or a corrected one (an env_setup left out of details= comes from the latest proposal for this facility)"). Every answer to a connect without details opens with it ("The details= given earlier for <id> failed to come up (<the failure, one line, ≤300 chars>) and is not kept: this connect did not run it."; a proposal carries it beyond its 1800-char cap, so no probe note is cut for it; a login gate, which resolved nothing yet, does not). A new `details=` for the id clears it the moment it is stored; so does a connect of the id that comes up (login shape warm, or a facility endpoint attached). A registry or cached entry is never in `pending_facility_cache`, so it is never dropped. Popping the pending entry with the session one keeps the proven-only rule: a later warm bring-up on another config (the registry's, the cache's) can never commit the failed one to `facilities.json`.

**The binding stays; no tool brings the dropped config up.** The bind precedes the bring-up, so a failed connect leaves the facility bound (a mark, not an unbind: the smaller change). `_drop_failed_details` marks that facility object (`AppCtx.dropped_binding`: the object and the refusal), and `warmth._provision` refuses first, before any spend or state change, while no endpoint is up: `ensure_endpoint_up` answers `down` and `run_shell` `failed`, with the failure, the afresh route and "or give details= again" (`DroppedConfigError`, shown as it is by `notices._hpc_bridge_error`). The next bind (a new facility object) ends it; connect also clears it there.

**Not cleaned up (a known gap, older than this change).** After a failed bring-up no endpoint id is known, so `teardown_endpoint` and `stop_endpoint` answer "no endpoint was up" without SSH. What the bring-up left on the login node stays: in the lmod case, the Globus token store `bootstrap` seeded there because `whoami` failed under the broken env_setup (`~/.globus_compute/`, 0700, with `storage.db`, 0600 — a bearer credential), with the local `endpoints.json` record (`seeded_credentials=True`, no endpoint id) that says hpc-bridge placed it. A later bring-up that comes up reuses that store, and its teardown wipes it; a session that ends without one leaves it. Follow-up: a teardown that reads that record when no endpoint is known.

**A connect queued behind the failing one.** A connect without details resolves its config before it waits for `app.lock`. If the session's config for the id changed meanwhile (the call holding the lock dropped it, or a `details=` replaced it), `_connect` answers `_Again` once it holds the lock and `_connect_facility` resolves again (at most twice), so it never binds what the other call just dropped; its answer opens with the failure and still names a Globus login that landed in the first pass (`_Again.login_note`). The other way round, a failing bring-up drops only its OWN config (`_drop_failed_details` gets the connect's `entry`): a `details=` that replaced it while it held the lock is kept, polled and, once up, cached. A config equal to the one `facilities.json` holds as proven is compared through the model, so one an older plugin cached (without a newer field) counts.

The two refusals of a `details=` without `env_setup` (no proposal for the id; a proposal for another host) say what a connect without details does from where the session stands (`_without_details`): it resolves the facility afresh, or, while the session keeps a config for the id, it reconnects with that one, whatever `ssh_host` the call names, and proposes nothing — a proposal for another host then comes under another facility id, which the other-host refusal names. They used to promise a proposal in every case.

Not changed: a facility that cannot be built at all (`binding._facility_from_entry` raising) is not a login-node failure and keeps its entry.

## Consent is per conversation; a fresh bootstrap is proven (live findings, 2026-09-04)

Three fresh-user sessions on globus1 showed: (1) the connect right after our own `bootstrap` re-finds the endpoint online
and reads as `reused` — which skipped the proven-cache commit forever and told the agent it had "reused an already-online
endpoint" seconds after a fresh start. `AppCtx.bootstrapped_facilities` records the facilities THIS session bootstrapped;
`_commit_proven_facility` skips only a reuse of an endpoint from before the session, `_reuse_note` says "reconnected to
the endpoint this session started", and the result's `reused` flag is False for our own start. (2) Claude Code's
auto-memory carried a previous session's "confirmed config" into the next one and the agent registered the facility
without asking — the proposal notice now says the confirmation must come from the user in THIS conversation and that the
probe must not be re-run over the agent's own ssh. (3) On the silent (wait-and-continue) login path nothing named the
identity that landed; `_connect_facility` now prefixes "Globus login landed as <identity>" to the result.
