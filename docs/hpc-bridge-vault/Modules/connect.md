# connect

> [!abstract] Role
> The connect flow the agent drives: the Globus login gate FIRST, the resolution ladder (explicit details this session → the registry → the local BYO cache → the SSH probe that proposes a config), the switch of shapes/state to the bound facility, the identity-blind MEP attach or the SSH bootstrap, the allocation listing over the free login shape. Also `_commit_proven_facility` (a BYO config is cached only once the login-shape canary answered) and `_drop_dead_pin` (an unreachable login-node pin is forgotten).

The login gate is [[login_gate]] `_stored_login`, the same as `authenticate`'s: a missing login and a stored one Globus refuses to renew (revoked or expired) both answer `needs_login` before ANY route runs — registry, local cache, a session's own entry, details=, the MEP attach, the bootstrap — so nothing copies the token store to a login node on a dead login (it did, live 2026-10-14's failure mode on an SSH facility); a check that cannot reach Globus carries on. A login that lands during the gate's wait calls `warmth._forget_identity_verdicts` first, as `authenticate` does — the cached identity label and the runners built on the old token are dropped — so "Globus login landed as …" names the NEW identity. `_connect_mep`'s attach error names a dead login (`_hpc_bridge_error`, [[notices]]).

Split step 10 (2026-09-03) — the last. The login-shape channel is injected (`run_login`) as in [[scheduler_ops]]; `server._connect_facility` is a thin wrapper supplying `server._login_runner(app)`, so the many tests that call it and patch `server._run_shell` keep working. Tests that patch the probe patch `connect.discover_facility_details` / `connect._propose_or_ask`. A proposal binds nothing: `_propose_or_ask` records the facility id in `AppCtx.proposed_facility` so a `run_shell` made meanwhile is told to finish the connect with `details=…` ([[server]], No facility bound). `_connect_facility` clears it first thing, so it always describes the LAST connect. A probe that answers `needs_preauth` sets the resume to `connect_facility(<id>, ssh_host=<host>)`: without the host an un-catalogued facility resolves to nothing and the resumed call answered `needs_facility_details` (review 2026-10-10). The account preset (`HPC_BRIDGE_ACCOUNT`) is passed to `binding._facility_from_entry` only for the facility `HPC_BRIDGE_MACHINE` names ([[binding]]); when a preset is set but not used, the bound result's notice opens with one clause saying so (`notices._unapplied_presets_note`: the variable and why — another machine, a facility endpoint, or a partition given in `details=` — never its value). `_prior_note` names a block a facility endpoint lets go of with `notices._left_block_clause`, the words a switch uses too. At the bind it records `AppCtx.terms_origin` (`binding._terms_origin`; `_discovered_partition` (`connect.py:137`) tells a bring-your-own partition the probe proposed, and details= kept, from one the details changed). Every bound result (`needs_account`, an SSH `provisioning`) states the next block's terms before any spend: `_next_block_terms` (`:144`) builds them from the config a new compute runtime would get (`warmth._seed_uec`, nothing built or started) into `block` and `notices._connect_terms_note` — the default queue and its source, the account needed (with the hint) or not, size and walltime, and the one question to ask, whose yes is the confirmation sent with the answer in one call (spend terms, 2026-10-14). On a MEP the terms are read before the facility's notes, so what fitting the config to its schema drops is said at connect. The warming notice promises "your allocations" only where the entry lists them, and an empty listing is said as one. The question never asks about a partition or account the facility would drop (`notices._dropped_term_notice`). A cached BYO config whose `scheduler_options` sets the account or queue, or carries a line that is no directive, is refused with that reason (`binding.SchedulerOptionsError`). The details' (or the cached config's) `scheduler_options` are written as directives first (`binding._directive_details`: a bare `-…` option gets the scheduler's prefix), the written form is what the session entry and the local cache keep, and the bound result opens its notes with exactly what was written (`notices._directive_note`: "scheduler_options: wrote '-l filesystems=home:eagle' as '#PBS -l filesystems=home:eagle' — …"). A refused details= keeps its reason and remedy (`_DETAILS_ERROR_CAP`, 800).

**A re-bind cancels nothing, and says so** (2026-10-16 `polaris_filesystems`, pi: the reconnect said "Nothing is started or billed yet" while a held pilot of the session sat queued). Before the drop, `warmth._ssh_left` reads what the SSH endpoint's compute shape leaves: its block if it came up (it idle-releases after its last task), and the pilots the last provisioning probe listed live (`ShapeRuntime.pilots`), each by its state then. After the bind `_left_checks_note` → `notices._ssh_left_note` names them, on this endpoint again or on the one this connect left — a held pilot never starts on its own, so it runs no task and never idle-releases; a queued one may still start, run the check queued with it and bill until it idle-releases — else the checks of ours not seen to finish (`_unresolved_count`; on the endpoint left, the words a bind elsewhere always used), and that `stop_endpoint` cancels every block of that endpoint, these included. Whenever it says anything (or a facility endpoint's block was left), the terms note leads "Nothing new is started or billed by this connect" instead of "Nothing is started or billed yet" (`_connect_terms_note(left=True)`, the MEP attach too). The decision (2026-10-20): the re-bind does NOT cancel a held pilot. A connect has no stop's evidence and no confirmed release channel (the login shape is being proven again), a switch cancels nothing either (the stop is the one place blocks are cancelled, with its honest `down`/`draining`), and a held pilot bills nothing while it is held; what was missing was saying it, and how to end it. ## Consent is per conversation; a fresh bootstrap is proven (live findings, 2026-09-04)

Three fresh-user sessions on globus1 showed: (1) the connect right after our own `bootstrap` re-finds the endpoint online
and reads as `reused` — which skipped the proven-cache commit forever and told the agent it had "reused an already-online
endpoint" seconds after a fresh start. `AppCtx.bootstrapped_facilities` records the facilities THIS session bootstrapped;
`_commit_proven_facility` skips only a reuse of an endpoint from before the session, `_reuse_note` says "reconnected to
the endpoint this session started", and the result's `reused` flag is False for our own start. (2) Claude Code's
auto-memory carried a previous session's "confirmed config" into the next one and the agent registered the facility
without asking — the proposal notice now says the confirmation must come from the user in THIS conversation and that the
probe must not be re-run over the agent's own ssh. (3) On the silent (wait-and-continue) login path nothing named the
identity that landed; `_connect_facility` now prefixes "Globus login landed as <identity>" to the result.
