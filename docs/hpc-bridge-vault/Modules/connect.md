# connect

> [!abstract] Role
> The connect flow the agent drives: the Globus login gate FIRST, the resolution ladder (explicit details this session → the registry → the local BYO cache → the SSH probe that proposes a config), the switch of shapes/state to the bound facility, the identity-blind MEP attach or the SSH bootstrap, the allocation listing over the free login shape. Also `_commit_proven_facility` (a BYO config is cached only once the login-shape canary answered), `_drop_failed_details` (a BYO config whose bring-up failed on the login node before that is dropped, not run again — below), `_drop_cached_config` (a config read from `facilities.json` whose bring-up failed or handed off leaves the session, to be read again — below, 2026-10-29) and `_drop_dead_pin` (an unreachable login-node pin is forgotten).

The login gate is [[login_gate]] `_stored_login`, the same as `authenticate`'s: a missing login and a stored one Globus refuses to renew (revoked or expired) both answer `needs_login` before ANY route runs — registry, local cache, a session's own entry, details=, the MEP attach, the bootstrap — so nothing copies the token store to a login node on a dead login (it did, live 2026-10-14's failure mode on an SSH facility); a check that cannot reach Globus carries on. A login that lands during the gate's wait calls `warmth._forget_identity_verdicts` first, as `authenticate` does — the cached identity label and the runners built on the old token are dropped — so "Globus login landed as …" names the NEW identity. `_connect_mep`'s attach error names a dead login (`_hpc_bridge_error`, [[notices]]).

Split step 10 (2026-09-03) — the last. The login-shape channel is injected (`run_login`) as in [[scheduler_ops]]; `server._connect_facility` is a thin wrapper supplying `server._login_runner(app)`, so the many tests that call it and patch `server._run_shell` keep working. `connect._connect_facility` is itself a thin wrapper around the flow, `connect._connect` (it opens an answer with a dropped config's failure, below). Tests that patch the probe patch `connect.discover_facility_details` / `connect._propose_or_ask`. A proposal binds nothing: `_propose_or_ask` records the facility id in `AppCtx.proposed_facility` so a `run_shell` made meanwhile is told to finish the connect with `details=…` ([[server]], No facility bound). `_connect` clears it first thing, so it always describes the LAST connect. A probe that answers `needs_preauth` sets the resume to `connect_facility(<id>, ssh_host=<host>)`: without the host an un-catalogued facility resolves to nothing and the resumed call answered `needs_facility_details` (review 2026-10-10). The account preset (`HPC_BRIDGE_ACCOUNT`) is passed to `binding._facility_from_entry` only for the facility `HPC_BRIDGE_MACHINE` names ([[binding]]); when a preset is set but not used, the bound result's notice opens with one clause saying so (`notices._unapplied_presets_note`: the variable and why — another machine, a facility endpoint, or a partition given in `details=` — never its value). `_prior_note` names a block a facility endpoint lets go of with `notices._left_block_clause`, the words a switch uses too. At the bind it records `AppCtx.terms_origin` (`binding._terms_origin`; `_discovered_partition` (`connect.py:137`) tells a bring-your-own partition the probe proposed, and details= kept, from one the details changed). Every bound result (`needs_account`, an SSH `provisioning`) states the next block's terms before any spend: `_next_block_terms` (`:144`) builds them from the config a new compute runtime would get (`warmth._seed_uec`, nothing built or started) into `block` and `notices._connect_terms_note` — the default queue and its source, the account needed (with the hint) or not, size and walltime, and the one question to ask, whose yes is the confirmation sent with the answer in one call (spend terms, 2026-10-14). On a MEP the terms are read before the facility's notes, so what fitting the config to its schema drops is said at connect. The warming notice promises "your allocations" only where the entry lists them, and an empty listing is said as one. The question never asks about a partition or account the facility would drop (`notices._dropped_term_notice`). The details' (or the cached config's) `scheduler_options` are written as directives first (`binding._directive_details`: a bare `-…` option gets the scheduler's prefix, an indented directive is unindented), the written form is what the session entry and the local cache keep, and the first bound result carries what was written, after the re-bind's notes (what an earlier binding left, its spend) and before the reuse note (`notices._directive_note`: "scheduler_options: wrote '-l filesystems=home:eagle' as '#PBS -l filesystems=home:eagle' — …", each line cut at 120 characters). The note waits in `AppCtx.directive_notes` until a result carries it: a details= connect that answers `needs_preauth` first (key accepted, a one-time code pending) is resumed with no details, and its resumed connect reports it then (review round 2, T7). A refused details= keeps its reason and remedy (`_DETAILS_ERROR_CAP`, 800; each echoed line cut at 120). A cached BYO config whose `scheduler_options` now hold a refused line (a shell command, another batch system's directive word, the account, the queue, the walltime or the size) is offered back as a PROPOSAL without those lines (`_cached_refusal_proposal`, `binding._accepted_details`: each left out with its reason; `proposed_drafts` seeded, so details= may leave env_setup out): the store is keyed on ssh_host, so the earlier remedy "connect with ssh_host= for a fresh proposal" re-read the same record and the agent looped (review round 2, T2).

**A re-bind cancels nothing, and says so** (2026-10-16 `polaris_filesystems`, pi: the reconnect said "Nothing is started or billed yet" while a held pilot of the session sat queued). Before the drop, `warmth._ssh_left` reads what the SSH endpoint's compute shape leaves: its block if it came up (it idle-releases after its last task), and the pilots the last provisioning probe listed live (`ShapeRuntime.pilots`), each by its state then. After the bind `_left_checks_note` → `notices._ssh_left_note` names them, on this endpoint again or on the one this connect left — a held pilot never starts on its own, so it runs no task and never idle-releases; a queued one may still start, run the check queued with it and bill until it idle-releases — else the checks of ours not seen to finish (`_unresolved_count`; on the endpoint left, the words a bind elsewhere always used), and that `stop_endpoint` cancels every block of that endpoint, these included. It ends with "To end it now, call stop_endpoint before confirming the new block". What `_ssh_left` read is kept per endpoint (`AppCtx.ssh_left`): the first re-bind dropped the shape it was read from, so a later connect to the same endpoint names it from there (the live polaris run's follow-up connect had fallen back to "a check … may still be queued", review T10); a confirmation there drops it (that block's probes list the endpoint's pilots themselves), as do a stop whose release was CONFIRMED (it cancelled them all; an unconfirmed one — a cold channel, a refused `qdel`, out of time — may have left a held pilot, which the next re-bind still names: round 3, #5) and a teardown. The reuse note also carries the facility's `select_note` ([[facility-remote]]): a reused endpoint whose template predates `select_options` does not render them, and only a teardown and a fresh connect fixes it. A pilot's wording follows its state ([[scheduler_ops]] `_pilot_fates`): held, refused as submitted, running, or waiting — on a limit that clears it may start later and bill. Whenever it says anything (or a facility endpoint's block was left), the terms note leads "Nothing new is started or billed by this connect" instead of "Nothing is started or billed yet" (`_connect_terms_note(left=True)`, the MEP attach too). The decision (2026-10-20): the re-bind does NOT cancel a held pilot. A connect has no stop's evidence and no confirmed release channel (the login shape is being proven again), a switch cancels nothing either (the stop is the one place blocks are cancelled, with its honest `down`/`draining`), and a held pilot bills nothing while it is held; what was missing was saying it, and how to end it. Concepts: [[Happy path]], [[Discovery today]], [[Facility catalog]], [[In-terminal Globus login]].

**The proposal's partitions (2026-10-24, [[Resource requests]]).** A `details=` without `partitions` takes the
proposal's (`AppCtx.proposed_drafts`, the same host), as one without env_setup takes its env_setup, so the bound entry
keeps what the probe saw. The next block's terms (`_next_block_terms`) carry D3's proposed slice, and the one question
asks whether it is enough.

## A details= that failed is not run again (2026-10-20)

Live 2026-10-16 (free sweep, fake `lmod`, `lmod_bootstrap`, Hermes): the agent's first connect carried a made-up `env_setup` (`module load gcc/10.2.0`) and the remote configure failed with Lmod's "module(s) are unknown". The refusal it got next (a `details=` without `env_setup`, no proposal) said to call `connect_facility(…, ssh_host=…)` without details for a proposed config; it did, and got the same Lmod error back. The `details=` branch stores the entry in `AppCtx.session_facilities` before the bring-up (it must: a connect while it is still `provisioning` polls it, and a one-time-code handoff resumes it with `connect_facility(<id>)`), and the no-details branch took that entry first, so it re-ran the failed config.

**Which failure drops a config — decided positively, by type (review round 1, 2026-10-20).** Every poll of a config still coming up re-runs the bootstrap's SSH steps (each connect resets `app.state`), so a rule read off the explanation's words dropped configs to a slow registration, a 503 from the manager check or a dropped connection, and kept ones whose own failure happened to quote "Permission denied". Now only `ConfigStepFailed` ([[facility-base]]) can drop one: raised by the steps that run through the config's `env_setup` — `configure`, `start` and `list` in `RemoteEndpointCLI` (`base.step_error`: never for ssh's own exit status 255), and the endpoint venv's check that stopped in the site prefix, its build (not a timeout) and "no uv, no curl and no python3" (`EndpointVenvConfigError`, [[facility-endpoint_venv]]) — and only when the step's last few meaningful lines (`ConfigStepFailed.tail`, `base.said_tail`, four lines: the final error and what printed just before it — pip's "Connection to pypi.org timed out" warning above its last error — never a login banner far above, a `.bash_logout` trailer or a title escape; review round 3 found a banner's "idle sessions timeout", a `sock.settimeout` frame and a `globus_sdk` path keeping real config errors, round 4 an earlier network cause dropped) name none of `notices._NOT_THE_CONFIG_WORDS`: a timeout (`\btimed out\b`, `timeout ?error`, uv's `network timeout`), a Globus error (`globus_sdk\.…error`, `GlobusAPIError` …, and globus-compute-endpoint's own "Network failure; unable to register endpoint: ConnectionError on request", exit 75, or "Endpoint registration blocked"), a lost ssh connection, an endpoint still registering, the login node out of processes or on a stale NFS handle, or its filesystem refusing a write (`_REMOTE_FS_REFUSED`: globus-compute-endpoint's own Errno 13 or read-only file system under `~/.globus_compute`, a full disk or quota — explained as REMOTE FILESYSTEM, as before 2026-10-20). A negative exit status (the local ssh killed) is ssh's, like 255. A venv build that could not reach PyPI or astral.sh, or found no room to write (read-only, full, over quota), stays a plain `EndpointVenvError` (`endpoint_venv._BUILD_NOT_THE_CONFIG`, read from the end of the build's stderr, else its stdout: `_build_tail`); a permission refused on the venv's own path is the configuration's (its base), and drops it. `notices._failure_of_the_config` is that rule; `_explain_provision_error` no longer applies its SSH and network categories to a `ConfigStepFailed` (ssh got through, so a "Permission denied" there is a file `env_setup` reads, not sshd). And a config whose bring-up got past `start` this session on an endpoint of its own (`AppCtx.details_started`; not one that reused an endpoint of an earlier config still online — none of it ran) is never dropped: each poll re-runs the venv check, whoami and list through env_setup, and a flaky node must not cost a config that started. Every branch of `_explain_provision_error` is pinned, with the decision, in `tests/test_failed_details.py`.

The states of a facility's `details=` config, and what a connect without details does in each:

| State | Kept in `session_facilities` / `pending_facility_cache` | A connect without details |
|---|---|---|
| coming up (`provisioning`: it got past `start`) | yes / yes | polls it (unchanged) — no failure of a later poll drops it |
| came up (login shape warm) | yes / no — cached to `facilities.json` | reconnects with it, zero SSH (unchanged), even after a later bring-up of it fails |
| equal to the config `facilities.json` holds as proven for that host | yes / yes | reconnects with it, as a proven config |
| failed for anything but the config — ssh, a host key, a timeout, Globus (service or login), registration, the remote filesystem, a token store, a venv in the way, an old uv | yes / yes | runs it again: what those answers' "call connect_facility again" asks for (unchanged) |
| one-time-code handoff (`needs_preauth`) | yes / yes | the resume runs it (unchanged) |
| **refused on the login node on its first bring-up** (`_failure_of_the_config`) | **no / no** (`_drop_failed_details`) | **resolves the facility afresh**: the registry if it lists the id, else a config already proven for that host, else a probe that proposes one (the host the dropped config named, when the call names none); never the dropped config |

Dropped rather than marked: every reader of `session_facilities` (the no-details rung, `_without_details`, [[scheduler_ops]]' pilot probe) keeps one meaning — a config the session keeps is coming up or proven — and none has to learn to skip a mark. What failed is kept apart, in `AppCtx.failed_details` (the host and the failure's notice), so the error stays visible. The failure's own answer ends with what a connect does next, in one piece with any "connect_facility again" before it ("This configuration (details=) is not kept[. So, to connect_facility again as above]: connect_facility(<id>, ssh_host=<host>) without details resolves the facility afresh — … — and does not run this one; with details= it runs the configuration given — this one again, or a corrected one (an env_setup left out of details= comes from the latest proposal for this facility)"). Every answer to a connect without details opens with it ("The details= given earlier for <id> failed to come up (<the failure, one line, ≤300 chars>) and is not kept: this connect did not run it."; a proposal carries it beyond its 1800-char cap, so no probe note is cut for it; a login gate, which resolved nothing yet, does not). A new `details=` for the id clears it the moment it is stored; so does a connect of the id that comes up (login shape warm, or a facility endpoint attached). A registry or cached entry is never in `pending_facility_cache`, so this rule never drops it (a cached one has its own, below: left-over local state, 2026-10-29). Popping the pending entry with the session one keeps the proven-only rule: a later warm bring-up on another config (the registry's, the cache's) can never commit the failed one to `facilities.json`.

**The binding stays; no tool brings the dropped config up.** The bind precedes the bring-up, so a failed connect leaves the facility bound (a mark, not an unbind: the smaller change). `_drop_failed_details` marks that facility object (`AppCtx.dropped_binding`: the object and the refusal), and `warmth._provision` refuses first, before any spend or state change, while no endpoint is up: `ensure_endpoint_up` answers `down` and `run_shell` `failed`, with the failure, the afresh route and "or give details= again" (`DroppedConfigError`, shown as it is by `notices._hpc_bridge_error`). The next bind (a new facility object) ends it; connect also clears it there.

**Not cleaned up (a known gap, older than this change).** After a failed bring-up no endpoint id is known, so `teardown_endpoint` and `stop_endpoint` answer "no endpoint was up" without SSH. What the bring-up left on the login node stays: in the lmod case, the Globus token store `bootstrap` seeded there because `whoami` failed under the broken env_setup (`~/.globus_compute/`, 0700, with `storage.db`, 0600 — a bearer credential), with the local `endpoints.json` record (`seeded_credentials=True`, no endpoint id) that says hpc-bridge placed it. A later bring-up that comes up reuses that store, and its teardown wipes it; a session that ends without one leaves it. Follow-up: a teardown that reads that record when no endpoint is known.

**A connect queued behind the failing one.** A connect without details resolves its config before it waits for `app.lock`. If the session's config for the id changed meanwhile (the call holding the lock dropped it, or a `details=` replaced it), `_connect` answers `_Again` once it holds the lock and `_connect_facility` resolves again (at most twice), so it never binds what the other call just dropped; its answer opens with the failure and still names a Globus login that landed in the first pass (`_Again.login_note`). The other way round, a failing bring-up drops only its OWN config (`_drop_failed_details` gets the connect's `entry`): a `details=` that replaced it while it held the lock is kept, polled and, once up, cached. A config equal to the one `facilities.json` holds as proven is compared through the model, so one an older plugin cached (without a newer field) counts. And a bring-up that comes up while another connect's `details=` waits commits only the config its binding was built from (`AppCtx.bound_entry`, `_session_is_ours`, in connect and in ensure_endpoint_up's warm login shape): the waiting one stays pending, never cached as PROVEN without having run.

The two refusals of a `details=` without `env_setup` (no proposal for the id; a proposal for another host) say what a connect without details does from where the session stands (`_without_details`): it resolves the facility afresh, or, while the session keeps a config for the id, it reconnects with that one and proposes nothing — unless the call names another `ssh_host`, which is resolved afresh under the same id and does not run the kept one (the other-host refusal names that call). They used to promise a proposal in every case; until 2026-10-29 the kept config won whatever `ssh_host` the call named, and a proposal for another host needed another facility id.

**With the scheduler_options rewrite (2026-10-20, #220 with #221).** A dropped config takes its directive note (`AppCtx.directive_notes`) with it, so no later answer — the cache's config coming up, say — reports a rewrite of the dropped one; given again, the config carries its note again. The comparison with the config proven for the host reads the stored one as the cache rung serves it (`binding._directive_details`): one an older plugin cached with a bare option, re-sent as it was, is that proven config, and is kept. A cached config whose `scheduler_options` now hold a refused line is offered back as a proposal (`_cached_refusal_proposal`): after a dropped details= it opens with the failure itself (`_connect_facility` opens no proposal with it), and confirming it with details= that fail drops it like any other (a stored record with a refused line is never served as it is, so it never counts as proven). In a bound answer the failure comes first, then what a re-bind left (`_left_checks_note`), the spend, the login, the presets and the directive note; on a facility endpoint's attach too, where `needs_account` also clears the failure. Pinned in `tests/test_integration_220_221.py`.

Not changed: a facility that cannot be built at all (`binding._facility_from_entry` raising) is not a login-node failure and keeps its entry.

## Left-over local state (Perlmutter report, 2026-10-29)

A user came back to Perlmutter weeks after connecting it: its config PROVEN and cached in `facilities.json`, its endpoint pinned to `login22` in `endpoints.json`. login22 no longer answered and their key no longer worked (NERSC: a key OR a password + one-time code). Each piece of local state stood in the way. Proofs: `tests/test_perlmutter_report_state.py`; fake-cluster cells `stale_login_pin`, `kept_entry_after_failure`, `cached_password_otp`.

- **The dead pin is probed where ssh connects (1a).** `_drop_dead_pin` checks that the facility's own host still answers before it drops a pin (else it is a client-side outage, and the pin is kept). It used to open a TCP connection to the ALIAS, and the user's alias was an ssh-config `Host perlmutter`, which no resolver knows. So the check always read as an outage and the pin was never dropped. It now probes the HostName `rebind` resolved for the alias (`ssh -G`, kept on the target as its HostKeyAlias). The old test stubbed the probe wholesale, which hid this. It now fakes `socket.create_connection` at the boundary. Still kept: a HostName the client cannot reach directly (a ProxyJump), as before.
- **A config read from the cache does not outlive its failure (1b, 3).** The cache rung puts the config it reads in `session_facilities`, and it used to stay there for the session. Neither a failed bring-up nor the user deleting its record from `facilities.json` removed it, so it won over every later connect. That included one naming another `ssh_host`. Now `AppCtx.from_cache` marks such configs (facility id → the `ssh_host` the call named). `_drop_cached_config` takes one out of the session when its bring-up fails or hands off (`needs_preauth`). This costs nothing, because the record is still on disk. The next connect resolves the facility afresh: the record again, or a probe if the record is gone. A connect that names no host re-reads the record for the host it was read under (`from_cache` keeps it), so the handoff's resume `connect_facility(<id>)` and a poll without `ssh_host` still find the record when the facility id is not its key. A `details=` config keeps its own rule (`_drop_failed_details`, above). It is the only copy, so it is not dropped for a failure outside the config.
- **An explicit other `ssh_host` wins (1b).** When a connect without `details=` names an `ssh_host` that differs from the host of the config the session keeps (cached or `details=`), that host is resolved afresh under the same id, and the kept config is not run for it. If a config proven for that host replaces the kept one, `_forget_kept_config` also clears the kept one's pending cache write, `details_started` mark and directive note. Otherwise the replacement's canary would commit the kept one as PROVEN. A proposal for the other host leaves the kept config in place for connects that name no other host. This replaces the review-2026-10-20 (7c) rule "another facility id".
- **A password + one-time-code denial on a proven host is the terminal handoff (2).** The bring-up path handed off only on `key_accepted_second_factor_pending`: key accepted, `keyboard-interactive` pending (Expanse, #87). NERSC's denial still lists `publickey` (`(publickey,password,keyboard-interactive,hostbased)`), so it read NO SSH ACCESS. Now a denial that would read NO SSH ACCESS, offers a password or keyboard-interactive (`is_interactive_auth_failure`), AND lands on a host this user has PROVEN access to is `needs_preauth` instead (`_preauth_handoff`). The proof of access is a `facilities.json` record for the entry's `ssh_host` (`_access_proven`), written only after the login canary answered there. `otp_ok` comes from `offers_one_time_code`, so this is the terminal command, not a code prompt. A stranger whose key is refused on a 2FA site (Anvil, a registry entry with no record) still gets NO SSH ACCESS. The discovery probe already handed off on first contact; only the cached/registry bring-up path lacked this.

## Consent is per conversation; a fresh bootstrap is proven (live findings, 2026-09-04)

Three fresh-user sessions on globus1 showed: (1) the connect right after our own `bootstrap` re-finds the endpoint online
and reads as `reused` — which skipped the proven-cache commit forever and told the agent it had "reused an already-online
endpoint" seconds after a fresh start. `AppCtx.bootstrapped_facilities` records the facilities THIS session bootstrapped;
`_commit_proven_facility` skips only a reuse of an endpoint from before the session, `_reuse_note` says "reconnected to
the endpoint this session started", and the result's `reused` flag is False for our own start. (2) Claude Code's
auto-memory carried a previous session's "confirmed config" into the next one and the agent registered the facility
without asking — the proposal notice now says the confirmation must come from the user in THIS conversation and that the
probe must not be re-run over the agent's own ssh. (3) On the silent (wait-and-continue) login path nothing named the
identity that landed; `_connect_facility` now prefixes "Globus login landed as <identity>" to the result.
