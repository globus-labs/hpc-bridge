# resources

> [!abstract] Role
> A block's size, pure (no I/O): what ensure_endpoint_up's `cores` / `memory_gb` / `gpus` / `nodes` / `whole_node` become in the runtime config, what a partition hands out (classified from the login-node probe's lines), what a block of a config gets there (the default slice), what is refused before any submit, what the wire says on Slurm and PBS, and the words and the cost of the terms. Design: [[Resource requests]].

## What it does

- **A batch-derived block's workers** (`WORKERS`, `hpcb_workers`): set by [[server]] `_ensure_endpoint_up(workers=…)` for a block [[batch]] derived from its rows (slots + 1), part of the block's identity, mapped to `max_workers_per_node` by [[facility-remote]] `dispatch_uec`; on a facility endpoint only `max_workers_per_node` itself, and only where its template renders it. Never a size of the terms, and never the session's choice (`compute_choice`): [[warmth]] `_apply_resources` takes a change of it alone for another block (review F1); the derived block's own size asked again is that block, its workers kept, and any real switch — size, partition, account — clears it (`_repoint`; review round 2, R2-H / R2-E).
- **The request.** `requested` (`resources.py:65`) turns the tool's arguments into runtime-config updates under hpc-bridge's keys (`SIZE_KEYS`: `nodes_per_block`, `cores_per_node`, `mem_per_node`, `gpus_per_node`, `exclusive`; None clears one) or a refusal for a malformed value. `memory_gb` is a number on every tool, a fraction included (review G4, 2026-11-05: 1.5 GB could not be asked; the counts stay whole). `size_key` makes the size comparable for a switch ([[warmth]] `_block_key`); `needs_new_template` names the keys only this plugin's templates render.
- **What a partition hands out.** `classify_slurm` (`:698`) and `classify_pbs` (`:811`) read the probe's `PSHAPE` / `PDETAIL` / `QOS` / `SELECT_*` and `PNODE` / `PQUEUE` / `PSERVER` lines into [[models]] `PartitionShape`s: per-core or whole-node with the evidence (`why`), the node's cores, memory and GPUs, per-job caps, Slurm billing weights (`billing_weights`), and for PBS the `place` a slice needs. `summary` is the proposal's note.
- **What a block gets.** `effective` (`:272`) returns a `Size`: on hpc-bridge's own template (`ssh`) whole nodes when asked or when the partition gives only those, a slice when asked on a per-core partition, or — D3, only where the endpoint's template takes it — the proposed slice of a per-core partition (`default_slice_cores`; memory from DefMemPerCPU, not sent, else the node's per core, sent); otherwise the facility's default as before. On a facility endpoint (`mep`) exactly the keys it receives.
- **The validation.** `refusal` (`:375`): a slice of a whole-node partition (a registry's `exclusive: false` default is no request for one: `chosen`), `whole_node=True` with fewer cores than a node, more than a node has, over a QOS per-job cap or node cap.
- **The wire.** `slurm_wire` (`:466`: `exclusive`, parsl's `cores_per_node` / `mem_per_node`, GPUs as `#SBATCH --gpus-per-node` in scheduler_options) and `pbs_wire` (`:485`: `cpus_per_node`, `mem`/`ngpus` merged into `select_options`, a `#PBS -l place=` only where needed), called by [[facility-remote]] `SlurmFacility.dispatch_uec`. A memory of whole GB goes as parsl's `mem_per_node` (GB); a fraction as its MB, never less (`mem_mb`): Slurm `#SBATCH --mem=<MB>M` in scheduler_options (parsl's `mem_per_node` takes whole GB only), PBS `mem=<MB>mb`. A facility template's memory key gets whole GB, rounded UP by ONE rule, `whole_gb`, which [[facility-mep]] `dispatch_uec` and `effective` (channel `mep`) share (review round 1: two rules had the terms say 2 GB where 3 were sent). A memory under 1 MB (`MIN_MEMORY_GB`) is refused (it had read "0 GB"). The terms say an asked memory as asked (`12.5 GB`, never `12 GB`).
- **The terms.** `charge` (`:523`: the most a block can cost, "8 cores × 0.5 h"), `size_words`, `multinode_note` (D2), read by [[notices]] `_block_terms` / `_terms_line`.
- **The per-core memory share** (the billed Anvil live test of 2026-11-10). `enforced_share_mb` (MaxMemPerCPU only — the one share the raise and `billed_cores` read) and `cores_for_memory`: where the wire sends a slice's cores AND its memory and the enforced share is known, a memory above the cores' share raises the cores to ceil(memory MB / share), the memory read as the scheduler gets it (`mem_mb`). `effective` applies it (`_cover`: `Size.cores_asked`, `Size.share_mb`), so `slurm_wire` sends `--cpus-per-task` at the raised count, the terms say it in hpc-bridge's words (`memory_cores_words`: "15.5 GB needs 9 cores' memory share on partition 'shared' (1896 MB each): 9 cores are billed, and the block asks for 9, not 8") and `charge` bills it. Live: `cores=8, memory_gb=15.5` on Anvil's `shared` went out as `--cpus-per-task=8 --mem=15872M`; Slurm raised the job to 9 CPUs and parsl's launcher `srun` died at once (`SLURM_CPUS_PER_TASK=9 != SLURM_TRES_PER_TASK=cpu=8`): the block FAILED in 5 s, the executor went to BadStateException, and the size words had said 8 cores. **Raise, not refuse:** holding the memory to the share and refusing would make the user ask again for what the scheduler gives and bills anyway; raising never fails at start and never understates. The default proposal never exceeds its cores' share (`_slice_memory`, `tenth_down`: 8 × 1896 MB is said 14.8 GB — it read "15 GB", which said back is over the share; a node's memory per core is held to a MaxMemPerCPU). `refusal` counts the raised cores against a node and a QOS cap (the proposed slice's, for a memory asked alone). The same rule on every other path that sends a block: a facility endpoint's wire raises the cores it sends beside its whole-GB memory ([[facility-mep]] `dispatch_uec`; 1.9 GB goes as 2 GB, over one core's 1896 MB), a Jobs-mode job's header ([[jobs]] `spec_of`), a batch's derived block ([[sizing]] `derive_block`'s refusals, [[batch]] `_is_derived` by the cores asked); an exported handoff's config, which goes out as written, is refused naming the cores to send ([[handoff]] `terms_of`). **Round 2 (Anvil's live `scontrol show partition`, 2026-11-10): only an enforced share raises cores.** `shared` reads DefMemPerCPU=1896 MaxMemPerCPU=1896 — Slurm's own MaxMemPerCPU enforcement added the CPU — while `gpu` reads DefMemPerCPU=3750 and no MaxMemPerCPU, where Slurm adds no CPUs for memory (round 1 fell back to DefMemPerCPU, and would have over-asked and over-billed there). Three cases: (a) MaxMemPerCPU known — raise, and the terms state the billed cores; (b) known to have none (`PartitionShape.max_mem_per_core_known` with no value: scontrol printed MaxMemPerNode, or MaxMemPerCPU=UNLIMITED; `classify_slurm` reads which) — no raise, no extra line; (c) not known (`share_unknown`: a registry entry stating no cap, a capture without the field) — no raise, and the terms say the scheduler may give — and bill — more cores than asked ([[notices]] `_memory_cores_sentence`, or the cost line's own "may bill too"). DefMemPerCPU alone only caps the default proposal's memory (at most cores × DefMemPerCPU). On PBS, which adds no ncpus for memory itself, only a share a registry entry states raises (`max_mem_per_core_mb`). The Anvil registry entry states `shared`'s 1896 MB; `debug`'s was never read and stays unknown. Tests: `tests/test_per_core_memory_share.py`, with a hermetic fake Slurm that raises the job's CPUs as Anvil did and a fake `srun` making 23.11's check, run on the block script the wire renders (parsl's own where importable).

> [!warning] The size is mapped only at the wire
> As with a facility's `key_map`, the runtime config keeps hpc-bridge's names and the session's explicit choice; the default slice and each scheduler's rendering happen in `dispatch_uec`, so a partition switch re-derives the default and a whole-node partition overrides a slice default. Writing the D3 slice into the runtime config would make it a "choice" that survives a switch onto a whole-node partition.

> [!warning] What parsl does (read from its source, not guessed)
> SrunLauncher runs `srun --ntasks <nodes>` — a worker pool on every node, as a step holding its CPUs; SingleNodeLauncher starts `tasks_per_node × nodes` pools, all on the first node; SimpleLauncher runs the pool once in the batch script. So N > 1 nodes take SimpleLauncher on both templates (D2). `cores_per_node` renders `--cpus-per-task` with no trailing newline (the template's blank line follows it); `mem_per_node` must be an int.

> [!warning] Never understate the bill (review round 1, 2026-10-24)
> Where the evidence is weak the block is a whole node: a Slurm block nothing asks to slice is parsl's default `--exclusive` (`why_whole` "parsl", or "old_template" on an endpoint whose template predates block sizes); a partition is per-core only with a DefMemPerCPU or OverSubscribe=YES/FORCE (not `CR_Socket`, not a whole-node partition's QoS twin); a facility endpoint's block is a slice only when `exclusive: false` reaches it, else its template's default (`whole_node` None), which `charge` costs as a whole node. A facility's own size directives are read in (`options_size` `:205`: `--exclusive`, `--mem=0`, a GPU line, PBS `ngpus`). `billed_cores` (`:343`) counts memory beyond the ENFORCED per-core share (MaxMemPerCPU only, since 2026-11-10's round 2) as cores. `Size.key` is what the block holds: the switch logic ([[warmth]] `_block_key`, `_apply_resources`) compares it, not the raw config.

> [!warning] A slice only on all the evidence (review round 2, 2026-10-24)
> No `--exclusive` sent is a slice only on a partition known to hand one out (`kind == "per_core"`) and, on a facility endpoint, to a template seen to render `exclusive` (`takes`, from [[facility-mep]] `renders`). Anywhere else a slice asked — `cores=`, or a registry's `exclusive: false` (Expanse's on `gpu`, `debug`, `large-shared`; Anvil's `standard`, whose QoS is `wholenode`'s) — is still sent (`Size.wire_slice`), but the terms say the partition decides (`whole_node` None, `why_whole` "unshared") and `charge` counts the whole node. `charge` returns None where a weight's amount is not known — a whole node of unknown cores, memory or GPU count is never costed as the cores asked, nor without its GPUs; `_whole` and `billed_cores` take a whole node's cores from the partition only. `options_size` is anchored (`--exclude=` is no `--exclusive`, `--mincpus`/`--job-name=x-c2` no `-c`), reads `--core-spec`/`-S`/`--thread-spec` as whole nodes (each implies `--exclusive`), and counts a bare `--gres=gpu` and `--gpus-per-task`.
