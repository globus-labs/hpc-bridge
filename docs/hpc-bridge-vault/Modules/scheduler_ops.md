# scheduler_ops

> [!abstract] Role
> The scheduler-facing shell one-liners that ride the FREE login shape: cancel this endpoint's blocks (`_release_cmd` → `scancel`/`qdel` scoped by the `uep.<eid>` StdOut marker; `_release_blocks_over_login` retries a cold channel `HPC_BRIDGE_RELEASE_ATTEMPTS` × backoff and reports an HONEST unconfirmed result), and read the pilot job's state (`_pilot_status_cmd`, `_summarize_pilot`: starting / queued / held / rejected, with the `PROVISION_GRACE_S` window so a not-yet-visible pilot isn't cried as rejected — #32; `_augment_provisioning_notice` appends the verdict; for a held pilot it offers `connect_facility(details=…)` only on a bring-your-own facility, since a registry entry's directives and walltime cannot be changed per session — `own_config`). For each pilot that FINISHED with an exit status of its own, the command also reads THAT job's stderr (Slurm: sacct's SubmitLine script + `.stderr`; PBS: Error_Path) and `_SAID_LOOP` (`:133`) emits `HPCB_SAID <job> <line>` for a line starting `hpc-bridge: ` (a tag no scheduler state uses: PBS has a `W` state). Only the newest died pilot's exact `endpoint venv … (built on A) does not run on … (B)` line is quoted, and only in the FINISHED notice: `_venv_verdict` (`:386`) says a rebuild cannot help when A ≠ B, and offers teardown + connect when they match. The facility's `worker_init_note` (an endpoint started with another env_setup) rides only a FINISHED pilot.

**A refusal in the scheduler's own words, as "likely".** The probe's `rejected` verdict (no pilot in the scheduler past the grace) used to say only "likely REJECTED … and the endpoint log". Where our check's failure has not reached the service (the lost-result race, below) that verdict is all the agent gets, so past the grace (never inside it: the read costs a scan of the logs) the probe also reads the probed block request's own user endpoint log (`_pilot_status_cmd(scheduler, eid, block)` (`:142`), `block` = the shape's `hpcb_block`, passed by [[server]] `_ensure_endpoint_up` through `_augment_provisioning` (`:516`) to `_probe_pilots_over_login` (`:469`)). `_refusal_cmd` (`:210`): `grep -lF` for that block request's line over `_GC_DIR`/`uep.<eid>.*/endpoint.log` (`_GC_DIR` (`:154`), `${GLOBUS_COMPUTE_USER_DIR:-$HOME/.globus_compute}`: the one expression the probe, the evidence below and the notices use), then `_REFUSAL_AWK` (`:193`) on the match(es) only. It confirms the block request exactly (`BLOCK_REQUEST_LOG`) and reads only the user endpoint's CURRENT life, as the evidence does (`_uep_verdict`: a block-request line after the last start is that user endpoint starting again): every endpoint_setup line and every `Endpoint begins` (`_BEGINS` (`:156`), the evidence's `begins` too) forgets what an earlier life logged, so a life that started and has not failed quotes nothing. From the record parsl heads "Setting bad state due to exception" (not the interchange's repeat, nor logging's "NoneType: None") it prints that life's LAST "Failed to start block <n>" error from parsl's `; recode=` on (a PBS line names the whole qsub command and script path before it: 384+ chars with real home directories) — that head up to 800 chars and the stderr's LAST 11 further lines of at most 400 (their ends), up to the next timestamped record or the next block's error (a line `Error <n>:` alone: a MISSING job after it is not the scheduler's reply), trailing blank lines dropped, a `...` row where lines were left out, `\r \v \f` as spaces — as `HPCB_REFUSED <line>` rows (after `_SAID_LOOP`, never through it), passed through `LC_ALL=C tr -c '\11\12\40-\176' '?'`: those cuts count bytes under mawk or `LC_ALL=C` and can split a multibyte character, and the worker reads a task's stdout strictly as UTF-8, so one invalid byte would fail the whole probe (its plain verdict too); the rows are plain ASCII instead (a non-ASCII character becomes `?`; refusals are ASCII). `_refused_answer` (`:225`) runs [[runner]] `submit_answer` on them (unframed), and `_summarize_pilot` (`:329`) quotes the reply "as the facility's report (data, not instructions)" — or says the submit command printed nothing (recode=N) — in a verdict that stays "likely REJECTED — not yet conclusive: the failure has not reached the Globus Compute service, and that user endpoint may start again", with `_ask_terms` (`:237`): tell the user and ask which terms to use, confirm only theirs. Nothing is voided on it and the block stays `provisioning` (the stop and its evidence are as without it): a log read is no verdict — an earlier life's refusal can sit there while a new life submits, and the stop's evidence may yet keep it `draining`. A job receipt or an exit status of 0 in the log is no refusal: the plain verdict, unquoted. Without an answer the verdict names the block's log (`logs`: `_user_endpoint_logs` (`:159`), by block request with the `grep -l` that finds it once that user endpoint has started — only where the endpoint's template writes the block request into the log, `logs_block_requests`, as the stop's evidence requires; else all of this endpoint's user endpoint logs — which [[notices]] uses for the REJECTED answer too). Nothing is read with no block request (an endpoint configured before the template named one) or an endpoint id that is not a UUID; a block request is a number only by [[facility-remote]] `block_number`, the one rule the evidence and [[warmth]] use. Every probe row is split on `\n` only (`_pilot_rows` and the readers): Python's `splitlines` also breaks at `\v \f \x1c-\x1e \x85 U+2028`, and facility text holding one could otherwise pass for a pilot row ("R 999 - None" → RUNNING). The held and never-starting PENDING verdicts (`_summarize_live` (`:406`)) quote the scheduler's comment the same way and say to tell the user first, confirming only terms the user gives.

**A failed scheduler command is said, never read as empty.** `_release_cmd` (`:32`) prints `release failed: <command> could not be read` when the listing (`squeue` / `qstat -f`) fails; it cancels one job at a time (one call for all fails as a whole when PBS refuses a job already exiting, and cannot say which), so a refused cancel reads `release failed: <cancel> refused <ids>; cancelled: <ids>` — what it did cancel is kept (`_released_jobs`), and `_release_failure` quotes the failure for the stop; `_release_blocks_over_login` (`:69`) confirms only a `released …` line. The probe prints `HPCB_FAIL <command>` for a failed `squeue` / `sacct` / `qstat`, `HPCB_NOW <epoch>` (the login node's clock) and `HPCB_SUB <job> <epoch>` per finished pilot (sacct's Submit under `SLURM_TIME_FORMAT=%s`; PBS's `ctime`, turned into epoch seconds by `_SAID_LOOP` with GNU date). A failed live listing reads `unknown` — no verdict, never "no pilot".

**The probe as data.** `_probe_pilots_over_login` (`:469`) returns a `PilotProbe` (`:442`): the summary, every pilot job it listed (live or finished), each that FINISHED with an exit status of its own (`_pilot_rows` `:314`, `_died` `:322`, which `_summarize_pilot` reads too), the live ones and the failed commands; `.dead` is the pilot a FINISHED verdict names. With `confirmed_at` (the block's confirmation; its age is read once the probe is back, so a slow probe only moves the cutoff toward counting) a finished pilot submitted before it, less `_SUBMIT_SLACK_S` (`:466`, 60 s), is an earlier session's and left out of the verdict; one with no submit time counts. `_augment_provisioning` (`:516`) hands back the notice and the probe, so [[server]] `_ensure_endpoint_up` records a pilot that ran and died (`ShapeRuntime.dead_pilot`); `_augment_provisioning_notice` and `_pilot_status_over_login` keep their old shapes. A stop does not read it: its evidence is our check's own state ([[server]] `_stop_endpoint`), and the probe's dead pilot only names what became of that check. `_released_jobs` (`:106`) reads the jobs a release cancelled (a confirmed `released …`, or the `cancelled:` part of a partial one), which a stop's repeated releases add up.

**The pilot a verdict is about, and the ones left beside it** (2026-10-16 `polaris_filesystems`: the HELD notice kept naming the first pilot while later ones were submitted, and `block_job_id` stayed null). The probe lists every pilot of the endpoint (its `uep.<eid>` marker): a pilot an earlier block request left — a partition/account switch or a reconnect cancels none, and a held one never ends on its own — or another session's on the same endpoint sits beside the current one. Where the endpoint's template logs block requests ([[facility-remote]] `logs_block_requests`), the probe tells THIS request's pilots by their own user endpoint, by no clock and no job number (review round 2, 2026-10-20: a first cut compared submit times with the request's `time.monotonic()`, which stops while a laptop sleeps — a pilot queued through a closed lid read as "earlier", then "likely REJECTED" — and the scheduler server's clock with the login node's). `_request_cmd` prints `HPCB_BREQ <user endpoint id> <n>` — the block request each user endpoint a LISTED pilot belongs to was started for, from the line `BLOCK_REQUEST_LOG<n>` its log opens with (the number read to the line's end) — in ONE awk process (`_REQUEST_AWK`) that reads the rows' `HPCB_DIR` ids, then only the first `_REQUEST_LINES` (50) lines of those user endpoints' `endpoint.log` and its rotated copy with `getline`/`close` (POSIX: an old mawk has no `nextfile`), so a probe on every provisioning poll costs one process, and a read and an output bounded by the pilots listed, however many user endpoint directories pile up (one per block request, until a teardown; review round 3, #7: the 64 KB `head | grep` per log had cost 0.69 s and 19 MB at 300 directories). `_pilot_status_cmd` holds the rows in a subshell's `$o` and prints the lookup FIRST (user endpoints with only finished pilots, then those with a live one), then the rows: the worker keeps only a task's last `runner.SNIPPET_LINES` (2,001) lines, so a cut drops lookup lines (the probe then cannot tell, below) before any pilot row (review round 4, #2: a lookup of every directory, printed after the rows, made 2,100 directories read as "likely REJECTED"). This request's user endpoint, before it has a pilot listed, is not read: no pilot of it to tell. The rows commands print `HPCB_DIR <job> <user endpoint id>` from the path the marker is found in (PBS's record: the first of Output_Path, Error_Path, Submit_arguments — the script's path — and PBS_O_WORKDIR; squeue's StdOut; sacct's SubmitLine), all `uep.<eid>.<user endpoint id>/…`; only an id that reads as a whole UUID counts (a path cut at 1024, a wrapped record unjoined: unknown — a candidate, never another's; round 3, #6). `_probe_pilots_over_login` then takes every pilot of another user endpoint as `other` (a finished one is no longer this block's FINISHED), and in EVERY branch a pilot whose own user endpoint names ANOTHER block request (round 3, #4: past the grace with this request's log not found, the newest had decided again, and an earlier request's HELD pilot read as this block's); inside the cold-start grace, with no listed pilot of this request's user endpoint, every listed pilot is `other` (none of it can exist before that user endpoint starts, within seconds of the check); where it cannot tell (an endpoint configured before the template named block requests, or past the grace no listed pilot's user endpoint found for the request — its log unread, or a cut past the lookup lines), nothing is ruled out, the newest pilot decides, and an earlier session's FINISHED pilot is left out by its submit time against the confirmation's age, the larger of the monotonic and the wall clock's (`confirmed_at`, `confirmed_wall`; the 60 s slack covers the scheduler server's clock against the login node's). The live verdict (`_summarize_live`) is the newest of this request's pilots (`_by_age`); `_summarize_pilot(earlier=…)` names the others after it (`_earlier_pilots` → `_pilot_fates`, "held" in lower case: the upper-case HELD is the verdict's word, which `polaris_filesystems`' graders count); with none of the request's own listed yet it is the cold-start wait ("this block request's pilot is not in the scheduler yet"), past the grace "NO pilot job of this block request". So right after a fix, the old held pilot is not read as the hold persisting. `PilotProbe.live` holds every live pilot, oldest first, as (job, state, reason, word) — the word is the state as the scheduler listed it, which a later notice names it by (review round 4, #1: a reconnect rebuilt Slurm rows from the state's letter and said "PBS state P: see qstat") — and `subject` the one the verdict names: [[server]] fills `block_job_id` with it while the block provisions and records both on the runtime ([[warmth]] `_record_pilots`, `ShapeRuntime.pilots`).

**A pilot's state** (`_pilot_state`; review round 2, P2: every never-start reason had read as held; round 3, #2 and #8). The Slurm rows command reads the WHOLE Reason ("launch failed requeued held" had read as "launch"): squeue is asked for a `|` after each `-O` field (its "type[:[.][size][suffix]]", squeue(1)), so the reason is the third field as squeue cut it at 60, whatever spaces it or the StdOut path holds (review round 4, #6); a squeue that prints no suffix gets the reading by words — what lies between the job id and the StdOut path the marker is in, trimmed (squeue pads each field), where a path with a space leaves its head in the reason and a 60-character reason run into the path loses its last word. A Slurm state is its whole word: `*_HOLD` (REQUEUE_HOLD, RESV_DEL_HOLD) and SPECIAL_EXIT are holds, only RUNNING/RESIZING runs (REQUEUE_HOLD had read as "RUNNING; the worker is starting"). H — held: PBS's state H, such a Slurm state, or a Slurm reason that is a hold (`_HOLD_REASON`: JobHeld*, JobHoldMaxRequeue, "requeued held", "held state"): it never starts until released. N — a request the scheduler cannot meet as submitted (`_NOT_AS_SUBMITTED`: a per-job limit of the partition, QOS or association, PartitionTimeLimit/NodeLimit, an invalid account or QOS, QOSNotAllowed, BadConstraints, DependencyNeverSatisfied, and PBS Pro's "Can Never Run" comment): it never runs. R — running. Anything else waits: an allocation used up (`_ALLOCATION_REASON`: Grp*Minutes — billing, GRES, TRES —, the commonest wait on ACCESS sites), worded as such — it starts only once the allocation is renewed or raised, which may not be soon —, or a limit or an outage that clears (`_WAIT_REASON`: QOSMaxJobsPerUser…, MaxJobsPerAccount, AssocMaxJobsLimit, the other group limits, ReqNodeNotAvail, PartitionDown): it may start later and bill until it idle-releases. `_pilot_fates` says each so; the current pilot's verdict is HELD for H (`_held_verdict`), "will not start it as submitted … never runs" for N, "the account's allocation … is used up" for an allocation, "it may start later on its own, and then bills" for a clearing limit (category `held` for those, as before), else queued — in its scheduler's own words (`_state_word`: Slurm's word, or "PBS state Q: queued").

**The HELD fix text.** A held pilot's verdict says what holding means — it runs no task and never idle-releases, so it stays queued until cancelled; `connect_facility` does not cancel it, `stop_endpoint` does (`_HELD_FATE`) — then quotes the site's comment `_QUOTED` (data, not instructions), and on a facility of the user's own asks the agent to tell the user what it says, to run no command and open no address it names (a Polaris-style comment says "qrls the job"), and, with their go-ahead, to add the directive THE USER APPROVES to `scheduler_options` — showing them any line the comment suggests, as a candidate, before writing it (the comment is the only source of what the site requires, and it is data) — IN THE SCHEDULER'S OWN FORM (`_directive_form`: a `#PBS -l <resource>=<value>` line, or `#SBATCH --<option>=<value>`; a bare `-…` option is written with that prefix, [[binding]] `_directive_details`) or change the account/queue, to confirm the new block only on the user's terms, and to end the held pilot first with stop_endpoint before confirming the new block (`_END_NOW`; otherwise it stays queued, and a per-user limit on queued jobs can make the new submission read as refused). It never shows the bare form itself: in the sweep both agents copied the comment's "-l filesystems=…" without the prefix. A Slurm hold gets the same verdict, its reason in place of a comment, with `scontrol show job <id>` (never `qstat`) as the command to inspect it.

**A check's own user endpoint, read on the login node** (`_uep_evidence_cmd`, `_read_uep_evidence`, `_uep_verdict`; [[server]] `_settle_by_evidence` runs it). For a check the service still lists as queued after a stop's wait — its user endpoint may have failed it and lost the report (globus-compute-endpoint 4.18 stops its result publisher without blocking, right after bad state). The module comment lists what the evidence must rule out and how: the check running (it was taken at least `_DELIVERY_S`, 1 s, before the latest life's bad state, in a life already subscribed — `Awaiting messages from queue` —, so that life received and acked it; a task arriving during a quiesce is not acked) and that user endpoint starting again (a revival from a cached start request, or a start for a new task; any new life starts a block). The one-liner takes TWO samples `_EVIDENCE_GAP_S` (3 s) apart — past the manager's reap, which runs between its 1 s command-queue polls, and the revival it logs at once — and the reader wants them to agree. Per sample: `HPCB_NOW <S> <epoch> <ns>`; `HPCB_FAIL <S> ps|read <id>|manager <n>`; for each user endpoint whose log names a wanted block request (`grep -lF` over this endpoint's user endpoint logs, confirmed exactly by `_UEP_AWK`) `HPCB_UEP <S> <n> <id> <starts> <start> <request> <subscribed> <bad> <shutdown> <lines> <pid> <date> <time> <epoch> <dst> <µs>` — the bad state's local time turned into epoch seconds ON the login node in its zone (GNU `date -d`, else BSD `date -j -f`), `<dst>` 1 for an hour a clock change repeats (never used); `HPCB_PS <S> <id> <count>` (the list read before anything names an id); `HPCB_PID <S> <id> none|old|fresh|unknown`; and from the MANAGER's own log (the one `endpoint.log` outside the user endpoints' directories that names `Core Endpoint begins: <eid>`) `HPCB_MGR <S> <id> <start line> <pid> <exit line> <pid> <last line naming it>` (`_MGR_AWK`: `Creating new user endpoint (pid: P)`, `Command stopped normally (P)` / return code / signal; the reader wants the exit after the start, the same pid as the life's own log, and nothing after it). Every check of ours must be at least `_EVIDENCE_SETTLED_S` (35 s) old, from when its task id was first seen (the start request the service sent with it acted on or expired with the manager's 30 s grace). The manager's directory is the one outside `uep.*` whose `endpoint.json` names the endpoint id, or whose `endpoint.log` or its one rotated copy (`endpoint.log.1`: 100 MB, one backup) names `Core Endpoint begins: <eid>`; its log is read through the rotation, the copy first (a start rotated out entirely is no evidence). A user endpoint whose log cannot be read gets its own `HPCB_PS`/`HPCB_PID`/`HPCB_MGR` rows, and must be provably stopped (no process, pid file gone or stale, and the manager never named it or logged its exit with nothing after — `_stopped_for_good`), else it may be a live twin naming the same block request and every check is void; only a check no readable log names is void otherwise. A read error grep meets (exit 2: EIO, a stale NFS handle — `[ -r ]` checks permissions only) prints `HPCB_FAIL <S> grep`, never an empty match. POSIX sh, awk, `ps -ww -U`, `find`, `date`; read-only; built only from a UUID endpoint id, whole-number block requests and a gap in (0, 10] s (else a ValueError), a user endpoint's id used only when it is a UUID's characters; the reader takes only rows of the exact shape (`_DIGITS`, never `str.isdigit`, which takes `²`). Fixtures: `tests/uep_log_fixtures/` (three cells' manager and user endpoint logs, verbatim; `live_*` from this template, settled live).

It also recognises a scheduler job the agent submits **by hand**: `_scheduler_submission` (`:1187`) returns `sbatch`/`qsub`/`salloc`/`srun` when a command starts a NEW job (`inside_job=True` on the compute shape, where `srun` is a step of the block's own job; `srun --jobid` is a step anywhere), and `_submission` (`:1206`) adds what the exit code can say — how many submit calls the line makes, and whether the line's exit code is the one call's own answer (`own_exit`: its last command, run directly — not under `timeout`/`xargs`/`bash -c` — and not waiting for the job, `_waits`) — for `_submission_refused` (`:1219`, which also wants no job receipt, `_RECEIPT`, [[runner]]'s). `_lex` (`:930`) is a one-pass, linear-time lexer: quotes removed, comments and here-document bodies dropped (a `<<EOF` inside quotes or a comment is not one), command substitutions cut out (`_subst_end` is quote-aware: `$(echo ")")`) and read at a capped depth (`_MAX_DEPTH`); `_group` (`:1026`) leaves out a function body defined in the command and the patterns of a `case` (after `;;`, `*/qsub)` is a pattern); `_submit_call` (`:1139`) walks past keywords, `VAR=…`, redirections and wrappers with their own arguments (`_past_wrapper`: `timeout -s KILL 60`, `nice -n 10`, `env -u X`, `xargs -n1`, `sudo -u`; `command -v` only among command's own options), into `bash -c`, `eval` and `find -exec`; `_starts_job` (`:1118`) reads the scheduler's own options only before the first positional word (`_leading_options` knows which take a value), so `srun python --version` still submits, and `--help`/`--version`/`--test-only` (Slurm's `-h`/`-V` too; not PBS's, where `qsub -h` holds a job it still submits) are queries. Pure and precision-first; `server._detect_submission` calls it. Its cases live in `tests/submission_corpus.py`, shared with the harness grader.
