# batch.py

> [!abstract] Role
> Batch phase 1: many independent tasks fanned out and collected through the session's ONE confirmed compute block — `run_batch`, `status`, `cancel` ([[The MCP tools]]) — with every row recorded in the durable [[ledger]]. Design: [[Batch and swarm execution]] §4, §5, §10.

## What it does

- **The template** (`validate`, `substitute`, `row_values`): `{name}` for a row's own identifier keys, `{row}` for a plain-value row, `{index}` — each becomes `"$HPCB_F_name"`, a REFERENCE to an environment variable the wrapper sets to the value (carried base64-encoded): the value never enters the command's text (review round 1, L3). That reference is data only where it is a bare word of a command the OUTER shell runs, so `_template_decisions` — a conservative reading of bash's grammar, a stack of frames (`$(…)` opens a quoting context of its own, so `out="$(basename {x})"` is a bare word; quotes, here-documents, `$((…))`/`((…))`/`$[…]`, `[[ ]]`, `${…}`, array subscripts and backticks are frames a placeholder is refused in) with bash's own comment rule (`#` begins a word after a blank or `;&|()<>`, never after an escaped char) — substitutes only where it is certain, and refuses everywhere else (review round 2: `x\ #` and `)#` had hidden a quote that opened a `bash -c` string). It also refuses, by the words of the simple command (`_code_arg`), a placeholder that is a shell's `-c` code, an interpreter's code flag (`python -c`, `perl -e`, `node -e`…), awk's or sed's program, any word of an `ssh`/`watch`/`parallel` command, of an eval-like command (`eval`, `trap`, `let`, `read`, `declare`, `printf -v`, `test -v`/`-eq`…), and after any `#` it may read otherwise than bash; and a row's variable written straight into such a string or into an unquoted here-document. Round 3: also any placeholder before a pipeline stage, a here-string (`<<<`) or a `>(…)` that feeds a program reading CODE from its standard input (`_reads_code_from_stdin`: a shell or interpreter with no script file, `xargs` running one or a command outside `_XARGS_SAFE`, `parallel`, `source /dev/stdin`, `awk`/`sed -f -`, `dc`/`ed`/`at`/`ssh`/`sqlite3`…) — every placeholder before it in its frame, since a loop or a group feeds a pipe too; anything inside `<(…)`/`>(…)`; a placeholder in a wrapper's option-or-command slot (`_wrapper_slot`: `env {x}` with `-S …` ran the command; `sudo`, `timeout`, `xargs`, `nice`, `exec`…); and printf's format (`-v` assigns). `&>`, `>&` and `|&` are read as the redirections they are. `dash_rows`: `run_batch` names the rows whose value for a placeholder starting a word (no `--` before it) begins with `-` — a warning, since `-5` may be an option's argument. The refusal advises a bare word, the value as an inner shell's argument (`bash -c '… "$1"' _ {x}`), or a QUOTED-delimiter here-document reading the variable from the environment. The limit, said in the docs: a value reaches the command as one word; never hand it to eval, `sh -c` or an inner interpreter as code. `${name}` is the shell's own and never a placeholder; other brace text stays as written. [[runner]]'s `submit` brace-escapes the whole script for ShellFunction's `cmd.format()` afterwards.
- **The window** (`capacity_for`): `max(1, workers - 1)` — the block's `max_workers_per_node`, or the worker count a check or a result reported (`PARSL_WORKER_COUNT`); one worker stays free for interactive commands. On a one-worker block a batch task holds it, and an interactive `run_shell` waits behind it, its answer naming the batch (`shared_worker_note`).
- **The admission gate** (`admit_ok`, `_admit_locked`, under `app.lock`): a row is sent only while the block's remaining walltime, read from INSIDE the block (the canary's `HPCB_REMAINING` and every result: [[session_shell]] `REMAINING_SH`), is at least `task_walltime_s` + `MARGIN_S` (30 s). Unknown admits nothing. Past it the batch pauses at `needs_confirmation`, naming the walltime.
- **The wrapper** (`task_script`, one per attempt), in the batch's OWN directory `<results_dir>/<batch id>/` (`batch_dir`; batches may share a `results_dir`): the wrong-block guard; the free-space floor (`MIN_FREE_MB`, rc 75) BEFORE the claim; the attempt claim `mkdir tasks/<i>/attempt-<n>` — only an existing attempt is a duplicate (S4), any other failure (EACCES, ENOSPC, EDQUOT) fails the row with the OS's own words; the batch's `CANCELLED` marker checked before and watched during the run; `meta.json` at start; the command in its own process group (`set -m`) under the session's cwd/env read-only, the row's values set after; stdout and stderr through FIFOs, each capped at `OUTPUT_CAP_BYTES` with a rolling tail of the stream's real end; a watcher that kills the group at `task_walltime_s` (rc 124) or on the marker (rc 143); when the command exits, what is left of its group (background children) is sent TERM, then KILL after `KILL_GRACE_S`; each stream's own `tee` (reading the command's FIFO, feeding the head's and the tail's) is then given `READER_GRACE_S` and killed, so a child outside the group (setsid) holding a stream ends the task with the tails of what arrived; the readers never hold the wrapper's own stdout (L6, round 2); the background jobs never hold the result's file descriptors; one `HPCB_RESULT {json}` line (`parse_result`).
- **Its own runner** (`_batch_runner`, `_runner_for_block`): a COPY of the compute shape's config (the same user endpoint, so the same block) on an Executor of its own, whose task group the service mints and whose results nobody else consumes (S1); rebuilt when the shape's config changes (a new confirmation's fresh `hpcb_block` is a new user endpoint — live, the batch kept sending to the reaped one's), the old one closed once nothing is out. The task group is on the record as soon as the service mints it.
- **One pass at a time** (`tick` under `_Run.passing`): the loop's and a status call's passes never interleave, and admission waits out a block switch (`switching`).
- **Settling** (`_collect`, `_settle_result`, `_settle_failure`): a result wins whenever it arrives; a guard refusal is the block's reap (the row goes back, the batch pauses, and the block that answered is named in `blocks_left`); a ManagerLost/WorkerLost failure is `lost` on evidence (a retry for `idempotent`); a client-side SDK failure on a sent task (its AMQP result watcher quit: "SDK thread quit unexpectedly.") is NOT a result — the row keeps its slot, the runner is rebuilt and the result is pulled by REST (`_client_side`, `_runner_broken`; L2: the freed slots had overfilled the workers); a submit with no task id is `submit_unknown` (`_reconcile`: EVERY task group the batch's runners were minted is read — `Ledger.task_groups`, L5; a stray task's result settles the row it names; while one is pending nothing is decided; then an idempotent row is sent again; a non-idempotent one never is, and is never called lost: the failed POST may have queued its task in a group of its own, which no runner learnt — round 2 withdrew round 1's `lost`-on-absence rule). Such a row HOLDS THE STOP (`unknown_since` set, `unheld` unset; `Ledger.unknown_holding`, `unknown_note`) — an idempotent one even after it is sent again, its first copy may be queued — until its copy's result comes back, or, on SSH, `_unknown_evidence`: `UNKNOWN_SETTLE_S` after the FAILURE, its config retired (a stop or a reap) and the user endpoint it targets (from the job's sacct SubmitLine) gone, with no pilot of it queued, in two looks a few seconds apart (a task left pending at the service does not restart a user endpoint; only a new submit with its config would, spike S5). On a MEP nothing clears it.
- **Evidence and presumption**: on SSH (`_evidence`) the jobs the ledger's rows in flight were sent to (this process's record, else the ledger's `sent_job`, else the last block seen — a dead server's rows too, L4) are looked up on the login shape; a job sacct (or PBS) says ended settles the tasks SENT TO IT `lost` on that evidence, marks the reap and pauses. For five minutes after (`_release_old_uep`, run by the background loop, which stays up for it: S5) the reaped block's user endpoint — read from its sacct SubmitLine — has its pilots cancelled by its own `uep.<eid>.<uep id>` marker: parsl starts one for the task that was out on the dead block, and no one confirmed it (live; recorded in `blocks_seen`) — unless the block the user confirmed after the reap has the SAME config, so the same user endpoint, whose pilot is then the user's block (S4). A new confirmation forgets what was known of the old block (`_sync_block`). `_presume`: a task IN FLIGHT with no result past `task_walltime_s` + `PRESUME_GRACE_S` since a block was seen is `presumed_lost` (keeps its slot, never retried, holds no stop): on a MEP every row out; on SSH a row no future of this process holds (a dead server's). Never a `submit_unknown`: absence is no evidence (round 2). The block evidence is this process's, else the ledger's `blocks_seen` (L4).
- **Restart** (`_adopt`, `_rest_pull`, `_reconcile_unsent`): a server finding a batch whose holder is gone takes the lease to COLLECT — by REST with the raw `v2.get_task_batch` (`collect_rest`; `Client.get_batch_result` drops failed tasks, S4) — pauses a batch that was admitting (spend lived in the old process), and starts the loop that keeps collecting. `run_batch(batch_id=…)` takes a batch over the same way: without `confirm_spend` it never resumes one (S7, rule 4). Before the lease is stale, a batch whose holder is gone (`Ledger.holder_alive`) reads `needs_confirmation`. A row the dead server queued without ever learning its task id is reconciled against the batch's task group: a task the ledger does not know settles the row its result names; with all accounted for, the row was never sent and goes back to the backlog.
- **The next block** (`_maybe_switch`, `_maybe_warm`): the user's yes at a walltime pause covers the NEXT block; once the tasks out on the block in front finish — and any submit of unknown fate is settled (L5) — on an endpoint hpc-bridge stood up (`fresh_ueps`) the shape is dropped and a fresh block confirmed; the block left runs out its last minutes, banked to its end and named in `blocks_left` (S8). Any pause, drain, abort or stop withdraws that yes (`pause`, `_apply_cancel`; S1: a drained batch had gone on to start a block). While a block is still starting the batch checks it as run_shell would. With the backlog empty the gate asks for nothing. On a facility MEP the next block can only start after the old one ends, and the batch asks again then.
- **Stop and cancel**: `pause_all` (called by [[server]]'s stops under `app.lock`, before anything is released), `retire_all` (the block's config, in the ledger), `in_flight_note` (the stop's busy refusal: every ledger batch's rows in flight on this endpoint, naming `cancel(id, 'abort')`), `unknown_note` (a batch's submits of unknown fate: the stop is `draining` naming them, never `down` — S3). `cancel` drains (keeps the backlog) or aborts: `write_cancel_marker` over the login shape, or on a MEP ONE small task, only to the batch's confirmed, live, not-ending block with a worker to spare (`_marker_block_why_not`; S2: a marker task could start a block nobody confirmed), never a second while one is out; the answer says when the marker was not written and that the tasks out then run to their end (S6). `blocks_left` (`_blocks_left`) names every block of ours that can still bill: the session's, `app.left_blocks` (a MEP stop's), the switch's, a block the facility started for a task of ours, and the reaped user endpoint while it is watched (S8). A tool call's pass is bounded: it waits for the loop's pass at most `LOCK_WAIT_S` (else `PassBusy`, and the answer is the ledger's view, saying a pass is running), never starts a next-block switch or a block check (the loop's, which `status`/`cancel` start if it is not running), and skips the lookups its budget (`CALL_BUDGET_S`) cannot cover; `cancel` runs under the progress heartbeat as `status` does (round 2: the lock wait had been unbounded).
- **`poll_uuid`, `record_interactive`**: `poll_task` by a Globus task id — a batch row, or an interactive task recorded when it went `running`; once REST cannot answer for an interactive one (no client, unreachable, no result), its rc and tail are read from the session dir over the login shape (`_session_result`; [[session_shell]] `wrap(result_key=…)` writes them).
- **`status(wait_s)`** (`_wait_for_change`) returns when a row settles or the phase changes, or when `wait_s` is up — not at the next pass (L8).
- **The journal's event rows** (`_journal`): `batch.admit` (with `in_flight`, `capacity`, `remaining_s`, `need_s`), `batch.settle`, `batch.pause`, `batch.resume` — what the harness grades the window and the gate from.

> [!warning] A plain `status` never resumes spend
> It collects and keeps a RUNNING batch admitting, but a batch at `needs_confirmation` resumes only through `run_batch(batch_id=…, confirm_spend=True)`, the user's yes. A block that ends must never become a block parsl starts for a task left at the interchange (#204's pattern) — the gate and the window are what keep the interchange empty when the block goes.

> [!warning] Abort never touches the block
> In phase 1 the batch shares the session's block: `cancel(abort)` writes the marker and lets each wrapper kill its own command. It never SIGTERMs the user endpoint or cancels the block, which would end interactive work too.
