# batch.py

> [!abstract] Role
> Batch phase 1: many independent tasks fanned out and collected through the session's ONE confirmed compute block — `run_batch`, `status`, `cancel` ([[The MCP tools]]) — with every row recorded in the durable [[ledger]]. Design: [[Batch and swarm execution]] §4, §5, §10.

## What it does

- **The template** (`validate`, `substitute`, `row_values`): `{name}` for a row's own identifier keys, `{row}` for a plain-value row, `{index}` — each becomes `"$HPCB_F_name"`, a REFERENCE to an environment variable the wrapper sets to the value (carried base64-encoded): the value never enters the command's text (review round 1, L3). That reference is data only where it is a bare word of a command the OUTER shell runs, so `_template_decisions` — a conservative reading of bash's grammar, a stack of frames (`$(…)` opens a quoting context of its own, so `out="$(basename {x})"` is a bare word; quotes, here-documents, `$((…))`/`((…))`/`$[…]`, `[[ ]]`, `${…}`, array subscripts and backticks are frames a placeholder is refused in) with bash's own comment rule (`#` begins a word after a blank or `;&|()<>`, never after an escaped char) — substitutes only where it is certain, and refuses everywhere else (review round 2: `x\ #` and `)#` had hidden a quote that opened a `bash -c` string). It also refuses, by the words of the simple command (`_code_arg`), a placeholder that is a shell's `-c` code, an interpreter's code flag (`python -c`, `perl -e`, `node -e`…), awk's or sed's program, any word of an `ssh`/`watch`/`parallel` command, of an eval-like command (`eval`, `trap`, `let`, `read`, `declare`, `printf -v`, `test -v`/`-eq`…), and after any `#` it may read otherwise than bash; and a row's variable written straight into such a string or into an unquoted here-document. Round 3: also any placeholder before a pipeline stage, a here-string (`<<<`) or a `>(…)` that feeds a program reading CODE from its standard input (`_reads_code_from_stdin`: a shell or interpreter with no script file, `xargs` running one or a command outside `_XARGS_SAFE`, `parallel`, `source /dev/stdin`, `awk`/`sed -f -`, `dc`/`ed`/`at`/`ssh`/`sqlite3`…) — every placeholder before it in its frame, since a loop or a group feeds a pipe too; anything inside `<(…)`/`>(…)`; a placeholder in a wrapper's option-or-command slot (`_wrapper_slot`: `env {x}` with `-S …` ran the command; `sudo`, `timeout`, `xargs`, `nice`, `exec`…); and printf's format (`-v` assigns). `&>`, `>&` and `|&` are read as the redirections they are. `dash_rows`: `run_batch` names the rows whose value for a placeholder starting a word (no `--` before it) begins with `-` — a warning, since `-5` may be an option's argument. The refusal advises a bare word, the value as an inner shell's argument (`bash -c '… "$1"' _ {x}`), or a QUOTED-delimiter here-document reading the variable from the environment. The limit, said in the docs: a value reaches the command as one word; never hand it to eval, `sh -c` or an inner interpreter as code. `${name}` is the shell's own and never a placeholder; other brace text stays as written. [[runner]]'s `submit` brace-escapes the whole script for ShellFunction's `cmd.format()` afterwards.
- **Row sizing** (batch row sizing, PR 2; pure rules in [[sizing]]): `run_batch(…, cores, memory_gb, gpus, concurrency, pin=True, pilot=0)` sizes each row the sbatch way. `_sizing_args` refuses a bad one by name.
  - **No block confirmed** (`run_batch`'s size-first branch): no size → `needs_sizing` with `facts` (`facts_of`: the partition's node, its caps, `candidates`), nothing recorded; a size with no `concurrency` → `needs_sizing` naming it; a full size → `sizing.derive_block`, and `ensure_up(app, confirm_spend, size=…)` ([[server]] `_batch_ensure_up`) asks for that block — its terms carry `derived_from` and the batch's `sizing`. A pilot with no block asks for the partition's proposed slice (D3).
  - **A confirmed block** is checked against what it MEASURED (`measure_of`: this batch's note, the shape's check, the ledger's `block_measure`): a row that cannot fit is refused with the numbers and the block it would need (`_would_need`); a concurrency past what fits is capped and said; a block of several nodes (its config or its measure) is refused (`_multi_node`, pointing to phase 3). No size on a CPU-only block **defaults** to 1 CPU, the block's share of memory, as many as fit (`sizing_defaulted`, said in the notice); a GPU block asks. An unmeasured block admits a sized batch nothing until its check measures it, then pauses it at `needs_sizing` if a row cannot fit (`_sized_now`, `pause_sizing`).
  - **Pilot** (`pilot=1|2`): those rows run alone with the whole block (cores = its CPUs, memory = its available), then `needs_sizing` with `proposal` (`sizing.pilot_proposal` over their own use).
  - **A row killed at a DEFAULT memory** (`_default_memory_killed`) pauses the batch at `needs_sizing` with a proposal from that row — it is run again only if the batch is idempotent; an explicit `memory_gb` keeps the plain kill.
  - **A busy slot** (`_slot_busy`, rc 76: the row found no free CPUs or GPUs on its node and ran nothing) goes back to the backlog after `SLOT_BUSY_BACKOFF_S` × the streak (`not_before`); the third in a row pauses the batch, saying a slot is held by something the server does not know of.
  - `run_batch(batch_id=…, cores=…, …)` resizes the backlog (`_resume`'s `resize`, checked against the measure; rows out keep what they hold) and resumes a `needs_sizing` pause with no new yes.
  - Status: `sizing` (with the block's `slots` and `bound_by`), `proposal`, each row's `peak_rss_mb`, `cpu_s`, `wall_s`, `nproc`, `cpus`, `gpu_ids`, `why` and `over_size`; `_over_note` names the rows that ran over their size.
- **The window** (`capacity_for`) of an UNSIZED batch (one recorded before row sizing, or on a block with no measure): `max(1, workers - 1)` — the block's `max_workers_per_node`, or the worker count a check or a result reported (`PARSL_WORKER_COUNT`); one worker stays free for interactive commands. A sized batch's capacity is its `fit` slots, and [[ledger]] `reserve` admits it against the block's measured pool. On a one-worker block a batch task holds it, and an interactive `run_shell` waits behind it, its answer naming the batch (`shared_worker_note`). The window is the BLOCK's, shared by every batch on it ([[ledger]] `reserve`: the demo of 2026-11-03 had two batches each fill their own window, and the excess queued at the interchange); while another batch on the block waits, a freed slot goes to the one with the fewest rows out. Only rows that can still hold a worker of the block in front count (`_on_block`: the caller passes its `block_job` and `HOLD_MARGIN_S` = `WRAPPER_TAIL_S` — the wrapper's own worst case past `task_walltime_s`, `WATCH_POLL_S` + 2 × `KILL_GRACE_S` + 2 × `READER_GRACE_S`, the constants the wrapper is built with; 14 s were measured where round 1 had assumed 7 — plus `DELIVERY_S`, independent of the configurable admission margin). The worker count a check or a result reports is the block's, on the ledger (`_learn_workers`). A batch refused slots by the others says which batches hold them (`_held_by_note` on `reserve`'s own `holders`, `_Run.held_by`; with nothing of its own out its phase is `waiting`, that the reason): rows in flight free as they settle (`status('<id>')`, `cancel('<id>', 'abort')`); a row of unknown fate is named as such, and no cancel frees it — on SSH a stop or reap that retires its config does, once its user endpoint has exited (`_unknown_evidence`); on a facility endpoint only its result arriving, the window smaller by it until then.
- **The admission gate** (`admit_ok`, `_admit_locked`, under `app.lock`): a row is sent only while the block's remaining walltime, read from INSIDE the block (the canary's `HPCB_REMAINING` and every result: [[session_shell]] `REMAINING_SH`), is at least `task_walltime_s` + `MARGIN_S` (30 s). Unknown admits nothing. Past it the batch pauses at `needs_confirmation`, naming the walltime.
- **The wrapper** (`task_script`, one per attempt), in the batch's OWN directory `<results_dir>/<batch id>/` (`batch_dir`; batches may share a `results_dir`): the wrong-block guard; the free-space floor (`MIN_FREE_MB`, rc 75) BEFORE the claim; the attempt claim `mkdir tasks/<i>/attempt-<n>` — only an existing attempt is a duplicate (S4), any other failure (EACCES, ENOSPC, EDQUOT) fails the row with the OS's own words; the batch's `CANCELLED` marker checked before and watched during the run; `meta.json` at start; the command in its own process group (`set -m`) under the session's cwd/env read-only, the row's values set after; stdout and stderr through FIFOs, each capped at `OUTPUT_CAP_BYTES` with a rolling tail of the stream's real end; a watcher that kills the group at `task_walltime_s` (rc 124) or on the marker (rc 143); when the command exits, what is left of its group (background children) is sent TERM, then KILL after `KILL_GRACE_S`; each stream's own `tee` (reading the command's FIFO, feeding the head's and the tail's) is then given `READER_GRACE_S` and killed, so a child outside the group (setsid) holding a stream ends the task with the tails of what arrived; the readers never hold the wrapper's own stdout (L6, round 2); the background jobs never hold the result's file descriptors; one `HPCB_RESULT {json}` line (`parse_result`).
- **The row's slot** (`Slot`, `task_script(slot=…)`, batch row sizing): after the attempt claim and the cancel check, the wrapper claims its CPUs and GPUs on the node (`_CLAIM`: one lock per device under `${TMPDIR:-/tmp}/hpcb-slots-<uid>-<job>-<token>/`, the token the block's — review round 2; an aligned slot — the next k CPUs of the measured order, SMT siblings adjacent — first, else any k free; `flock` where the node has it, its open files inherited by the command, so the claim ends with the row's last process; else a directory naming the wrapper's and the command's pids, taken over once both are gone); with none free within `CLAIM_WAIT_S` it runs nothing (`slot_busy`). Once the command runs the wrapper lets go of its own copies (`_CLAIMED`), so the watcher and the cleanup never hold the slot. The command's shell is pinned with `taskset -cp` (`_PIN`; `pin=False` skips it) and gets `_slot_env` AFTER the session's env: `HPCB_SLOT_CPUS`, `OMP/MKL/OPENBLAS/NUMEXPR_NUM_THREADS`, `PYTHON_CPU_COUNT`, `SLURM_CPUS_PER_TASK`, `SRUN_CPUS_PER_TASK` = cores, `SLURM_OVERLAP=1`, and on a GPU block its own GPUs only (`CUDA_VISIBLE_DEVICES` / `ROCR_VISIBLE_DEVICES` / `ZE_AFFINITY_MASK`; none for a CPU row). The watcher samples the command group's RSS (and threads, where `ps` tells) every second, keeps the peak, and kills the row past its memory (`why: memory`, rc 87). The result adds `cpus`, `gpu_ids`, `pinned`, `peak_rss_kb`, `cpu_s` (the command shell's `times`), `wall_s`, `nproc` (as the row saw it, its affinity), `threads` and the block cgroup's `oom_kills` delta.
- **The wrapper's exit codes** (ONE table, at `CANCEL_RC`): 75 too little space, 76 no free slot, 77 an unsafe slot lock directory, 86 the wrong-block guard, 87 a memory kill, 88 the row's env refused it ([[envs]] `ENV_RC`), 124 the row's own timeout, 143 cancelled; `why` is the primary signal.
- **The batch's env** (block environments, PR 3; [[envs]], [[Block environments]]). `run_batch(…, env=)` takes the batch's own env; without one, the batch takes the session's at creation.
  - **Choosing it:** `envs.parse`, then `delivery`, then `ensure_built`. A refusal is `_refused` and nothing is recorded. The env is recorded on the batch (`add_batch(env=)`) and shown in `BatchStatus.env`.
  - **Admission (`_admit_locked`):** while the env builds, the batch admits nothing and says so ("Not admitting now: …", `run.waiting`). A failed build pauses the batch.
  - **In the wrapper,** the activation (`task_script(env_sh=)`, a fresh nonce per send, `_Run.env_nonces`) sits after the session's env and before the slot's: a module's `OMP_NUM_THREADS` cannot widen a row.
  - **A refused row** runs nothing. The wrapper writes `.env_refused`, and the result carries `env_refused_b64` and `ran: false` (`TaskReport.env_refused`) — only when the mark carries THIS attempt's nonce (`task_script(env_nonce=)`; review N12: a row that writes the file itself ran). The nonce is `_env_nonce`: derived from the batch record's own secret (`nonce_key`), so a restarted server believes its own rows' marks and keeps no table of them. `_settle_result` sends the row back to the backlog (`_env_refused`).
    - **Every refusal** is first believed as run_shell's is (`envs.believe_refusal`: review R2-S2, one path), so a `.failed` mark makes the env failed here and the user's yes rebuilds it.
    - **A gone env** is rebuilt on the login node (`rebuild_record`) and the row is admitted again.
    - **A failed build** (its `.failed` mark, or a rebuild that failed) pauses the batch. The user's yes retries the build ONCE (`_resume`: `retried` on the record); a second failure is final (review S1). `retried` is cleared once the env is ready again (R2-S7).
    - **The rows** carry the arch the env was built for: `_admit_locked` re-reads the batch after updating its record (SS3).
    - **run_batch** promotes a ready pending env before it reads the session's (R2-S11).
    - **What no yes can mend** — another arch, a failing line, a directory not the user's alone, a redacted record after a restart — is `_env_unusable`: `unbuildable` on the record, and a pause whose status tells the agent the user must change the env, never asking for a yes. A resume of such a batch is refused by name.
  - **The env is fixed at the batch's start:** `run_batch(batch_id=…, env=…)` is refused by name (U7). The batch's own built env says what the session's would (`envs.built_notice`, S14), and its status gives the env's state as this server knows it (`envs.info_of_record`, S11).
- **Its own runner** (`_batch_runner`, `_runner_for_block`): a COPY of the compute shape's config (the same user endpoint, so the same block) on an Executor of its own, whose task group the service mints and whose results nobody else consumes (S1); rebuilt when the shape's config changes (a new confirmation's fresh `hpcb_block` is a new user endpoint — live, the batch kept sending to the reaped one's), the old one closed once nothing is out. The task group is on the record as soon as the service mints it.
- **One pass at a time** (`tick` under `_Run.passing`): the loop's and a status call's passes never interleave, and admission waits out a block switch (`switching`).
- **Settling** (`_collect`, `_settle_result`, `_settle_failure`): a result wins whenever it arrives; a guard refusal is the block's reap (the row goes back, the batch pauses, and the block that answered is named in `blocks_left`); a ManagerLost/WorkerLost failure is `lost` on evidence (a retry for `idempotent`); a client-side SDK failure on a sent task (its AMQP result watcher quit: "SDK thread quit unexpectedly.") is NOT a result — the row keeps its slot, the runner is rebuilt and the result is pulled by REST (`_client_side`, `_runner_broken`; L2: the freed slots had overfilled the workers); a submit with no task id is `submit_unknown` (`_reconcile`: EVERY task group the batch's runners were minted is read — `Ledger.task_groups`, L5; a stray task's result settles the row it names; while one is pending nothing is decided; then an idempotent row is sent again; a non-idempotent one never is, and is never called lost: the failed POST may have queued its task in a group of its own, which no runner learnt — round 2 withdrew round 1's `lost`-on-absence rule). Such a row HOLDS THE STOP (`unknown_since` set, `unheld` unset; `Ledger.unknown_holding`, `unknown_note`) — an idempotent one even after it is sent again, its first copy may be queued — until its copy's result comes back, or, on SSH, `_unknown_evidence`: `UNKNOWN_SETTLE_S` after the FAILURE, its config retired (a stop or a reap) and the user endpoint it targets (from the job's sacct SubmitLine) gone, with no pilot of it queued, in two looks a few seconds apart (a task left pending at the service does not restart a user endpoint; only a new submit with its config would, spike S5). On a MEP nothing clears it.
- **Evidence and presumption**: on SSH (`_evidence`) the jobs the ledger's rows in flight were sent to (this process's record, else the ledger's `sent_job`, else the last block seen — a dead server's rows too, L4) are looked up on the login shape; a job sacct (or PBS) says ended settles the tasks SENT TO IT `lost` on that evidence, marks the reap and pauses. For five minutes after (`_release_old_uep`, run by the background loop, which stays up for it: S5) the reaped block's user endpoint — read from its sacct SubmitLine — has its pilots cancelled by its own `uep.<eid>.<uep id>` marker: parsl starts one for the task that was out on the dead block, and no one confirmed it (live; recorded in `blocks_seen`) — unless the block the user confirmed after the reap has the SAME config, so the same user endpoint, whose pilot is then the user's block (S4). A new confirmation forgets what was known of the old block (`_sync_block`). `_presume`: a task IN FLIGHT with no result past `task_walltime_s` + `PRESUME_GRACE_S` since a block was seen is `presumed_lost` (keeps its slot, never retried, holds no stop): on a MEP every row out; on SSH a row no future of this process holds (a dead server's). Never a `submit_unknown`: absence is no evidence (round 2). The block evidence is this process's, else the ledger's `blocks_seen` (L4).
- **Restart** (`_adopt`, `_rest_pull`, `_reconcile_unsent`): a server finding a batch whose holder is gone takes the lease to COLLECT — by REST with the raw `v2.get_task_batch` (`collect_rest`; `Client.get_batch_result` drops failed tasks, S4) — pauses a batch that was admitting (spend lived in the old process), and starts the loop that keeps collecting. `run_batch(batch_id=…)` takes a batch over the same way: without `confirm_spend` it never resumes one (S7, rule 4). Before the lease is stale, a batch whose holder is gone (`Ledger.holder_alive`) reads `needs_confirmation`. A row the dead server queued without ever learning its task id is reconciled against the batch's task group: a task the ledger does not know settles the row its result names; with all accounted for, the row was never sent and goes back to the backlog.
- **The next block** (`_maybe_switch`, `_maybe_warm`): the user's yes at a walltime pause covers the NEXT block; once the tasks out on the block in front finish — and any submit of unknown fate is settled (L5) — on an endpoint hpc-bridge stood up (`fresh_ueps`) the shape is dropped and a fresh block confirmed; the block left runs out its last minutes, banked to its end and named in `blocks_left` (S8). Any pause, drain, abort or stop withdraws that yes (`pause`, `_apply_cancel`; S1: a drained batch had gone on to start a block). While a block is still starting the batch checks it as run_shell would. With the backlog empty the gate asks for nothing. On a facility MEP the next block can only start after the old one ends, and the batch asks again then.
- **Stop and cancel**: `pause_all` (called by [[server]]'s stops under `app.lock`, before anything is released), `retire_all` (the block's config, in the ledger), `in_flight_note` (the stop's busy refusal: every ledger batch's rows in flight on this endpoint, naming `cancel(id, 'abort')`), `unknown_note` (a batch's submits of unknown fate: the stop is `draining` naming them, never `down` — S3). `cancel` drains (keeps the backlog) or aborts: `write_cancel_marker` over the login shape, or on a MEP ONE small task, only to the batch's confirmed, live, not-ending block with a worker to spare (`_marker_block_why_not`; S2: a marker task could start a block nobody confirmed), never a second while one is out; the answer says when the marker was not written and that the tasks out then run to their end (S6). `blocks_left` (`_blocks_left`) names every block of ours that can still bill: the session's, `app.left_blocks` (a MEP stop's), the switch's, a block the facility started for a task of ours, and the reaped user endpoint while it is watched (S8). A tool call's pass is bounded: it waits for the loop's pass at most `LOCK_WAIT_S` (else `PassBusy`, and the answer is the ledger's view, saying a pass is running), never starts a next-block switch or a block check (the loop's, which `status`/`cancel` start if it is not running), and skips the lookups its budget (`CALL_BUDGET_S`) cannot cover; `cancel` runs under the progress heartbeat as `status` does (round 2: the lock wait had been unbounded).
- **`poll_uuid`, `record_interactive`**: `poll_task` by a Globus task id — a batch row, or an interactive task recorded when it went `running`; once REST cannot answer for an interactive one (no client, unreachable, no result), its rc and tail are read from the session dir over the login shape (`_session_result`; [[session_shell]] `wrap(result_key=…)` writes them).
- **`status(wait_s)`** (`_wait_for_change`, `_change_key`) waits the whole `wait_s` unless the phase changes (a pause, a drain, the batch's end) or a row needs the agent — it fails, is lost or presumed lost, or its submit's fate is unknown — or nothing more can happen (`_settled`: the batch admits nothing and nothing of it is out, as after a drain or an abort once its last rows settle). The baseline is the batch as the call found it, before the call's own first pass (review round 1: a batch that pass finished, or one already done, had slept the whole wait). A row that completes, or one admitted, is counted in the answer but never ends the wait (the demo of 2026-11-03: 20 rows had taken 21 status calls, one agent turn per row; before that, L8: not at the next pass). The call's budget (`CALL_BUDGET_S`) is unchanged.
- **`status()` with no id** (`listing`): the ledger's batches, Jobs-mode jobs and envelopes, active first then newest, a page of at most `LIST_MAX` (200), filtered by `facility` and `active_only` — [[models]] `LedgerEntry` (counts, an envelope's last meter reading, a command preview of `PREVIEW_CHARS`). A pure READ: no tick, admission, collection or lease, so listing never starts work. An active record that looks abandoned says why in `stale` and is never changed: a batch whose lease holder is gone (`holder_alive`, heartbeat past the lease) or whose block config was retired (`_batch_stale`); a job or envelope whose meter reading is over `STALE_READING_S` (1 h) old, or an envelope past its deadline. `status(id)` takes such a batch over as before.
- **The journal's event rows** (`_journal`): `batch.admit` (with `in_flight`, `capacity`, `remaining_s`, `need_s`), `batch.settle`, `batch.pause`, `batch.resume` — what the harness grades the window and the gate from.

> [!warning] A plain `status` never resumes spend
> It collects and keeps a RUNNING batch admitting, but a batch at `needs_confirmation` resumes only through `run_batch(batch_id=…, confirm_spend=True)`, the user's yes. A block that ends must never become a block parsl starts for a task left at the interchange (#204's pattern) — the gate and the window are what keep the interchange empty when the block goes.

> [!warning] Abort never touches the block
> In phase 1 the batch shares the session's block: `cancel(abort)` writes the marker and lets each wrapper kill its own command. It never SIGTERMs the user endpoint or cancels the block, which would end interactive work too.

  - the row is its process group ∪ its shell's descendant tree ∪ (Linux) every process of the user carrying its token (`HPCB_ROW_TOKEN`, read from `/proc/*/environ`), from one `ps -o pid,ppid,pgid,rss` snapshot (`__hb_members`); the same set is measured (`__hb_sample`) and killed (`__hb_kill`) — a child that left the group (coreutils `timeout`, setsid) had escaped the memory kill (W3); memory is each process's Pss on Linux (`/proc/<pid>/smaps_rollup`: a page shared copy-on-write by a forked pool counts once), its RSS elsewhere or where unreadable (W10); the thread count leaves out the command's own shell (W9);
  - the CANCELLED marker is checked in the claim loop and after a claim: a row that waited for its slot through an abort runs nothing (W4); the mkdir fallback's stale takeover re-reads the moved claim's pid and, if it is not the dead one, puts it back and takes the slot as busy (W5, best effort where `flock` is missing);
  - `cpu_s` is the wrapper's own `times` around its wait (an `exec` in the row, or its own EXIT trap, lost it — W11); the OOM delta has its own variable (W1); each attempt's real `pinned` is recorded and judges `over_size`, and status names rows that ran NOT pinned (W8);
  - a GPU kind not known gets every visibility variable for the slot (CUDA, ROCR, HIP, ZE, `GPU_DEVICE_ORDINAL`), ROCm both ROCR and HIP; a 0-GPU row is hidden only where an empty value is documented to hide every device (`GPU_HIDE_KINDS`: CUDA), elsewhere status says its visibility is not restricted (`gpu_note`, W7).
  - The server side: a derived block's workers are that block's alone — never the session's choice, and a change of them alone is another block (F1; "cleared by a block asked by size alone" was round 2's R2-H: now its own size restated is the same block, and any real switch clears them); on a whole-node partition the derived block IS the whole node, with the workers that fit, and a derived size the facility will not take is refused with its own words, never a spend question about another block (F2); `ACTIVE_STATES` / `PAUSABLE_STATES` carry `needs_sizing` (F3); a resize changes only what it names (`_merged`; memory, unnamed, is the default again), and pauses name `gpus=` for a GPU batch (F4); a pilot counts as run only rows out or settled, holds the block's GPUs as well as its CPUs (the user's size kept in `pilot_saved` and restored at the proposal), and a pilot whose rows cannot fit the block is refused or paused with the reason (F5); a kill at the default memory is judged by the attempt's own `req_mem_default` (F6); a resize is recorded before any spend question, a yes on a batch waiting for its size confirms the block and then asks for the size, and each answer names both when both are needed (F8). F7 is the [[ledger]]'s head-waiter reservation.
- **Review round 2 (8 defects at cbbcc1a; fixed test-first in `tests/test_batch_sizing_r2.py`).**
  - **A pause never overwrites `needs_sizing`** (R2-B): `pause` — a reap, a wrong-block refusal, a drain, a restart's adoption — leaves a batch whose size is owed at `needs_sizing` and records that the user's yes is owed too (`needs_yes`, its reason appended to the pause reason). The size owed is the LEDGER's (`size_owed`, set by `pause_sizing`, cleared only by a resize; or a pending proposal), never the state alone: `_resume` answers a yes alone with "still waits for its rows' size". A `pause_sizing` of a batch that already waited for a yes keeps that yes owed.
  - **A resize leaves `needs_sizing` at once** (R2-J), before `ensure_up`: to `needs_confirmation` (the yes owed, or the block did not answer as up) — a size that fits the confirmed block still resumes on its own.
  - **An adopted `needs_sizing` batch owes the yes** (R2-I): `_adopt` pauses it as it pauses an admitting one (`needs_yes`), so a resize alone never resumes it on a block this process confirmed for other work.
  - **The node lock directory** (R2-C, R2-D): `hpcb-slots-<uid>-<job>-<token>`, the token the block's (`Ledger.slot_token`: random, made when the block is first measured, kept per endpoint and config, returned with `block_measure`) — another user cannot guess the name to make it first; the ownership, mode and symlink checks stay. A directory that could not be made (nothing at the path: ENOSPC, EACCES, EROFS) is said as such ("could not be made (<mkdir's error>)"), apart from one that is not this user's private one. Either way the row ran nothing (`ran: false`): the server puts it back in the backlog and pauses the batch naming the path and the cause (`_lock_dir_refused`), as the busy-slot pause does — never failed.
  - **A pilot** (R2-A, R2-A2): a resize during it merges over the user's own size (`pilot_saved`), not the whole block's; its rows are not default memory (`reserve` marks no `req_mem_default` while `pilot_saved` is set); a pilot row killed at its memory — the whole block's — ends the pilot as a pilot ends (`_pilot_killed`: the user's size restored, `pilot_saved` cleared, `needs_sizing` with a proposal from that row; an idempotent row goes back to run at the size the user picks).
  - **A switch under batch rows** (R2-H, R2-E): the derived block's own size restated is that block (its workers kept: `_ensure_up_once` no longer drops them); any real switch — size, partition, account — clears `hpcb_workers` (`warmth._repoint`); and a real switch while batch rows are in flight is REFUSED naming them (`warmth._batch_rows_refusal` → `in_flight_note(then=…, paused=False)`), as `stop_endpoint` is — the task-handle guard never counted batch rows, and on SSH the old block idles out only after them: two blocks billing.
  - **The mkdir fallback** (R2-F): a claim names the wrapper's pid, then `"<wrapper> <command>"`; it is stale only when every pid it names is gone, and the release removes it only while its pid file still names this wrapper first.
  - **A killed row's CPU time is no evidence** (R2-G): `cpu_s` is null for a row killed at its memory, its timeout or an abort (its killed processes were reaped elsewhere, so `times` had lost them), and `sizing.pilot_proposal` takes no cores from a killed row whatever it reported: the proposal asks the user for cores (`_NO_CPU`).

> [!warning] A row's own `srun` escapes its slot
> `SLURM_OVERLAP=1` lets it share the pool's step (it no longer waits behind it) and `SRUN_CPUS_PER_TASK` sizes it, but slurmstepd places the step's tasks on CPUs Slurm picks, not on the row's slot — and they run under slurmstepd, outside the row's process tree, group and token, so the memory watch misses them too. A documented limitation pending a live check.
