# binding

> [!abstract] Role
> How a machine is REACHED: build the `Facility` for a catalog entry (`_facility_from_entry` → an SSH `SlurmFacility` with login name from `~/.ssh/config`, key, ControlMaster and login-node pin, or a `MEPFacility`), the runtime catalog (`make_catalog` → the public registry, read anonymously unless a Search-scoped login exists), the startup-pin path (`make_facility`, `_catalog_facility`), the no-facility default (`_default_local_facility`), the session/BYO helpers (`_entry_from_details`, `_session_endpoint_name`, `_facility_store`, `_resolve_scratch_root`).

Split step 5 (2026-09-03). **The patch-target rule:** every caller — in [[server]] and in this module — goes through the owning module's attribute (`binding.make_catalog()`, `binding._facility_from_entry(…)`, `config._control_settings()`), and tests patch `binding.<name>` / `config._control_settings`, never `server.<name>`. Re-exports from `server` remain for imports only. This is the trap the code-quality review warned about: a name re-exported from `server` but patched there does not reach a caller that resolved it elsewhere.

**The env presets apply to one facility.** `HPC_BRIDGE_ACCOUNT` and `HPC_BRIDGE_PARTITION` belong to the facility `HPC_BRIDGE_MACHINE` names: by id or subject (`config.names_machine`), or by an alias the startup pin resolved (`_catalog_facility` records it in `_PINNED`; `_names_machine`). `_facility_from_entry` applies the partition preset only to the entry named (the startup pin's included, since `_catalog_facility` records its resolution first), never over a bring-your-own entry's own partition (`facility_key == SESSION_KEY`). The account is its caller's choice: `_catalog_facility`'s `_require_env("HPC_BRIDGE_ACCOUNT")` is unchanged, and [[connect]] passes the preset only for the named machine. A facility MEP never took the partition preset (its defaults are the entry's). `_partition_preset(entry)` is that rule in one place, and `_terms_origin(entry, discovered=…)` (`binding.py:114`) records where the default terms come from for BlockTerms' sources ([[models]]): `registry`, `env` (the partition preset applied), or for a bring-your-own entry `byo_details` / `discovered`; the entry's `account_required` as the registry's claim (None for your own) and its `account_hint`. The startup pin keeps its origin in `_PINNED_ORIGIN` (only a pin that succeeded) for `server.lifespan`. `_entry_from_details` refuses a `scheduler_options` that sets the account or the partition/queue (`catalog.entry.scheduler_terms_directive`: `#SBATCH -A/--account/-p/--partition` by any prefix sbatch accepts and in a bundle of short flags, `#PBS -A/-q`) with a `TermsDirectiveError`: sent verbatim, it would charge what the block's terms never show. [[connect]] reports a cached config refused for it as such, not as "isn't in the catalog". A bring-your-own entry (`_entry_from_details`) carries `account_required=False`: nothing curated says its scheduler enforces accounting, so the account floor stays off there, as before; a registry SSH entry's flag reaches its `SlurmFacility` ([[facility-remote]]).

**The no-facility default.** With no `HPC_BRIDGE_MACHINE`, `make_facility` (`:165`) returns `_default_local_facility()` (`:154`), and `lifespan` uses the same builder, with `unbound=True`, when a pin fails at boot. It is a [[facility-local|`LocalFacility`]] marked `implicit` (nothing chose it) unless `HPC_BRIDGE_ENDPOINT_ID` is set — the only local-dev path, an endpoint the user runs ([[Configuration]]) — and always after a failed pin. [[server]] then refuses every call that would stand up or use an endpoint with "No facility connected" (`context._no_facility_bound`), so the agent connects a facility instead of getting a local endpoint on the MCP host.
