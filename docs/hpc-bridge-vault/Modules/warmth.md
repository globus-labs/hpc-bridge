# warmth

> [!abstract] Role
> The per-shape warmth state machine — Executor build/reuse (`_runner_for`), the canary that proves a worker is live (`_confirm_worker`: TTL, live-task shortcut, non-timeout failures → `runner_stale`, the sticky NO ACCOUNT verdict, the transient-conflict count), the spend floor and partition/account application (`_provision`, `_apply_partition`, `_apply_account`; `_provision` also has an SSH facility adopt the endpoint's own configured worker_init, `adopt_endpoint` in [[facility-remote]], before the canary, so every task runs the venv its manager was started with), and dropping shapes (`_drop_compute_shape`, `_drop_all_shapes`, `_forget_identity_verdicts`). Task-handle bookkeeping lives here too (`_register_task`, which records the scheduler job a command submits by hand, `TaskHandle.submission`; `_resolve_task`, whose finished result carries the [[notices]] submission note; `_busy_session`, `_live_task_handles`, `_drain_shape_tasks`, `_endpoint_gone`) because a live task IS a warmth signal the runner rebuild and the canary consult.

`_note_dispatch` (`warmth.py:316`) reads each dispatch's outcome as a liveness signal: a result or a still-running task refreshes the block's confirmation, a failure voids it (forcing a re-canary; `_void_warm` keeps it as the block's last proof of life, `last_proof_at`, for the idle presumption and the billing bound) — except a result too big to come back, which the worker produced by running the command ([[dispatch]]).

**A switch is a different block.** `_apply_partition` / `_apply_account` (`warmth.py:655`, `:683`) hand a real change to `_repoint` (`:705`). It first takes in a finished command the wrong-block guard refused and nobody polled (`_settle_refusals`: the kicked reap its poll would have made, so the replacement is the block the switch leaves; its poll still says the command did not run; a reap found there is left untold, so the switching call answers needs_confirmation with it even with `confirm_spend=True`), then runs `_check_reaped`. `_leave_block` settles the same way, so a facility stop, detach or reconnect names the replacement too. Since the shape's spend was confirmed for the old terms' block only, it drops `spend_confirmed` and keeps those terms (`ShapeRuntime.switched_terms`) for the re-ask (`notices._reask_prefix`). Nothing cancels the old block on a switch. Whatever block of ours `_resolve_left` finds is billed once to the latest it can bill: on an SSH endpoint `_leave_block(remember=False)` (it idle-releases on its own, min_blocks=0, and `stop_endpoint` cancels every block of the endpoint by its `uep.<eid>` marker), on a facility endpoint `_leave_switched`, which leaves it in `left_blocks`; the re-ask names it from `switch_left` while a stop still would (`notices._still_left`). After a reap, a switch keeps the terms the reap was on (`ShapeRuntime.reap_terms`), and the re-ask says the terms were switched while they differ from those (on both channels): back on them, the block the reap found is the one a confirmation takes. A switch forgets the presumed block (`_forget_presumed`). Blocks are dated by their scheduler job: `AppCtx.job_seen_since` keeps when each job on the endpoint was first proven up (a check's answer, a late answer, a refused command dated by its handle's end; `_saw_job`, bounded without ever dropping a shape's confirmed or presumed job, kept for the endpoint a reconnect binds again and dropped by a bind elsewhere, as `billed_to` is), and `_answering_block_since` takes the earliest proof of the job that answers, so a job met again after a switch back, a stop or a reconnect keeps its real age on any number of hops, whatever its terms. A job that answers more than `_REQUEUE_GRACE_S` (30 s: Slurm's KillWait / OverTimeLimit, PBS's kill grace) past its walltime counted from that proof was requeued under its id (a preemption, a node failure, a PBS rerun): its proof moves to that answer and it runs a fresh walltime. `_provision` dates a block by its answer (`CanaryResult.answered_at`), not the call's clock: a cached answer may be up to the runner's freshness window old. A job at its hard end is never taken for a fresh one; a real requeue answering inside the grace is recognised one confirmation later at worst (one more question). It bills afresh from that confirmation: back-and-forth switching can count some time twice (an upper bound), never less than ran. The re-ask on the confirmed terms says they are back. `switch_unseen` records a block asked for but never seen up (no identity, no confirmation), so `server._stop_endpoint` still polls for its pilot (`expect_block`); a block seen up whose confirmation was only voided is not one. The switching call answers `needs_confirmation` unless it carries `confirm_spend=True` itself; when it does, its answer carries the old block's fate once (`notices._switch_receipt`). A confirmation in `_provision` clears the switch fields. A switch bumps `ShapeRuntime.block_epoch`: a handle records the epoch it was sent in (`TaskHandle.epoch`), and `_resolve_task` takes a task as proof of life only for its own epoch, so a task that finished on the old block, polled later, never marks the new one warm. (`_last_activity` needs no such filter: the old task ended before the switch, and every stamp of the new block is later.) The new value is recorded in `AppCtx.compute_choice`, and `_shape_runtime` (`:80`) seeds every new compute runtime (not the login shape) with it: a stop (`_drop_compute_shape_locked`) keeps the session's partition and account, `_drop_all_shapes` (a connect_facility, a teardown or a detach) forgets them, and a new Globus login (`_forget_identity_verdicts`) keeps them, as it keeps a live shape's. The account floor in `_provision` reads the account the block would be charged to (the session's choice, or the facility's configured default seeded into the config) on every channel: an SSH facility carries `account_required` too ([[facility-remote]]).

**The wrong-block guard** (`warmth.py:427`–`:497`; the shell side is [[session_shell]]). `_guard_job` (`:434`) is the job a command sent now must run in: a billed shape, one block at most, spend confirmed, `block_job` known, else None. `_new_guard` (`:441`) wraps it with a fresh nonce for one dispatch. `_guard_refusal` (`:446`) reads a complete result as a refusal (`session_shell.refusal`). `_wrong_block_outcome` (`:452`) turns one into the kicked reap `_confirm_worker` makes for a different job, while the block it was sent for is still the confirmed one: `_mark_reaped(..., kicked=True)` banks it to `_release_bound`, the outcome is `needs_confirmation` with the "did NOT run" notice, and `last_canary` is set to name the replacement's job, so a confirm that skips its canary dates the block by it. Otherwise it marks nothing: after a release under the call it says so, and after spend was confirmed again it says to send the command again. `_register_task` keeps the guard on the handle (`TaskHandle.guard`), so `_resolve_task` (`:1023`) finds a refusal however late it is polled, a client-cancelled call's command included. [[Cost control]] has the whole flow.

**No bootstrap on a dead login.** `_provision` bootstraps when no endpoint is bound — reached without connect's gate by a startup pin (`HPC_BRIDGE_MACHINE`) or a call after a teardown — and the bootstrap may copy the stored login to the login node. So it first asks [[login]] `check_stored_login(force_refresh=True)` (forced: a refresh token revoked while its access token is still valid is caught too) and raises `LoginExpiredError` on `expired`, before any SSH: `ensure_endpoint_up` answers `down`, `run_shell` `failed` (via `_error_outcome`), connect's bootstrap `failed` (via `_explain_provision_error`), each with [[notices]] `_hpc_bridge_error`'s dead-login text. `unchecked` carries on.

Split steps 7–8 (2026-09-03; the review planned `warmth` and `tasks` separately — their coupling made one module the honest cut). Every function runs under `app.lock`, held by the caller in [[server]]. One exception: a cancelled call registers its still-running command (`_register_task(..., client_cancelled=True)`) in a single synchronous step without the lock, because a cancelled call must not wait for it, and code with no await cannot interleave with any other call. A live handle of that kind is like any other: the canary short-circuits on it, `_presumed_reaped` will not presume the block gone, `_busy_session` refuses its session, and partition/account switches are refused. A handle pending past its ceiling (`_past_ceiling`) still counts as live, because it may only be queued. `_overdue` (past its ceiling plus `_LOST_TASK_GRACE_S`) is consulted only by a facility MEP's stop and detach (`server._block_work`). `_runner_for` defers a credential-only swap while a call is in its sync-wait, as it does for a live handle. `_drop_compute_shape_locked` is the drop for a stop that must look and drop in one locked step. On a facility MEP (no cancel channel, [#178](https://github.com/globus-labs/hpc-bridge/issues/178)), `_leave_block` runs before a stop, detach, reconnect or partition/account switch lets the block go: `_resolve_left` names it (the confirmed `block_job`, else a check-found replacement, else a check that answered after its wait — the runner's `canary_answer` — else the presumed block, else a queued check — `_check_queued`) with its latest end (the walltime's end while `_work_on_block`), the block is banked to that end from where its clock stood — its tail only past the job's high-water mark (`AppCtx.billed_to`), so no tail is counted twice — and it is remembered in `AppCtx.left_blocks` — only to be named again, never billed or used to date a block. A switch (`_leave_switched`) also closes the old runner and clears the last check and a reap's kick. `_take_left` (in `_provision`, when a block is first confirmed) only removes entries it supersedes (the same job, or with one block the same partition and account); the block bills from its own confirmation. `_prune_left` drops blocks past their walltime's end, never a queued check. `_known_block_job` names only a confirmed block of the same partition and account, not presumed gone, for the five-minute allocating notice (with a cancel only for this shape's own `block_job`); `_confirm_worker` keeps the canary's mapped account as `AppCtx.worker_user`. `_resolve_task` notes a result only on the runtime the task ran on, and only if that runtime is still current: it never rebuilds a dropped shape. Tests patch `warmth._provision` / `warmth._drop_compute_shape`; `server` calls those through the module.
