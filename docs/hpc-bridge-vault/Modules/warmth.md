# warmth

> [!abstract] Role
> The per-shape warmth state machine — Executor build/reuse (`_runner_for`), the canary that proves a worker is live (`_confirm_worker`: TTL, live-task shortcut, non-timeout failures → `runner_stale`, the sticky NO ACCOUNT verdict, the transient-conflict count), the spend floor and partition/account application (`_provision`, `_apply_partition`, `_apply_account`; `_provision` also has an SSH facility adopt the endpoint's own configured worker_init, `adopt_endpoint` in [[facility-remote]], before the canary, so every task runs the venv its manager was started with), and dropping shapes (`_drop_compute_shape`, `_drop_all_shapes`, `_forget_identity_verdicts`). Task-handle bookkeeping lives here too (`_register_task`, which records the scheduler job a command submits by hand, `TaskHandle.submission`; `_resolve_task`, whose finished result carries the [[notices]] submission note; `_busy_session`, `_live_task_handles`, `_drain_shape_tasks`, `_endpoint_gone`) because a live task IS a warmth signal the runner rebuild and the canary consult.

`_note_dispatch` (`warmth.py:347`) reads each dispatch's outcome as a liveness signal: a result or a still-running task refreshes the block's confirmation, a failure voids it (forcing a re-canary; `_void_warm` keeps it as the block's last proof of life, `last_proof_at`, for the idle presumption and the billing bound) — except a result too big to come back, which the worker produced by running the command ([[dispatch]]).

**A switch is a different block.** `_apply_partition` / `_apply_account` (`warmth.py:1373`, `:1402`) hand a real change to `_repoint` (`:1429`). It first takes in a finished command the wrong-block guard refused and nobody polled (`_settle_refusals`: the kicked reap its poll would have made, so the replacement is the block the switch leaves; its poll still says the command did not run; a reap found there is left untold, so the switching call answers needs_confirmation with it even with `confirm_spend=True`), then runs `_check_reaped`. `_leave_block` settles the same way, so a facility stop, detach or reconnect names the replacement too. Since the shape's spend was confirmed for the old terms' block only, it drops `spend_confirmed` and keeps those terms (`ShapeRuntime.switched_terms`) for the re-ask (`notices._reask_prefix`). Nothing cancels the old block on a switch. Whatever block of ours `_resolve_left` finds is billed once to the latest it can bill: on an SSH endpoint `_leave_block(remember=False)` (a block that came up idle-releases on its own, min_blocks=0, and `stop_endpoint` cancels every block of the endpoint by its `uep.<eid>` marker), on a facility endpoint `_leave_switched`, which leaves it in `left_blocks`; the re-ask names it from `switch_left` while a stop still would (`notices._still_left`). A block that never came up is its pilot, and a HELD pilot never idle-releases (2026-10-16 `polaris_filesystems`: the switch said "idle-releases ~600s after its last task" of one): a confirmed switch records whether the old block came up (`ShapeRuntime.switch_left_up`, `_came_up`: a worker answered on it and no reap since) and the pilots the last probe saw (`switch_left_pilots`, from `ShapeRuntime.pilots`, which `_record_pilots` sets from each provisioning probe on the runtime and epoch it was for, and the switch clears), so the re-ask and the receipt say what is true of it (`notices._ssh_block_fate`: it idle-releases; its pilot was queued and may still start — a limit it waits on may clear; or it was held, or refused as submitted — it stays queued until cancelled, and `stop_endpoint` cancels that one too). A confirmation clears them. The record holds (job, state, reason, word) per pilot — the word is the state as the scheduler listed it, which the notes name it by ([[context]] `SeenPilots`); the block's own pilot leaves it when a worker first answers on it (`_provision`, by the probe's subject and the answering job) and again when the block is found gone (`_mark_reaped`), so a re-bind never names a dead job as still queued (review round 2, P3). `_ssh_left` reads the same record for a re-bind ([[connect]]), which keeps it in `AppCtx.ssh_left` for a later re-bind of that endpoint; a confirmation there drops it. A confirmation also stamps `ShapeRuntime.confirmed_wall` beside `confirmed_at`: the probe's age of it is the larger of the two clocks', since the monotonic one stops while the machine sleeps ([[scheduler_ops]]). After a reap, a switch keeps the terms the reap was on (`ShapeRuntime.reap_terms`), and the re-ask says the terms were switched while they differ from those (on both channels): back on them, the block the reap found is the one a confirmation takes. A switch forgets the presumed block (`_forget_presumed`). Blocks are dated by their scheduler job: `AppCtx.job_seen_since` keeps when each job on the endpoint was first proven up (a check's answer, a late answer, a refused command dated by its handle's end; `_saw_job`, bounded without ever dropping a shape's confirmed or presumed job, kept for the endpoint a reconnect binds again and dropped by a bind elsewhere, as `billed_to` is), and `_answering_block_since` takes the earliest proof of the job that answers, so a job met again after a switch back, a stop or a reconnect keeps its real age on any number of hops, whatever its terms. A job that answers more than `_REQUEUE_GRACE_S` (30 s: Slurm's KillWait / OverTimeLimit, PBS's kill grace) past its walltime counted from that proof was requeued under its id (a preemption, a node failure, a PBS rerun): its proof moves to that answer and it runs a fresh walltime. `_provision` dates a block by its answer (`CanaryResult.answered_at`), not the call's clock: a cached answer may be up to the runner's freshness window old. A job at its hard end is never taken for a fresh one; a real requeue answering inside the grace is recognised one confirmation later at worst (one more question). It bills afresh from that confirmation: back-and-forth switching can count some time twice (an upper bound), never less than ran. The re-ask on the confirmed terms says they are back. On an SSH endpoint `_repoint` (`:1429`) retires the old runner before the terms change (`_retire_runner`): a check of the old terms still queued — its block asked for and never seen up, or after a reap a check found (`reap_kicked`) — may have asked their user endpoint for a block that can still land, so the endpoint keeps that check in `AppCtx.sent_checks`, with the old terms and the pilot that died there, and a stop still sees, cancels and names it whatever a confirmation or a rejection on the new terms does; a block seen up answered every check, so nothing is kept for it. The switching call answers `needs_confirmation` unless it carries `confirm_spend=True` itself; when it does, its answer carries the old block's fate once (`notices._switch_receipt`). A confirmation in `_provision` clears the switch fields. A switch bumps `ShapeRuntime.block_epoch`: a handle records the epoch it was sent in (`TaskHandle.epoch`), and `_resolve_task` takes a task as proof of life only for its own epoch, so a task that finished on the old block, polled later, never marks the new one warm. (`_last_activity` needs no such filter: the old task ended before the switch, and every stamp of the new block is later.) The new value is recorded in `AppCtx.compute_choice` — so is a value a call names again unchanged (`_apply_partition` / `_apply_account`: no switch, but the session's choice now, BlockTerms' `this_call` / `earlier_call`) — and `_shape_runtime` (`:118`) seeds every new compute runtime (not the login shape) with it through `_seed_uec` (`:98`), which [[connect]] also reads to state the next block's terms without building one: a stop (`_drop_compute_shape_locked`) keeps the session's partition and account, `_drop_all_shapes` (a connect_facility, a teardown or a detach) forgets them, and a new Globus login (`_forget_identity_verdicts`) keeps them, as it keeps a live shape's. The account floor in `_provision` reads the account the block would be charged to (the session's choice, or the facility's configured default seeded into the config) on every channel: an SSH facility carries `account_required` too ([[facility-remote]]).

**The wrong-block guard** (`warmth.py:444`–`:524`; the shell side is [[session_shell]]). `_guard_job` (`:465`) is the job a command sent now must run in: a billed shape, one block at most, spend confirmed, `block_job` known, else None. `_new_guard` (`:472`) wraps it with a fresh nonce for one dispatch. `_guard_refusal` (`:477`) reads a complete result as a refusal (`session_shell.refusal`). `_wrong_block_outcome` (`:483`) turns one into the kicked reap `_confirm_worker` makes for a different job, while the block it was sent for is still the confirmed one: `_mark_reaped(..., kicked=True)` banks it to `_release_bound`, the outcome is `needs_confirmation` with the "did NOT run" notice, and `last_canary` is set to name the replacement's job, so a confirm that skips its canary dates the block by it. Otherwise it marks nothing: after a release under the call it says so, and after spend was confirmed again it says to send the command again. A refusal polled after a partition/account switch (`TaskHandle.epoch` ≠ the runtime's `block_epoch`) names the terms as the new block's, not the replacement's it reached. `_register_task` keeps the guard on the handle (`TaskHandle.guard`), so `_resolve_task` (`:1751`) finds a refusal however late it is polled, a client-cancelled call's command included. [[Cost control]] has the whole flow.

**A submission the scheduler rejected, and a pilot that died** (live 2026-10-15, `submit_policy_rejected` / `slurm_worker_died`). When this call's check failed because the scheduler REJECTED the block's submission on a shape whose spend was confirmed — whatever its block count: the rejection reaches our check only through parsl's block-error handler, which needs every block that user endpoint ever had to be FAILED, so `_terminal_failure` reads it as terminal too (`_rejected_now`, `warmth.py:719`), `_provision` — after it stopped the clock as a terminal verdict — calls `_void_rejected` (`:726`): the confirmation covered a block that was never created, so it is dropped as a reap or a switch drops it, with the cause and terms kept in `ShapeRuntime.rejected` for the re-ask ([[notices]] `_reask_prefix`) and the stop's `down` — the cause refers back to the submit command's answer the check carried ([[runner]] `CanaryResult.submit`, in brief by `_submit_rejection_cause`), else parsl's line; a refusal the provisioning probe only reads in the block's own user endpoint log voids nothing ([[server]]) — until the next confirmation (which also stamps `confirmed_at`, so the probe can leave out a pilot an earlier session left in the scheduler's history); a block confirmed before it loses its identity too (with one block the endpoint submits only once it has gone), so the block a new confirmation starts is not taken for an unasked replacement. parsl's block-error handler failed every task of that user endpoint, our check among them, and a bad-state executor is never scaled out again — which is why a stop finds that check resolved and expects no block from it ([[server]] `_stop_endpoint`). A pilot that ran and died is recorded by the server from the provisioning probe (`_note_dead_pilot`, `:770`, via `_record_dead_pilot`, `:777`: `ShapeRuntime.dead_pilot`, a [[context]] `DeadPilot`) — to NAME it: what a stop answers comes from the check that pilot was started for, and a retired runner's checks carry it (`SentCheck.dead`). `_check_resolved` (`:765`) forgets it when a worker answers a check or a submission is rejected; a fresh `confirm_spend` does not. `_record_dead_pilot` records the probe's verdict while the shape and its `block_epoch` are the ones the probe — run off the lock — was for (a block that kept its identity after a check failed with an error included), unless a worker answered DURING the probe (`warm_confirmed_at` past the value read before it); after a switch or a drop meanwhile nothing is recorded: the old terms' check is already the endpoint's.

**A fresh compute user endpoint per block request** (`_fresh_block`, `:1347`; live 2026-10-16, `queued_check_relaunch`). The web service keys a user endpoint on its config, so a confirmation that asks for a NEW block puts a new `hpcb_block` number (`secrets.randbelow(2**48 - 1) + 1`: a whole number, which the template renders `| int` into the user endpoint's `endpoint_setup`, so its own log names it from its start — [[facility-remote]]) in the compute shape's config and rebuilds the runner (`runner_stale`): that block's pilot is its user endpoint's FIRST. parsl reads a first pilot a stop cancelled, or one that died before it connected, as MISSING at its next status poll; with no block of that user endpoint ever up, its block-error handler (threshold `max(1, init_blocks)`) sets bad state and fails every task it holds, our check among them — where a LATER pilot of a user endpoint that already had a block is replaced instead, for as long as the check waits. "A new block" is the confirmation `_provision` takes (`new_request`) after a stop, a reap, a rejection or a switch, or the first one; not a confirmation over a replacement already answering on these terms (`kicked_up`: a kick met before a switch, `reap_terms` other than the current ones, does not count), nor one while a block of ours is up or our work is on it (`block_since`, `inflight`, a live handle) — that block is not abandoned. The login shape never changes. Only where it is safe and ours: an SSH endpoint whose template lets an idle compute user endpoint exit ([[facility-remote]] `fresh_ueps`: read from the published template, or set by the `provision` that wrote it), on a billed shape; a facility's endpoint never gets one. Each compute user endpoint exits ten idle minutes after its last task (`idle_heartbeats_soft`, [[profile]] `uep_idle_heartbeats`), so they do not pile up on the login node; the manager starts one again for the next task like any first one.

**Our tasks, kept per endpoint (#24's evidence).** `_retire_runner` (`:811`) closes a shape's runner at every close site (`_runner_for`'s rebuild, `_drop_all_shapes`, `_drop_compute_shape_locked`, `_leave_switched`, `_repoint`) and first, for a billed shape on an SSH endpoint, hands the checks it sent that may still be queued ([[runner]] `sent_checks`) to `AppCtx.sent_checks[eid]` as [[context]] `SentCheck`s (`_keep_checks`), with the terms they asked for (`_runner_terms`), the dead pilot to name, when each one's task id was first seen (`_taken_at`: the runner's `taken_at`) and the block request each was sent for (`_sent_block`: the runner's `sent_block`, read at the send — the shape's config may be the same dict and gets a new request's number after it; `_block_number` ([[facility-remote]] `block_number`, the one rule the probe and the evidence use too) takes only a whole number in range, so an earlier plugin's hex token, or an odd value on disk, names nothing) — `Executor.shutdown` cancels only tasks never handed to the web service. A command whose future failed on the client's side alone (not `TaskExecutionFailed`: e.g. "SDK thread quit unexpectedly.", which fails every open future while the tasks live on) is kept the same way (`_keep_lost_command`, from `_resolve_task` and the dispatch): its handle is gone, the task may not be. Past `_SENT_CHECKS_MAX` (64) per endpoint only what is KNOWN resolved goes (`_locally_resolved`: answered, failed by the service, never sent), oldest first — an unresolved one is never dropped. Each change, and each check sent (`_note_checks_sent`, after every canary), is written to disk by task id with its block request and when its id was first seen (`_persist_checks`, [[state]] `SentCheckStore`; `_our_checks` reads `block` and `taken_at` back) — the kept tasks AND the current compute runner's, always; the store MERGES (it removes only the tasks this process saw resolve: those it wrote that are no longer unresolved here, and those its lookups resolved, `AppCtx.resolved_checks`), so two sessions on one endpoint keep each other's rows; every read and write runs on a thread of its own (`_STORE_POOL`, a `_RecordThread`: one daemon thread, so a write hung at exit never keeps the interpreter alive), each write in the directory decided when it was queued (`_RecordJob.root`, never re-read in the thread), off the event loop (`_schedule_flush` / `_flush_checks`: one flusher per endpoint, the latest state first, its removals computed when it writes, and what it writes counted as written from then — a failed write puts back what was there; `_read_checks`, bounded; `_flush_all` at teardown, at shutdown and before a stop reads). A check is on it from its SUBMIT ([[runner]] `on_sent`, set by `_confirm_worker`, and again in a `finally` around the wait), a command while it runs (`_note_command_sent` / `_note_command_done`, `AppCtx.commands_sent`); one with no task id yet is written under a key of its own (`no_id`, read back as `unknown`, dropped after `_NO_ID_BOUND_S` on a fresh-user-endpoint endpoint) until `_watch_ids` writes its id; a row this process wrote and no longer holds is never adopted back; so a home directory that hangs cannot freeze the server; a write that fails is said on stderr and tried again on the next change — so a restarted server's `_our_checks` reads them back, with why the record cannot be trusted when it cannot be read (the stop then fails closed) (no future, no client: looked up with any runner's client of the binding) — `_our_checks` is what a stop must see resolve: those, plus the current compute runner's. `_check_states` reads them: first each future (`_local_state`: answered → `ok`; failed with `TaskExecutionFailed` → `failed`, the service's own verdict; certainly never sent → `unsent`; a submit that failed with no task id, where the service may have taken it → `unknown` for `_NO_ID_BOUND_S`, 300 s — the user endpoint's start, parsl's 60 s poll and 5 s pass after a cancel, the failure reaching the service, with margin — then dropped with a line on stderr — only where `drop_no_id`, an endpoint with a compute user endpoint per block request; on one of an earlier plugin it stays `unknown`), then a resolution seen before (`AppCtx.resolved_checks`, never asked again), then the rest by task id, batched per client (`_lookup_into`: `get_batch_result`, then `get_task` for a task the batch drops, at most `_MAX_SINGLE_LOOKUPS`, 32, per round, none past the round's deadline), each answer KEPT as it is read — one read after the round stopped waiting goes to the cache — within `_LOOKUP_TIMEOUT_S` (20 s). SDK 4.18's `get_task` RAISES `TaskExecutionFailed` for a task the endpoint failed with an exception (bad state, a REJECTED submission, a dead first pilot): `failed` (`_task_state`). `lost` (`CheckState`) is set only by a stop ([[server]] `_settle_by_evidence`): the service still says pending, but the check's own user endpoint received it, failed it with bad state and stopped for good; `_settle_checks` counts it resolved, as `ok`, `failed` and `unsent`, so it leaves the endpoint's record (`AppCtx.resolved_checks`). `pending` while the service says so; `success` (with a result or none) is `ok`, any other finished status `failed`; a `SerdeError` arises only for a finished task's result this process cannot read: `ok`; anything else (transport, auth, an unexpected answer) `unknown`, read as still queued. `_settle_checks` keeps only the pending and unknown ones after a stop looked (on disk too); `_forget_checks` drops the endpoint's with its teardown; `_unresolved_count` counts them for [[connect]]'s note on a bind elsewhere.

**No bootstrap of a dropped config** (2026-10-20). A failed connect leaves its facility bound; when [[connect]] dropped that config (`_drop_failed_details`), it marks the facility object (`AppCtx.dropped_binding`), and `_provision` raises `DroppedConfigError` first — before any spend or state change — while no endpoint is up: `ensure_endpoint_up` answers `down`, `run_shell` `failed`, with the failure and the two routes ([[notices]] `_hpc_bridge_error` shows it as it is). The next bind ends it.

**No bootstrap on a dead login.** `_provision` bootstraps when no endpoint is bound — reached without connect's gate by a startup pin (`HPC_BRIDGE_MACHINE`) or a call after a teardown — and the bootstrap may copy the stored login to the login node. So it first asks [[login]] `check_stored_login(force_refresh=True)` (forced: a refresh token revoked while its access token is still valid is caught too) and raises `LoginExpiredError` on `expired`, before any SSH: `ensure_endpoint_up` answers `down`, `run_shell` `failed` (via `_error_outcome`), connect's bootstrap `failed` (via `_explain_provision_error`), each with [[notices]] `_hpc_bridge_error`'s dead-login text. `unchecked` carries on.

Split steps 7–8 (2026-09-03; the review planned `warmth` and `tasks` separately — their coupling made one module the honest cut). Every function runs under `app.lock`, held by the caller in [[server]]. One exception: a cancelled call registers its still-running command (`_register_task(..., client_cancelled=True)`) in a single synchronous step without the lock, because a cancelled call must not wait for it, and code with no await cannot interleave with any other call. A live handle of that kind is like any other: the canary short-circuits on it, `_presumed_reaped` will not presume the block gone, `_busy_session` refuses its session, and partition/account switches are refused. A handle pending past its ceiling (`_past_ceiling`) still counts as live, because it may only be queued. `_overdue` (past its ceiling plus `_LOST_TASK_GRACE_S`) is consulted only by a facility MEP's stop and detach (`server._block_work`). `_runner_for` defers a credential-only swap while a call is in its sync-wait, as it does for a live handle. `_drop_compute_shape_locked` is the drop for a stop that must look and drop in one locked step. On a facility MEP (no cancel channel, [#178](https://github.com/globus-labs/hpc-bridge/issues/178)), `_leave_block` runs before a stop, detach, reconnect or partition/account switch lets the block go: `_resolve_left` names it (the confirmed `block_job`, else a check-found replacement, else a check that answered after its wait — the runner's `canary_answer` — else the presumed block, else a queued check — `_check_queued`) with its latest end (the walltime's end while `_work_on_block`), the block is banked to that end from where its clock stood — its tail only past the job's high-water mark (`AppCtx.billed_to`), so no tail is counted twice — and it is remembered in `AppCtx.left_blocks` — only to be named again, never billed or used to date a block. A switch (`_leave_switched`) also closes the old runner and clears the last check and a reap's kick. `_take_left` (in `_provision`, when a block is first confirmed) only removes entries it supersedes (the same job, or with one block the same partition and account); the block bills from its own confirmation. `_prune_left` drops blocks past their walltime's end, never a queued check. `_known_block_job` names only a confirmed block of the same partition and account, not presumed gone, for the five-minute allocating notice (with a cancel only for this shape's own `block_job`); `_confirm_worker` keeps the canary's mapped account as `AppCtx.worker_user`. `_resolve_task` notes a result only on the runtime the task ran on, and only if that runtime is still current: it never rebuilds a dropped shape. Tests patch `warmth._provision` / `warmth._drop_compute_shape`; `server` calls those through the module. The concepts: [[Warmth, the canary & cold-start]], [[Resource shapes & the spend floor]], [[Cost control]].

**A block's size is a term too (2026-10-24, [[Resource requests]]).** `_apply_resources` (`warmth.py:1531`) is the
analogue of `_apply_partition` for resources.requested's updates (cores, memory, GPUs, nodes, whole node; None clears a
key): refused while a task or a sync-wait command holds the shape, a real change handed to `_repoint` (`:1576`, which now
takes several keys at once and writes None as a pop, in the runtime config and in `AppCtx.compute_choice`), and
`_seed_uec` applies the session's choice the same way. `_block_key` (`:824`: partition, account and
what the block holds, `Size.key`) is what `switched_terms` / `reap_terms` record and compare, so a size change re-asks and a switch
back to the confirmed size is back on its terms; `_void_rejected` keeps the size too (`ShapeRuntime.rejected_size`).
`_stale_size` (`:770`): after `adopt_endpoint`, a size the session chose that the bound endpoint's template cannot
render (an endpoint configured before this change: `takes_resources` False) raises `StaleTemplateError` before any
check — the one path that learns it only at the bring-up (a startup pin); the validation refuses it up front otherwise.

**Review round 1.** `_apply_resources` compares what the block holds before and after (`_block_size(...)[0].key()`): the
same block in other words (`cores=8` when 8 is the proposed slice, `whole_node=True` on a whole-node partition) is the
session's choice with no switch. `_provision` reads the size again after `adopt_endpoint` (`asked_size` vs the size then)
and, when it differs, drops the confirmation before anything starts (`ShapeRuntime.resized`, said by the re-ask).
`_repoint` records whether a switch moved the size (`switched_size`) for the re-ask's words.

## A broken endpoint environment (2026-10-30, the returning-user cells)
`_provision`, after `_confirm_worker`: when the block is not warm and the dispatch failure is an import failure
(`notices.broken_endpoint_env`: `No module named …`, an ImportError), `_repair_broken_env` runs the facility's
`repair_endpoint_env` once per endpoint id (`AppCtx.env_repairs` holds what it did, or why it failed), marks the
shape's runners stale and confirms the worker again. It runs on whatever shape asked — the login shape is free — and
asks nothing about spend: a compute block's confirmation is unchanged. `server` prefixes the repair's words to the next
warm or provisioning notice (`_env_repair_note`, once).

## A repair that needs the user's login (2026-10-30, c08)
When a repair's SSH login is denied with an interactive method left — the key accepted and a one-time code pending,
or a password / keyboard-interactive login on a facility this user already runs an endpoint on (the key revoked,
nersc) — `_repair_handoff` makes the same handoff a connect does:
- it sets `app.pending_preauth` to the CLI's target, and `app.preauth_resume` to `ensure_endpoint_up(shape=…)`;
- it keeps the user's command and the words in `AppCtx.env_repair_handoff`;
- it does not count as a repair done: the next check that meets the broken environment tries again, over the
  connection the user opened.

`server` puts the command in `EndpointStatus.preauth_command` while the block is `provisioning`, and the words in every
answer until the shape is warm.

**Review round 1 (2026-10-31).** `_repair_broken_env` changed in four ways:
- **It runs in its own task** (`AppCtx.env_repair_tasks`, awaited through `asyncio.shield`). A call cancelled between
  the manager's stop and its start no longer takes the restart with it. The next check reads how it ended, even when
  that check passes (`_provision` calls in whenever a task is pending).
- **It is done only when the facility verified it** (`env_repaired`). A repair that raised is tried once more
  (`_REPAIR_TRIES` = 2); a login handed to the user is not an attempt.
- **It waits while work runs** on the endpoint it would restart (`_work_on_the_endpoint`: a live task handle on any
  shape, or a command in its sync-wait). Restarting the manager ends every user endpoint it runs.
  `env_repair_deferred` says so on every answer until the work ends.
- **Its note** (`server._env_repair_note`) is read only where every answer that follows carries it — the `down`
  answers too. `env_repair_said` keeps the note said per id, so a later attempt's new note is said again.
- **After a repair**, every shape's conflict streak starts at 0, and `ShapeRuntime.conflict_grace_until`
  (`_REPAIR_CONFLICT_GRACE_S`, 120 s) keeps RESOURCE_CONFLICT answers from counting while the user endpoints start
  again. In c08, re-run, three such answers in twelve seconds read "NO LONGER transient" and took the block down.

**Review round 2 (2026-10-31).**
- **The repair task does not outlive its binding.** A task left running by a cancelled call reached its start after a
  teardown had answered `down`, and registered the endpoint again. `_abandon_env_repairs` cancels every repair task and
  gives its try back. It runs from `_drop_all_shapes` (a re-bind, a detach) and from the teardown's claim, where it
  only cancels, so the claim has no await. The cancelled tasks wait in `AppCtx.env_repair_settling` until
  `_settle_env_repairs` has seen them unwind; it is bounded at 10 s, and `ssh_exec` kills its ssh child on the way
  out. The teardown task and connect both wait on it before they touch the login node.
- **The repair asks first.** It is started with `wanted=_still_bound(app, eid)`. The facility asks that before it
  stops or starts a manager: the same facility, the endpoint still bound, no teardown of it running.
- **Released work counts as busy.** `_work_on_the_endpoint` counts `_released_waiting`: commands still in their
  sync-wait on a runtime a release retired, on the bound endpoint. `server._block_work` uses the same helper.
- **A passing check clears a ghost.** `_confirm_worker` removes the endpoint from `AppCtx.ghost_endpoints` (see
