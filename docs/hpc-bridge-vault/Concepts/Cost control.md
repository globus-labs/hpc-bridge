# Cost control

> [!abstract] In one line
> The load-bearing net is **idle block release** (`min_blocks=0` + `max_idletime`): the compute node self-releases after the last task, so a forgotten session can't bleed allocation. A spend clock and the [[Resource shapes & the spend floor|spend floor]] guard the rest.

## The three nets

1. **Idle-release (back end).** The scheduler provider (`SlurmProvider` **or** `PBSProProvider` — scheduler-neutral) runs `min_blocks=0` with `max_idletime` (default 600 s), so the compute block — the thing that costs allocation — self-releases after the last task (validated live on Anvil). This is the safety net even if nothing else fires. The release comes from parsl's scaling pass, which runs every `strategy_period` ([[facility-remote]]). New endpoints get 5 s. An endpoint configured before this change and still running keeps 30 s, because reuse never rewrites the template. A facility MEP sets its own. The idle timer starts on the first pass that sees no task outstanding, and the block is cancelled on the first pass past `max_idletime`. So the release lands within about 0–10 s after the window at 5 s, plus each pass's own work, and within about 0–60 s at 30 s.

`warmth._IDLE_GRACE_S` (15 s: two 5 s passes plus 5 s for their work) is how long past the window the clock waits before presuming the block gone without looking. A canary to a released block makes the endpoint submit a new billed block before the user is asked. So a call after the release but before the presumption can still do that. On endpoints with the 5 s period the grace **narrows** that span to about 0–15 s; it does not close it.

Such a check is still caught. With the 5 s pass, the new block can answer inside the canary's 8 s timeout, so a timeout alone no longer reveals it, but the scheduler job id does. A canary answered by a different job than the confirmed block's (`block_job`) is a reap found by a check (`_confirm_worker`, kicked). The call answers `needs_confirmation` and names both jobs. The notice says the new block is already running and billing, started for work sent after the old block went (a task left waiting for a block) or for the check itself. Nothing more runs on it once a check has seen it, until the user confirms. The state is left exactly like a timeout-found reap: the new block is not adopted (no age, no job, no spend clock) until the user confirms it, and the confirm's canary then dates it. So, as on main's timeout path, a replacement block the user then confirms is dated from the confirm, not from its first answer. Keeping that first age is a possible follow-up. A defensive invariant in `_provision` backs this: a billed block is dated and billed only while spend is confirmed for it.

**Between checks, the wrong-block guard.** A check runs only once the last proof of life is stale: `CANARY_TTL_S` (45 s) since the last answer, and every completed command refreshes it. So a command sent sooner is not checked first. Each command on a confirmed block therefore carries the block's job, and the worker refuses it anywhere else:
- **Who is guarded.** `_ready_session` builds the dispatch's guard (`warmth._new_guard`) in the same locked step that counts the dispatch: a billed shape, one block at most (`_single_block`), spend confirmed, and `block_job` known (`_guard_job`). The login shape, `max_blocks` > 1 and an unknown job are never guarded. `reset_session` is guarded like `run_shell`: on a replacement it would be work there unasked, and a reset that "succeeded" would refresh the trust window and hide the replacement from the next check.
- **The refusal.** The guard (`session_shell.Guard`) is the block's job plus a fresh nonce for this dispatch. `session_shell.wrap(command, session, guard=…)` (and `reset_command`) puts it before anything else. When `${SLURM_JOB_ID:-${PBS_JOBID:-}}`, the expression the canary reports, is set and differs, it prints one line `HPCB_WRONG_BLOCK <nonce> <job>` to stderr and exits 86. Nothing else runs: no cd, no session state, no `.env`, no command. Unset (a LocalProvider block) or equal, the command runs as before. One gap: a worker a PBS site starts on a sister node (`mpiexec`, `pbsdsh`) may not inherit `PBS_JOBID`, and there a command runs unguarded, as on a block with no job.
- **Reading it back.** A refusal is exit 86 and a stderr line, any line, that starts `HPCB_WRONG_BLOCK <this dispatch's nonce> ` (`session_shell.refusal`). The nonce is what output cannot forge; the line's position proves nothing. Other lines come before it: a shell's start-up (a setlocale warning, `BASH_ENV`, a conda libtinfo note). Others come after it. On an endpoint without task sandboxing (a facility's, NCSA Delta's) the SDK's own sandbox warning is flushed after the command's output. A `set -x` prints `+ exit 86`, and an EXIT trap prints its own line. A first-line rule lost the refusal to the first kind, and a last-line rule lost it to the second, so on such a facility endpoint every refusal came back as an ordinary exit 86. The job is bounded to job-id characters and 96 characters before it is named anywhere; anything else is "a job whose id hpc-bridge cannot read".
- **The outcome.** A refusal is the kicked reap a check makes for a different job (`warmth._wrong_block_outcome`, from `_dispatch_counted` or, for a poll handle or a client-cancelled call's command, `_resolve_task`; the handle keeps the guard in `TaskHandle.guard`). The tool answers `needs_confirmation`. Its notice says once that the command did NOT run, names both jobs, says once that the new block is already running and billing, and asks for the user's confirmation. The old block is banked to its release bound, the replacement is not adopted until the user confirms, and the confirm's canary then dates it. If the confirm skips its canary (a task of ours still on the block), the block is dated by the guard's job, not the old one's. Two refusals in flight are one reap. A refusal that comes back after spend was confirmed again is not a second reap: it says the command did not run and should be sent again, naming the block now confirmed. A refusal from a block released under the call marks nothing.
- **What is not a refusal.** A command that exits 86 by itself is an ordinary result, and so is one whose output carries a marker without this dispatch's nonce. Output a command prints (a file, a program's error text, an injected instruction) cannot carry a nonce it never saw. So a command that ran is not reported as not run, its block's clock and age are kept, and no text from the block reaches a notice.
- **The one forge left.** The nonce is in the wrapper's own text, and the command runs inside that wrapper. A command written on purpose to read it (`$BASH_EXECUTION_STRING`), print the marker line and exit 86 is taken for a refusal. That takes deliberate intent: nothing a command merely prints can do it. The outcome is a needless re-ask: the notice says that command did NOT run (it did), the block's clock is banked and the confirmed block is reaped, and the user is asked to confirm the same block again, whose confirm's canary then dates it anew. Nothing runs unasked and nothing is billed that the bound would not.

Why: live 2026-10-13, after a hook scancel'd job 112, `sleep 75` ran on job 113 unasked, and a review probe sent 20 commands 40 s apart (13 minutes) to a replaced block with no check. The review of the first build found that a first-line rule lost the refusal behind a start-up warning (the command came back as an ordinary exit 86, unasked), and that a forged marker told the agent a command that ran had not. The scenario `reap_replaced_block` waits until the cancel has landed, then sends `echo JOB=$SLURM_JOB_ID` inside the window. It gates on the outcome (`no_work_on_replacement`) and reports the path (`replacement_found_by`: the guard, lost with the dying block's worker, or a check). Which path happens is timing: on the first live runs (pi, codex on fake/mep) the command went to the dying block's worker and was lost with it, and the next call's check found the replacement.

The comparison keys on the block the spend was confirmed for (`block_job` with `spend_confirmed`, one block). That block keeps its identity (`block_since`, `block_job`) through a failed dispatch, a runner rebuild, and a check that failed with an error (a task lost with its worker, a refused or broken submit, a transient `RESOURCE_CONFLICT`). The next answer is then compared: the same job keeps its age, a different job is a kicked reap, and a timeout is the block gone, not a cold start. Why: a failed check used to erase the identity, so the replacement was taken under the old confirmation (fake cluster, 2026-10-13, `reap_replaced_block`: job 112 scancel'd, a check failed with `TaskExecutionFailed`, job 113 read `up` and ran work without asking). The identity stays in place rather than moving to `presumed_block_job`: nothing says the block went, and the `presumed_*` fields carry the idle presumption's billing. Only a reap clears it, and so does a partition or account switch, which drops the confirmation too: the new terms' block is asked for again. A block is dated by its scheduler job (`AppCtx.job_seen_since`), so a job met again later keeps its age ([[warmth]]).

Two things keep counting through a failed check:
- **The idle presumption** counts from the block's last proof of life. `warmth._void_warm` keeps the latest one as `last_proof_at` whenever it voids `warm_confirmed_at` (a failed check or dispatch, a runner rebuild), and `_last_activity` takes the later of the two, so a late poll of an older task can't hide a newer proof. Without it, the presumption could never fire again, and a later call would send a canary that starts a new block instead of asking first.
- **The spend clock** runs on, because the block may well be up. `_provision` bills the result as warm, and restarts the clock at once if that call's runner rebuild banked it. A same-job answer leaves no unbilled gap. The idle presumption, or a reap, banks the clock to the latest the block could have lived. Where nothing could end the hold (an unknown idle window, as on the registry's Anvil and Delta MEPs), the clock stops at the failed check instead.

**A `down` never leaves a clock running.** The following stop the clock at the verdict, banked to the latest the block could have lived (`_release_bound`), and never hold it:
- a scheduler rejection of the block submission (`_submit_rejected`, SSH or MEP). With one block, the endpoint submits only once the confirmed block is gone, so a rejection is evidence of that. With `max_blocks` > 1 it is not: another block may still be up, so its clock runs on. The rejection notice says only the new block was not created, and an earlier block's time stays in `session_spend`;
- a no-account verdict;
- the conflict limit (`TRANSIENT_CONFLICT_LIMIT`);
- a check that raises (the `down` from an error in `ensure_endpoint_up`, or the error from `run_shell`). `_provision` stops the clock before re-raising, and the status carries `session_spend`.

An orphaned task (`poll_task` finds its endpoint gone) stops its block's clock too, and so does the manager reporting offline.

**A stopped clock resumes if the same block answers.** Whenever the clock stops while the block keeps its identity, `cost._bank_warm_interval` records where it stopped (`clock_stopped_at`: the bank's end, never past `_release_bound` or the walltime). If the same block is then billed as warm again, its clock resumes from there, so the gap is billed. That covers the same job answering, a hold after a stop, and a no-account verdict cleared by a new login. A different job would be a reap. If the idle presumption comes first, it hands the stop point on as `presumed_billed_until`. A reap or a switch drops it. Why: the same scheduler job answering was billing all along, and the gap from a 409 to that answer used to bill 0 s where no idle window was known.

Under a no-account verdict nothing is presumed either (`_check_reaped` skips it), since no block can be started for that identity and a spend question would only meet the same refusal. The identity is kept, so after a login that clears the verdict the next answer is still compared. `needs_confirmation` and `needs_account` report the session spend, so a reap's bank shows at once.

The same applies to any replacement: a release, an `scancel`, a node failure, or a preemption. A preempted job that is requeued keeps its id, though, so only a timeout reveals that one. The comparison is made only with one block at most (`max_blocks` 1, or unset: every template and registry entry we know). With more, a canary can land on a sibling block.

On a 30 s endpoint, and on a facility MEP whose template publishes an idle window, the presumption can come while the block is still up. That costs an extra spend question. The block that answers next is dated by the scheduler job its canary reports (`CanaryResult.worker_job`, from `$SLURM_JOB_ID` or `$PBS_JOBID`), against the presumed block's (`presumed_block_job`):
- **The same job** was still up. It keeps its older age, so its real walltime is still presumed without a canary. Its spend clock continues from where the presumption stopped it (`presumed_billed_until`), so the gap is billed.
- **A different job** is a new block, aged and billed from now.
- **Either id unknown** (not expected: every Slurm or PBS block has one): a block answering before the presumed one's latest possible end is treated as the same block, so its walltime is presumed early rather than missed.

This decision is exact whenever the job id is known, and heuristic otherwise. One exception: a block requeued under the same job id (a Slurm or PBS requeue) is taken for the old one and keeps the older age until it answers more than 30 s past that age's walltime (`_REQUEUE_GRACE_S`, a scheduler's kill grace). Then it runs a fresh walltime from that answer ([[warmth]]). Until then it errs early, toward an extra question.

A presumed or canary-found block is billed up to last activity + idle + `_RELEASE_BOUND_S`, capped at its walltime's end. `_RELEASE_BOUND_S` is 65 s: two 30 s passes and their work, the slowest release on any endpoint hpc-bridge has configured, and approximate on a facility MEP. This is an upper bound, the honest side of a spend estimate, except that the bill stops when the presumption is made. If that block later answers (same job), the gap is billed then.
2. **The spend clock.** `session_spend` ([[cost]] `estimate_spend` = elapsed × nodes × `charge_factor`) is driven by **true worker presence** (the canary, [[Warmth, the canary & cold-start]]) and **accrued across warm intervals** — banked on each warm→cold transition so it survives idle-release without over-counting the idle gap. It rides every result. `charge_factor` defaults to `0.0` (free local dev).
3. **The spend floor (front end).** A billed block won't *start* without `confirm_spend=True` — see [[Resource shapes & the spend floor]].

> [!note] Long work is a *task*, not a detached process ([#21](https://github.com/globus-labs/hpc-bridge/issues/21))
> Idle-release keys off **Compute-task activity**, not node CPU. A long *foreground* task keeps the block busy, so it runs to completion (retrieved via [[The MCP tools|poll_task]] once it outlives the sync-wait) and is never released mid-run — its ceiling is the **block walltime** (the worker kills it at ~that, exit 124), optionally capped by `HPC_BRIDGE_MAX_TASK_S`. A **detached** process (`nohup … &`) is *not* a Compute task, so the block idle-releases out from under it — the classic footgun. `session_spend` accrues across the whole run: a running task keeps the warm clock ticking (the [[Warmth, the canary & cold-start|canary is short-circuited]] while it holds the worker).
>
> Work longer than the walltime either checkpoints and resumes across blocks, or runs as a batch job — submitted from the login node, or, on a facility MEP (no login node), from inside the block where the site allows it. A batch job sits **outside all three nets**: billed to the allocation like a block, but never gated, never on the spend clock, never cancelled by `stop_endpoint`. It is the user's to approve and to cancel; the run_shell / login_shell result says so ([[Resource shapes & the spend floor#The spend floor|the floor's blind spot]]).

> [!note] The idle timer only resets on a task a pass *sees*
> parsl's strategy (`Strategy._general_strategy`) resets the idle timer only when a pass finds a task outstanding at that instant. A task drops out of the count the moment its result arrives (HTEX `outstanding()` is `len(self.tasks)`). So a command that starts and finishes between two passes does not restart the timer: the window runs from the last task a pass saw, which can be earlier than the last task hpc-bridge ran. With 5 s passes only tasks shorter than 5 s can go unseen. With 30 s passes (still on older running endpoints, see above), most short commands and canaries do. A facility MEP's period is its own.

`stop_endpoint` means **stop spending, not destroy the endpoint**: it `scancel`s the billed block over the **login endpoint (AMQP, no SSH)** and **leaves the manager online**, so the next session reuses it with zero SSH ([[Standing up the endpoint|SSH-once]]). It drops the billed (`compute`) shape (a later run re-provisions a fresh block) and keeps the login shape, the manager, and the [[state|pin]].

**Confirmed-or-honest release (#24).** The cancel rides the login shape, which may be **cold** at stop time (the worker scaled in) — the first `scancel` dispatch then comes back `cold_start`, not `complete`, so the cancel is *unconfirmed*. That first hit wakes the worker, so `_release_blocks_over_login` **retries a bounded few times** (`HPC_BRIDGE_RELEASE_ATTEMPTS`×`_BACKOFF_S`, default 3×6s) to *confirm*. If confirmed → `status="down"` with `spend_stopped` true (the only result that says so). If still cold after the retries → **`status="draining"`, never `"down"`** (`spend_stopped` none: unknown): spend is not verifiably stopped, so the status must not say it is (an agent that reads "down" walks away while the block burns). idle-release (`min_blocks=0`+`max_idletime`, ~10 min) is the backstop, and re-calling `stop_endpoint` (channel now warm) confirms. Before the fix, stop returned `status="down"` with a notice admitting *"cancel not confirmed"* — a contradiction measured at ~5% of stops; see [[Agentic testing - Plan B (runtime sandbox)|the harness]] `stop_is_honest` invariant. Fully pulling the endpoint down (`gce stop` — the facility's `teardown()`) is a separate, rarer operation, **not** done here — it is the explicit `teardown_endpoint` tool ([[The MCP tools]]). (The old multi-minute "stop hang" was `runner.close()` blocking on `Executor.shutdown(wait=True)`, not the cancel — fixed in [[runner]].)

**Stop refuses while our work holds the block** (`_busy_block_refusal` / `_block_work`, [[server]]). Releasing an SSH block under a running task does not end the task: the endpoint relaunches a block for it (fake-cluster chaos `stop_while_running`, 2026-09-05), so `down` would be false. The stop answers `up` and names what holds the block: a task behind a poll handle (a `reset_session` past its sync-wait becomes one too, like `run_shell`), a call still inside its sync-wait (`ShapeRuntime.inflight`), or the command of an agent call the client cancelled (below). The invariants:
- **The stop looks under `app.lock`.** A `run_shell` that holds the lock while it provisions (its canary) has therefore counted its dispatch first. A MEP stop looks and drops in one locked step. The SSH release rides `run_shell`, so it runs off the lock; afterwards the stop looks again and drops in one locked step. If a dispatch reached the block meanwhile, it answers `draining` and keeps the shape.
- **A block released under a call** (a teardown's release step, or a re-bind) affects sent tasks two ways. `Executor.shutdown` cancels only unsent tasks, and the SDK's result watcher still resolves sent ones.
  - *A call still inside its sync-wait* stays tracked while the endpoint it was sent to is the bound one, including after a re-connect to the same endpoint. A stop counts it (`AppCtx.released_inflight`), and it gets a handle when it returns. Its dropped runtime is never rebuilt.
  - *A task that already had a handle* is drained with the shape (`_drain_shape_tasks`): the teardown abandons it, and a stop during the rest of that teardown (its one-time-code gate, for instance) no longer sees it.
  - After a teardown finishes, or after a re-bind to another endpoint, a returning call reports its command instead of tracking it (`_released_under_outcome`).
- **Past its ceiling is not lost.** A task's ceiling counts from when it *starts*, so one pending past it (counted from the submit) may only be queued behind another task or a relaunching block. It keeps holding everything it held: the stop and the canary short-circuit for a compute task, and its session and the idle presumption for any task. `poll_task` keeps answering `running` with a notice fitted to its shape: a login task does not hold the stop, but it holds its session and the login worker (the next login command, and a stop's cancel, queue behind it), so the agent can leave it and use another `session_id`. The one exception is a compute task on a facility MEP, where nothing else could ever end it. There, one pending `_LOST_TASK_GRACE_S` (600 s) past its ceiling is presumed lost (`warmth._overdue`), and stop and the detach abandon it, naming it.
- **Internal ops never use the agent's sessions.** The scheduler ops (`_login_runner`: the release, the pilot probe, the allocation listing) run in their own login session, `_INTERNAL_SESSION`. Its prefix is reserved: an agent call that names it is refused. A cancelled internal op is not tracked. One that outlives its sync-wait occupies only that session, and a stop that finds it busy says the release channel is busy, not cold.
- **Abandoning running work** is `teardown_endpoint` on an SSH endpoint, which abandons it with the manager; on a MEP nothing can end it early.

> [!warning] Cancelling a call does not cancel its command
> Esc in Claude Code sends `notifications/cancelled`, and `_heartbeat` cancels the dispatch coroutine, but the command was already sent and runs to its ceiling. For the agent's own calls (`agent_call`), `_dispatch_counted` hands the in-flight count to a poll handle marked `client_cancelled` in one synchronous step (no await), so stop, the busy session, the canary short-circuit and the spend clock all still see it. Left untracked (found in review, 2026-10), a stop answered a false `down`, the next forced canary read as a reap and re-asked for spend, and a second command could clobber the session.

**On a facility multi-user endpoint, a stop issues NO cancel — and `draining` is terminal ([#178](https://github.com/globus-labs/hpc-bridge/issues/178)).** A [[facility-mep|MEP]] has no login shape, so no release channel exists, and the Globus SDK offers no honest foreign-endpoint cancel (`ComputeFuture.cancel` is pre-run only; `stop_endpoint`/`delete_endpoint` act on *our* registration). `_stop_mep` ([[server]]) therefore stops submitting, drops the compute shape, and reports `status="draining"` — never `down`, and re-polling never yields `down`. What it must say is what is left billing, so the user can end it:
- The notice (`notices._no_cancel_notice`, about 570 characters for one block) **leads with "NO CANCEL WAS ISSUED"**, then names the block's scheduler job (`EndpointStatus.block_job_id`), the latest it can bill until as a clock time (with the date when it is not today; "possibly sooner (not verified)"), the user's command to end it now (`scancel <id>` on Slurm, `qdel <id>` on PBS: `MEPFacility.scheduler`, kept from the entry's `compute.scheduler`) and to check on it there (`squeue -j` / `qstat`), to relay. It never suggests a check from here: after a stop, `run_shell` or a confirmed `ensure_endpoint_up` is a task, which can keep the block alive or start a new one. (An unconfirmed `ensure_endpoint_up` answers `needs_confirmation` before any check, and a reconnect makes only web calls; a unit test pins both.)
- **The job id is resolved in the stop's locked step, before the shape is dropped** (`warmth._resolve_left`): the confirmed block's `block_job`; else the job of the new block a check found after a reap (`reap_kicked`); else the block whose check answered after its caller stopped waiting (`GlobusRunner.canary_answer`, read without waiting); else the presumed block's `presumed_block_job`; else a check still queued (`_check_queued`: the runner's `canary_pending`, or a timed-out check with no proof of life since), which the notice states as a fact — the facility will start or keep a block for it — with `squeue -u <mapped account>`; else none known. Where no job id is known, the notice says how Globus Compute names a block (`parsl.GlobusComputeEngine-…`, `parsl.Gl` in squeue) — and that every Globus Compute block on a shared mapped account looks the same (and a facility can rename them), so the user checks the start time and partition before cancelling. A named job id is always preferred. With `max_blocks` > 1 it says "at least".
- **The latest end** (`LeftBlock.until`, and `bound` says which): `_release_bound` (last activity + idle window + `_RELEASE_BOUND_S`, capped at the walltime); the walltime's end alone when the facility's idle window is unknown; and the walltime's end when work of ours may still be on the block (`_work_on_block`: a task whose end is not stamped, or a call in its sync-wait — a reconnect does not refuse while a task runs, and no idle window has started); unknown when nothing bounds it. The notice says which.
- **The mapped account.** The canary also prints `id -un` (`HPCB_USER`, parsed like `HPCB_JOB`), kept as `AppCtx.worker_user`: on `globus-labs` the identity maps to `glabs-gc`, so the user's own login name would miss the job in `squeue -u`.
- **Remembered, to name it — never to bill it.** Every block (or queued check) a facility stop, detach, reconnect or partition/account switch lets go is kept in `AppCtx.left_blocks` (`LeftBlock`: job, kind, latest end, when and how it was left, partition and account, `verified`, `ends_by`). A second stop, a stop after a reconnect to the same endpoint, and a stop or a second teardown after a detach still name it (never a bare "no endpoint was up"); a reconnect's own result names it too; a bind to another endpoint drops them. A block past its walltime's end (`ends_by`) is dropped (`_prune_left`). A queued check is never dropped: the queue wait is unbounded and the facility keeps starting blocks while it waits, so its entry stays, dated ("left queued at …; it may have run since"), the most recent per partition and account (one facility user endpoint each), and the notice names each partition (the newest few, then a count). A block a queued check starts is never on the spend clock, and the notice says `session_spend` does not count it. A block first confirmed afterwards only takes entries off the list (`_take_left`: the same job, or with one block the same partition and account); it is dated and billed from its own confirmation.
- **A switch lets go of the old block entirely.** After recording it, `_leave_switched` closes and clears the old runner and clears `last_canary` and `reap_kicked`, so a later stop cannot read the old runner's unread answer again and file it under the new partition (review 2026-10-13: it did, and left 645 s unbilled).
- **`spend_stopped`** is never true on a MEP: false while a block may still bill or a check is queued, none when every block it names is presumed released by now (past its latest end) or none is known. `block_state` is the block's presumed state, never "cold" while it may run.
- **Billing: to the bound, each tail once.** A facility stop, detach, reconnect or switch banks the block to its latest end (the honest upper bound, ahead of now when it is), from where its clock stood: a running clock is banked first, a stopped one from `clock_stopped_at`, a presumed block from `presumed_billed_until`, a check-found block from its answer. A remembered entry never bills again. A block confirmed again after a stop bills from its new confirmation (its clock is never continued from the left entry), so that run can overlap the earlier tail and count twice. What does NOT repeat is the tail: `AppCtx.billed_to` keeps, per (endpoint, job), how far a bank has counted that job, and a later tail adds only the time past it, then advances it (dropped with `left_blocks` on a bind elsewhere). So N stop/re-confirm cycles count the union of the block's bounds plus each cycle's own run once more — at most one bound beyond the union in the tests — where each stop used to bank the whole remaining tail again (no idle window, 2 h walltime: 4 stops in 310 s reported 8.0 node-h; review 2026-10-13). Keeping one continuous clock across a stop, a reconnect and a re-confirm was tried and dropped: each fix opened another double count or gap. **`session_spend` is an upper bound**, and the stop notice says it counts THIS call's block to its latest end; a block an earlier stop or detach left was counted in the spend reported then (a new binding starts `session_spend` at 0), and the notice says that instead.

A block cancelling itself (a last task running `scancel $SLURM_JOB_ID`) was considered and rejected: the task stays outstanding until the manager notices the worker is gone, so parsl starts a replacement block, which then idles out its window — and it cannot rule out a sibling session on the same block.

A task still running on the block makes stop *refuse* (`up`, `spend_stopped` false; the block stays busy until it ends; poll it to completion first). The same goes for a call in its sync-wait and for a cancelled call's command, but not for a task presumed lost (above). `teardown_endpoint` on a MEP is a **detach**: our state is cleared (`down`), the facility's endpoint is untouched, and the block bills on — so the detach gives the same notice and fields as the stop. It refuses under the same conditions as stop, because detaching would drop the handles (and the results with them) while the block stays busy and billing rather than idle-releasing. Every shape on a MEP is billed — the `needs_confirmation` notice does not point at a free login shape there (`_needs_confirmation_notice`). The five-minute still-allocating notice there names only a CONFIRMED block of the same partition and account, not presumed gone (`_known_block_job`: this shape's `block_job`, or a confirmed block a stop or switch left), and the mapped account; it gives that job's cancel command only for this shape's own block, else `<job id>` — an `scancel` of a wrong id can end someone else's job.

**The numbers the agent relays (0.1.18).** The spend clock multiplies by the block's own node count (its `nodes_per_block`), not a profile default. On a facility MEP the idle window is the facility's: read from its published template's `max_idletime` at attach, and when the template does not publish a constant the notices say "the facility's own idle window" rather than quote our 600 s, which is only true of the endpoints hpc-bridge configures itself. An SSH teardown stops the compute clock at the release, like `stop_endpoint`.

> [!note] session_spend ≠ real SU charge (today)
> Because `charge_factor` defaults to 0 and isn't set on Anvil, `session_spend` reads 0 even while Slurm charges the allocation. The authoritative number is the live `mybalance` delta; wiring a real per-facility rate is [[Discovery today|future discovery]] work, not current behaviour.
