# Cost control

> [!abstract] In one line
> The load-bearing net is **idle block release** (`min_blocks=0` + `max_idletime`): the compute node self-releases after the last task, so a forgotten session can't bleed allocation. A spend clock and the [[Resource shapes & the spend floor|spend floor]] guard the rest.

## The three nets

1. **Idle-release (back end).** The scheduler provider (`SlurmProvider` **or** `PBSProProvider` — scheduler-neutral) runs `min_blocks=0` with `max_idletime` (default 600 s), so the compute block — the thing that costs allocation — self-releases after the last task (validated live on Anvil). This is the safety net even if nothing else fires. The release comes from parsl's scaling pass, which runs every `strategy_period` ([[facility-remote]]). New endpoints get 5 s. An endpoint configured before 2026-10 and still running keeps 30 s, because reuse never rewrites the template. A facility MEP sets its own. The idle timer starts on the first pass that sees no task outstanding, and the block is cancelled on the first pass past `max_idletime`. So the release lands within about 0–10 s after the window at 5 s, and within about 0–60 s at 30 s, plus each pass's own work. hpc-bridge cannot tell which period a given endpoint runs, so from the window on it treats the block as possibly released (below).
2. **The spend clock.** `session_spend` ([[cost]] `estimate_spend` = elapsed × nodes × `charge_factor`) is driven by **true worker presence** (the canary, [[Warmth, the canary & cold-start]]) and **accrued across warm intervals** — banked on each warm→cold transition so it survives idle-release without over-counting the idle gap. It rides every result. `charge_factor` defaults to `0.0` (free local dev).
3. **The spend floor (front end).** A billed block won't *start* without `confirm_spend=True` — see [[Resource shapes & the spend floor]].

> [!note] Long work is a *task*, not a detached process ([#21](https://github.com/globus-labs/hpc-bridge/issues/21))
> Idle-release keys off **Compute-task activity**, not node CPU. A long *foreground* task keeps the block busy, so it runs to completion (retrieved via [[The MCP tools|poll_task]] once it outlives the sync-wait) and is never released mid-run — its ceiling is the **block walltime** (the worker kills it at ~that, exit 124), optionally capped by `HPC_BRIDGE_MAX_TASK_S`. A **detached** process (`nohup … &`) is *not* a Compute task, so the block idle-releases out from under it — the classic footgun. `session_spend` accrues across the whole run: a running task keeps the warm clock ticking (the [[Warmth, the canary & cold-start|canary is short-circuited]] while it holds the worker).

> [!warning] Past the idle window, spend is asked again before anything is sent (2026-10)
> A canary to a block that has idle-released makes the endpoint submit a new billed block. So from the moment a confirmed block has had no task for its idle window, the next call answers `needs_confirmation` and submits nothing, whatever the scaling period. ([[warmth]]: `_check_reaped`.) Until 2026-10 the clock waited 60 s past the window first. A call in that gap sent a canary, and that canary could start a new billed block before the user was asked.
> - **Tentative** (`_maybe_released`, up to `_CERTAIN_RELEASE_GRACE_S` = 60 s past the window): the block may still be up. Only the confirmation is cleared. The block keeps its age (`block_since`) and its running spend clock. The notice says the block "has been or is about to be idle-released", and that confirming continues on it if it is still up or starts a new block.
> - **The confirm's canary decides,** by the scheduler job it ran in (`CanaryResult.worker_job`, Slurm's or PBS's job id). The **same job** as the block's (`block_job`) means it was still up: its age and spend clock simply continue. A **different job**, no answer, or a failure means it was released: its spend is banked to last activity + idle + 60 s, an upper bound. The block that comes up is the one just confirmed, never reported as "kicked". An **unknown** job id is treated as a new block for billing but keeps the older age, so the walltime presumption errs early.
> - **Certain** (`_presumed_reaped`, ≥ 60 s past the window, or past the walltime): unchanged. The block is forgotten and banked to last activity + idle. A question left unanswered into this range turns certain without being asked twice.
>
> The cost is precisely one spend question for a user who comes back just after the idle window to a block that is still up. Confirming then continues on that same block.

> [!note] The idle timer only resets on a task a pass *sees*
> parsl's strategy (`Strategy._general_strategy`) resets the idle timer only when a pass finds a task outstanding at that instant. A task drops out of the count the moment its result arrives (HTEX `outstanding()` is `len(self.tasks)`). So a command that starts and finishes between two passes does not restart the timer: the window runs from the last task a pass saw, which can be earlier than the last task hpc-bridge ran. With 5 s passes only tasks shorter than 5 s can go unseen. With 30 s passes (still on older running endpoints, see above), most short commands and canaries do. A facility MEP's period is its own.

`stop_endpoint` means **stop spending, not destroy the endpoint**: it `scancel`s the billed block over the **login endpoint (AMQP, no SSH)** and **leaves the manager online**, so the next session reuses it with zero SSH ([[Standing up the endpoint|SSH-once]]). It drops the billed (`compute`) shape (a later run re-provisions a fresh block) and keeps the login shape, the manager, and the [[state|pin]].

**Confirmed-or-honest release (#24).** The cancel rides the login shape, which may be **cold** at stop time (the worker scaled in) — the first `scancel` dispatch then comes back `cold_start`, not `complete`, so the cancel is *unconfirmed*. That first hit wakes the worker, so `_release_blocks_over_login` **retries a bounded few times** (`HPC_BRIDGE_RELEASE_ATTEMPTS`×`_BACKOFF_S`, default 3×6s) to *confirm*. If confirmed → `status="down"`. If still cold after the retries → **`status="draining"`, never `"down"`**: spend is not verifiably stopped, so the status must not say it is (an agent that reads "down" walks away while the block burns). idle-release (`min_blocks=0`+`max_idletime`, ~10 min) is the backstop, and re-calling `stop_endpoint` (channel now warm) confirms. Before the fix, stop returned `status="down"` with a notice admitting *"cancel not confirmed"* — a contradiction measured at ~5% of stops; see [[Agentic testing - Plan B (runtime sandbox)|the harness]] `stop_is_honest` invariant. Fully pulling the endpoint down (`gce stop` — the facility's `teardown()`) is a separate, rarer operation, **not** done here — it is the explicit `teardown_endpoint` tool ([[The MCP tools]]). (The old multi-minute "stop hang" was `runner.close()` blocking on `Executor.shutdown(wait=True)`, not the cancel — fixed in [[runner]].)

**On a facility multi-user endpoint, stop is draining-only — and `draining` is terminal.** A [[facility-mep|MEP]] has no login shape, so no release channel exists, and the Globus SDK offers no honest foreign-endpoint cancel (`ComputeFuture.cancel` is pre-run only; `stop_endpoint`/`delete_endpoint` act on *our* registration). `_stop_mep` ([[server]]) therefore stops submitting, drops the compute shape, and reports `status="draining"` with the facility's idle-release window named in the notice — never `down`, and re-polling never yields `down`. A task still running on the block makes stop *refuse* (the block stays busy until it ends; poll it to completion first). `teardown_endpoint` on a MEP is a **detach**: our state is cleared, the facility's endpoint is untouched. Every shape on a MEP is billed — the `needs_confirmation` notice does not point at a free login shape there (`_needs_confirmation_notice`).

**The numbers the agent relays (0.1.18).** The spend clock multiplies by the block's own node count (its `nodes_per_block`), not a profile default. On a facility MEP the idle window is the facility's: read from its published template's `max_idletime` at attach, and when the template does not publish a constant the notices say "the facility's own idle window" rather than quote our 600 s, which is only true of the endpoints hpc-bridge configures itself. An SSH teardown stops the compute clock at the release, like `stop_endpoint`.

> [!note] session_spend ≠ real SU charge (today)
> Because `charge_factor` defaults to 0 and isn't set on Anvil, `session_spend` reads 0 even while Slurm charges the allocation. The authoritative number is the live `mybalance` delta; wiring a real per-facility rate is [[Discovery today|future discovery]] work, not current behaviour.
