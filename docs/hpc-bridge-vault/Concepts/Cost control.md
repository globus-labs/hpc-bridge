# Cost control

> [!abstract] In one line
> The load-bearing net is **idle block release** (`min_blocks=0` + `max_idletime`): the compute node self-releases after the last task, so a forgotten session can't bleed allocation. A spend clock and the [[Resource shapes & the spend floor|spend floor]] guard the rest.

## The three nets

1. **Idle-release (back end).** The scheduler provider (`SlurmProvider` **or** `PBSProProvider` — scheduler-neutral) runs `min_blocks=0` with `max_idletime` (default 600 s), so the compute block — the thing that costs allocation — self-releases after the last task (validated live on Anvil). This is the safety net even if nothing else fires.
2. **The spend clock.** `session_spend` ([[cost]] `estimate_spend` = elapsed × nodes × `charge_factor`) is driven by **true worker presence** (the canary, [[Warmth, the canary & cold-start]]) and **accrued across warm intervals** — banked on each warm→cold transition so it survives idle-release without over-counting the idle gap. It rides every result. `charge_factor` defaults to `0.0` (free local dev).
3. **The spend floor (front end).** A billed block won't *start* without `confirm_spend=True` — see [[Resource shapes & the spend floor]].

> [!note] Long work is a *task*, not a detached process ([#21](https://github.com/globus-labs/hpc-bridge/issues/21))
> Idle-release keys off **Compute-task activity**, not node CPU. A long *foreground* task keeps the block busy, so it runs to completion (retrieved via [[The MCP tools|poll_task]] once it outlives the sync-wait) and is never released mid-run — its ceiling is the **block walltime** (the worker kills it at ~that, exit 124), optionally capped by `HPC_BRIDGE_MAX_TASK_S`. A **detached** process (`nohup … &`) is *not* a Compute task, so the block idle-releases out from under it — the classic footgun. `session_spend` accrues across the whole run: a running task keeps the warm clock ticking (the [[Warmth, the canary & cold-start|canary is short-circuited]] while it holds the worker).

`stop_endpoint` means **stop spending, not destroy the endpoint**: it `scancel`s the billed block over the **login endpoint (AMQP, no SSH)** and **leaves the manager online**, so the next session reuses it with zero SSH ([[Standing up the endpoint|SSH-once]]). It drops the billed (`compute`) shape (a later run re-provisions a fresh block) and keeps the login shape, the manager, and the [[state|pin]].

**Confirmed-or-honest release (#24).** The cancel rides the login shape, which may be **cold** at stop time (the worker scaled in) — the first `scancel` dispatch then comes back `cold_start`, not `complete`, so the cancel is *unconfirmed*. That first hit wakes the worker, so `_release_blocks_over_login` **retries a bounded few times** (`HPC_BRIDGE_RELEASE_ATTEMPTS`×`_BACKOFF_S`, default 3×6s) to *confirm*. If confirmed → `status="down"`. If still cold after the retries → **`status="draining"`, never `"down"`**: spend is not verifiably stopped, so the status must not say it is (an agent that reads "down" walks away while the block burns). idle-release (`min_blocks=0`+`max_idletime`, ~10 min) is the backstop, and re-calling `stop_endpoint` (channel now warm) confirms. Before the fix, stop returned `status="down"` with a notice admitting *"cancel not confirmed"* — a contradiction measured at ~5% of stops; see [[Agentic testing - Plan B (runtime sandbox)|the harness]] `stop_is_honest` invariant. Fully pulling the endpoint down (`gce stop` — the facility's `teardown()`) is a separate, rarer operation, **not** done here — it is the explicit `teardown_endpoint` tool ([[The MCP tools]]). (The old multi-minute "stop hang" was `runner.close()` blocking on `Executor.shutdown(wait=True)`, not the cancel — fixed in [[runner]].)

**Stop refuses while our work holds the block** (`_busy_block_refusal` / `_block_work`, [[server]]). Releasing an SSH block under a running task does not end the task: the endpoint relaunches a block for it (fake-cluster chaos `stop_while_running`, 2026-09-05), so `down` would be false. The stop answers `up` and names what holds the block: a task behind a poll handle (a `reset_session` past its sync-wait becomes one too, like `run_shell`), a call still inside its sync-wait (`ShapeRuntime.inflight`), or the command of an agent call the client cancelled (below). The invariants:
- **The stop looks under `app.lock`.** A `run_shell` that holds the lock while it provisions (its canary) has therefore counted its dispatch first. A MEP stop looks and drops in one locked step. The SSH release rides `run_shell`, so it runs off the lock; afterwards the stop looks again and drops in one locked step. If a dispatch reached the block meanwhile, it answers `draining` and keeps the shape.
- **A block released under a call** (a teardown's release step, or a re-bind) affects sent tasks two ways. `Executor.shutdown` cancels only unsent tasks, and the SDK's result watcher still resolves sent ones.
  - *A call still inside its sync-wait* stays tracked while the endpoint it was sent to is the bound one, including after a re-connect to the same endpoint. A stop counts it (`AppCtx.released_inflight`), and it gets a handle when it returns. Its dropped runtime is never rebuilt.
  - *A task that already had a handle* is drained with the shape (`_drain_shape_tasks`): the teardown abandons it, and a stop during the rest of that teardown (its one-time-code gate, for instance) no longer sees it.
  - After a teardown finishes, or after a re-bind to another endpoint, a returning call reports its command instead of tracking it (`_released_under_outcome`).
- **Past its ceiling is not lost.** A task's ceiling counts from when it *starts*, so one pending past it (counted from the submit) may only be queued behind another task or a relaunching block. It keeps holding everything it held: the stop and the canary short-circuit for a compute task, and its session and the idle presumption for any task. `poll_task` keeps answering `running` with a notice fitted to its shape: a login task does not hold the stop, but it holds its session and the login worker (the next login command, and a stop's cancel, queue behind it), so the agent can leave it and use another `session_id`. The one exception is a compute task on a facility MEP, where nothing else could ever end it. There, one pending `_LOST_TASK_GRACE_S` (600 s) past its ceiling is presumed lost (`warmth._overdue`), and stop and the detach abandon it, naming it.
- **Internal ops never use the agent's sessions.** The scheduler ops (`_login_runner`: the release, the pilot probe, the allocation listing) run in their own login session, `_INTERNAL_SESSION`. Its prefix is reserved: an agent call that names it is refused. A cancelled internal op is not tracked. One that outlives its sync-wait occupies only that session, and a stop that finds it busy says the release channel is busy, not cold.
- **Abandoning running work** is `teardown_endpoint` on an SSH endpoint, which abandons it with the manager; on a MEP nothing can end it early.

> [!warning] Cancelling a call does not cancel its command
> Esc in Claude Code sends `notifications/cancelled`, and `_heartbeat` cancels the dispatch coroutine, but the command was already sent and runs to its ceiling. For the agent's own calls (`agent_call`), `_dispatch_counted` hands the in-flight count to a poll handle marked `client_cancelled` in one synchronous step (no await), so stop, the busy session, the canary short-circuit and the spend clock all still see it. Left untracked (found in review, 2026-10), a stop answered a false `down`, the next forced canary read as a reap and re-asked for spend, and a second command could clobber the session.**On a facility multi-user endpoint, stop is draining-only — and `draining` is terminal.** A [[facility-mep|MEP]] has no login shape, so no release channel exists, and the Globus SDK offers no honest foreign-endpoint cancel (`ComputeFuture.cancel` is pre-run only; `stop_endpoint`/`delete_endpoint` act on *our* registration). `_stop_mep` ([[server]]) therefore stops submitting, drops the compute shape, and reports `status="draining"` with the facility's idle-release window named in the notice — never `down`, and re-polling never yields `down`. A task still running on the block makes stop *refuse* (the block stays busy until it ends; poll it to completion first). The same goes for a call in its sync-wait and for a cancelled call's command, but not for a task presumed lost (above). `teardown_endpoint` on a MEP is a **detach**: our state is cleared, the facility's endpoint is untouched. The detach refuses under the same conditions as stop, because detaching would drop the handles (and the results with them) while the block stays busy and billing rather than idle-releasing. Every shape on a MEP is billed — the `needs_confirmation` notice does not point at a free login shape there (`_needs_confirmation_notice`).

**The numbers the agent relays (0.1.18).** The spend clock multiplies by the block's own node count (its `nodes_per_block`), not a profile default. On a facility MEP the idle window is the facility's: read from its published template's `max_idletime` at attach, and when the template does not publish a constant the notices say "the facility's own idle window" rather than quote our 600 s, which is only true of the endpoints hpc-bridge configures itself. An SSH teardown stops the compute clock at the release, like `stop_endpoint`.

> [!note] session_spend ≠ real SU charge (today)
> Because `charge_factor` defaults to 0 and isn't set on Anvil, `session_spend` reads 0 even while Slurm charges the allocation. The authoritative number is the live `mybalance` delta; wiring a real per-facility rate is [[Discovery today|future discovery]] work, not current behaviour.
