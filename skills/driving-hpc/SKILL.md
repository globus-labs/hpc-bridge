# Driving HPC with hpc-bridge

- You have a **persistent session shell**: `cd` and relative paths carry across turns — **and across blocks**: the working directory and exported variables live on the facility's shared filesystem, not on the node, so a new block after an idle release or walltime picks the session up where it was (files on node-local disk do not survive). Call `reset_session` for a clean slate.
- A call may be **cold** on first use — `ensure_endpoint_up`/`run_shell` reporting `provisioning`/`cold_start` means a worker is still warming (a compute block may be allocating, Slurm or PBS); retry shortly. Its notice may also say what the scheduler shows of the block, such as HELD, or likely REJECTED with the scheduler's reply; that is not a warm-up to wait out.
- A notice saying **the stored Globus login no longer works** (expired or revoked) is not a cold start or a queue wait: call `authenticate(force=True)`, relay its link, then retry.
- **Expect a command to be verbose? Redirect it to a file up front** (`cmd > out.log 2>&1`) and read ranges (`wc -l`, `head -n 100`, `sed -n '101,200p'`, `tail -n 100`): a result over Globus Compute's size limit fails outright and its exit code is lost, and long output that fits comes back cut to its end (~16,000 characters per stream), opening with a marker that says what was dropped — never read a cut result as the whole.

## SSH once, then work through the endpoint

hpc-bridge stands up a personal Globus Compute endpoint on the login node. Reaching it costs **one** SSH bootstrap — and often **zero**, because a still-running endpoint from a prior session is reused over the network. **Treat SSH as that one-time bootstrap, not a channel:** once the endpoint is up, do *everything* through it — discovery as well as compute — via `run_shell`. Every fresh SSH risks an interactive re-auth on a multi-factor (Duo/MFA) facility, so we avoid it.

Concretely: the **`login` shape** runs commands on the **login node** through the endpoint (a free `LocalProvider` — no allocation, no cost) — that's your no-SSH channel for discovery (`sinfo`/`qstat -Q`, `mybalance`, `squeue`/`qstat -u $USER`). The **`compute` shape** runs on a billed compute block. `login_shell` (raw SSH) is a **cold-start escape hatch only** — see the end.

## Compute-only facilities (a facility-run multi-user endpoint)

Some catalogued facilities are reached through the **facility's own multi-user endpoint** (a MEP) rather than an endpoint hpc-bridge stands up. `connect_facility` tells you: its notice says **"compute-only"** and it returns `needs_account` with `reused=True` immediately (nothing to bootstrap — **zero SSH, ever**; the facility maps your Globus identity to a local account). Three things differ from the flow below, and the tool results say so each time:

- **There is no `login` shape.** The facility's schema refuses a free login-node block, so `run_shell(shape="login")`, `ensure_endpoint_up(shape="login")` and `login_shell` are refused with a notice. **Everything — discovery included — runs on the `compute` shape**, which is billed but **stays warm between calls** (a pre-spawned block, kept alive by the facility's idle-release), so cheap follow-ups (`sinfo`, `squeue`, `ls`) don't re-queue. Partition defaults come from the catalog; confirm spend once, then work.
- **Account:** the result's `block` and notice say whether one is needed. If it says **"no allocation account is needed — do not look for one"**, don't search for an allocation tool: only the partition is the user's call (step 2 below). Otherwise the account comes from the user — there is no allocation listing (no login node to run it on); `block.account_hint` says where they find it.
- **A login name is not an account.** If the user answers an account question with their username, do not confirm spend: ask for the project/allocation id (`block.account_hint` says where the user finds it; on ACCESS machines it is usually the ACCESS project id). On an account-required facility `ensure_endpoint_up(confirm_spend=True)` with no account returns `needs_account` and starts nothing.
- **No account there?** Attaching never tests the identity mapping — only the first block start does, so a clean `connect_facility` says nothing about access. If `ensure_endpoint_up` comes back `down` with **"NO ACCOUNT at this facility"**, the facility's endpoint could not map the user's Globus identity to a local account. It is **terminal** — not a queue wait: do not poll or retry. Tell the user which identity was refused (the notice names it) and that they need an account on that machine with the identity added to the endpoint's mapping (facility support). Offer another facility meanwhile.
- **Stopping issues NO cancel.** hpc-bridge has no cancel channel to the facility's block: `stop_endpoint` stops submitting and returns `draining`, which is **final** here (do not re-poll it waiting for `down`), and the block **keeps billing** until the facility's idle-release or its walltime. Its notice names the block's scheduler job (`block_job_id`), the latest it can bill until, and the command that ends it now (`scancel <id>` on Slurm, `qdel <id>` on PBS); `spend_stopped` is never true here. **Relay the job id and that command to the user** — never "spend has stopped". Never check from here after a stop (no `run_shell` and no `ensure_endpoint_up(confirm_spend=True)` to see whether the block is gone): either is a task, which can keep the block alive or start a new one; the user checks on the facility (`squeue -j <id>` / `qstat <id>`). `teardown_endpoint` only detaches (the endpoint is the facility's, not ours) and leaves the block billing the same way, with the same notice. Both are refused while a task of ours is still running on the block, because nothing can end it there: poll it to completion first.

If `connect_facility` says the facility's endpoint is **offline**, nothing on our side restarts it — report it to the user as the facility's to fix.

## Bringing up a compute node: select → discover → gate → provision → wait

A compute block **spends your allocation**, so don't provision blind. Pick a machine, discover what's available and what it costs, let the user choose, then provision — all through the endpoint.

**Scheduler is discovered, not chosen.** The facility's **scheduler** (Slurm or PBS) is discovered at `connect_facility` time and drives how the `compute` block is realized — you don't pick it. On a **PBS** facility: the selection gate's "partition" is the PBS **queue**; poll the pilot with `run_shell("qstat -u $USER", shape="login")` where there is a login shape; and a site directive such as `#PBS -l filesystems=home:eagle` must be in the facility's configuration — `scheduler_options` in `details=` for a cluster you bring yourself (omit a required one and the job is **held**, never runs). A registry entry sends its own directives, if any (ALCF Polaris sends none, so its jobs get the facility's default `-l filesystems=home`), and no tool changes them per session: say so rather than promise one.

**0. Select the facility — `connect_facility` is ALWAYS the first call to reach any facility.** It's the entry point that decides reuse vs. discovery vs. pre-auth, so **never reach for `login_shell` or reason about SSH/Duo yourself before calling it** — for a facility you've used before it reuses the endpoint zero-SSH (next bullet), and it tells you if SSH is even needed. `list_facilities()` lists the catalogued systems; pick one (or the user names it) and call `connect_facility(facility="<id>")` — the `facility` arg is the `id` or `subject` from the list (e.g. `"anvil"` or `"purdue:anvil"`). This **binds the facility and establishes the endpoint** — standing up, or **reusing with zero SSH**, the manager plus a free login-node worker — and returns `needs_account` with the next block's terms in `block` (the default queue and where it came from, whether an account is needed and `account_hint` for where the user finds it, nodes and walltime) — nothing is billed yet. Where the facility has an allocation listing hpc-bridge can read (a cluster you bring with `mybalance`; no registry facility has one) it also returns your **allocations** (account + balance). It's the only step that may SSH, and only once. `provisioning` ⇒ the login node is still warming; call again shortly. Each `list_facilities` summary carries **`access`** — `mep` (zero SSH, but the facility must have mapped the user's Globus identity: no account ⇒ a terminal NO ACCOUNT on first use) or `ssh` (the user needs an account + key-based SSH on that host) — and an `access_note`: tell the user what a facility needs *before* they choose it.
   - **Reconnecting to a facility you've used before? Pass its `ssh_host`.** hpc-bridge caches a confirmed BYO config locally (keyed by `ssh_host`), so `connect_facility(facility, ssh_host="<alias>")` resolves it from that **local cache with no SSH probe**, then reuses the still-online endpoint over the web — a **fully zero-SSH reconnect**. (Your memory/notes are where to remember a facility's `ssh_host` and that you've connected before.) A brand-new facility — or one whose endpoint is gone — falls through to discovery below.
   - **`provisioning` can take a while — that's cold-start, not a hang.** A worker warms in its own time (a fresh scheduler block, a loaded login node, or a first-run venv install can each take minutes); keep polling `connect_facility`/`ensure_endpoint_up` — **don't assume a fixed timeout** (facilities vary widely). If you suspect it's genuinely stuck rather than slow, `login_shell` and read `~/.globus_compute/<name>/endpoint.log` for a worker **startup failure** (a non-zero `Command return code` / crash) — *that* is a real wedge: `teardown_endpoint`, then `connect_facility` again to rebuild. Steady progress (interchange starting, block scaling out) or plain slowness is not — just keep waiting.
   - **`needs_login` ⇒ a Globus login is needed (first use, or a credential missing a scope).** It's a link, not a prompt — and the tool has ALREADY opened the browser and waited ~90 s for the login to land (when it lands in time the call simply continues and you never see this phase). So: if the user says the page showed the login finished, just call `connect_facility` again. Only if no browser opened, show the USER `login_url` — it is SINGLE-USE (never re-open a finished one; a second visit fails harmlessly). `login_mode="paste"` (headless / remote): the user pastes the one-time code from Globus's page and you call `complete_login(code)`. Never ask for a Globus password; never paste the link into a shell.
   - **`needs_facility_details` ⇒ the facility isn't catalogued — discover it, don't interrogate.** The user supplies only *access*; you discover the config. Pass the login host — `connect_facility(facility, ssh_host="<login-host-or-alias>")` (SSH user + key come from your `~/.ssh/config`, or optional env overrides — not from you) — and the tool **probes the login node** and returns **`proposed_facility_details`** with a filled-in draft plus a `notice` flagging the low-confidence fields. **Review that draft *with the user* via `AskUserQuestion` — above all confirm `interface`** (a wrong NIC ⇒ workers never register) and anything the notice flags — fix what's wrong, then call `connect_facility(facility, details=<confirmed>)`. That registers a session-local facility and brings up the login shape, whose canary validates the values. Use `{user}`/`$USER` in paths (both resolve to the SSH login name). You pass `details` once — re-calls remember it, unless the configuration itself failed on the login node (not SSH, the network, a timeout or the home filesystem): then it is dropped, and a re-call without `details` resolves the facility afresh (a fresh proposal, for a cluster you bring yourself) while no tool brings the dropped one up; the failure's answer says so.
   - **Can't discover** (no SSH host yet, or the probe can't reach the node) ⇒ fall back to filling `details` from the **user** directly — the schema's field descriptions are the question list. Offer option values only for the genuinely common fields (`interface`: ib0 / hsn0; `partition`: the queues); for facility-specific free-text (`ssh_host`, `env_setup`, `scratch_root`) ask — do **not** invent a plausible-but-wrong value (a guessed `env_setup` they rubber-stamp just wastes a bootstrap).
   - **`needs_preauth` ⇒ the host needs a one-time interactive login step.** Two cases, told apart by the result's `preauth_code_ok`:
     - **`preauth_code_ok: true` — the facility takes a ONE-TIME CODE (TOTP / Duo passcode).** Ask the user for the *current* code from their authenticator and call `complete_preauth(code)`; it opens the shared connection. A one-time code is single-use and expires in seconds, so it may pass through the chat (like the Globus paste code). Then repeat the call that asked for it — `connect_facility`, or `teardown_endpoint` (the one later operation that needs SSH). Reconnecting to an endpoint that is already running never asks for a code: it goes over the web.
     - **Never edit the user's `~/.ssh/config` or keys, and never run `ssh` yourself to log the user in** (the session has no terminal; a password or code typed there would land in the transcript). Configuration problems are the user's to fix in their own editor — tell them exactly what to add.
     - **Otherwise (a password is needed) — you must NOT handle it.** Relay the `preauth_command` (an `ssh -fN …` line) for the user to run in THEIR OWN terminal; they type the password there, directly with ssh. **Never ask for, type, or run a command containing a password.** `complete_preauth` refuses password prompts for the same reason. When the user confirms the connection is up, call `connect_facility` again — the whole session rides it with no further SSH auth.
     - **If the user pastes a password anyway, never repeat it back** — not even to ask them to rotate it. Refuse it, say it is now in the transcript and should be changed (without restating it), and give them the `preauth_command` for their own terminal.
   - **`env_setup` must leave `globus-compute-endpoint` on `PATH`** — a site `module load` and/or `source <venv>/bin/activate`. Where the facility has no endpoint installed, the probe proposes hpc-bridge's own line, and hpc-bridge builds or repairs that environment itself when it starts the endpoint. **Leave `env_setup` out of `details=`** unless the user wants it changed: the server keeps the proposed one.
   - *(If a facility is pinned by env — `HPC_BRIDGE_MACHINE` — you can instead `ensure_endpoint_up(shape="login")` and read the balance yourself in step 1.)*

**1. Discover partitions THROUGH the endpoint** (over the network, no SSH) with `run_shell(..., shape="login")`, when the user wants a choice or the default looks wrong (it is optional: the default queue is already in `block`). Allocations came back from `connect_facility` only where it listed some; otherwise the account is the user's to name. Here you fill in the partition picture:
   - Partitions (Slurm): `run_shell("sinfo -h -o '%P|%a|%l|%D|%c|%m|%F'", shape="login")` → `name|avail|timelimit|nodes|cores|mem_MB|A/I/O/T-nodes`. The **I** (idle) in the last field is *live* availability — 0 idle will queue.
   - Accounts/QOS (Slurm): `run_shell("sacctmgr -nP show assoc where user=$USER format=Account,QOS,Partition", shape="login")` — the allocation→partition/QOS mapping behind the balances.
   - Queues (PBS): `run_shell("qstat -Q", shape="login")` for queues; `run_shell("qstat -u $USER", shape="login")` to watch the pilot.
   - **Re-read balance** (optional, SSH facilities only — a facility endpoint has no login shape): use the site's balance tool on the login shape, e.g. `run_shell("expanse-client user -r expanse", shape="login")` on Expanse, `mybalance` on Purdue clusters, `xdusage -p <project>` elsewhere on ACCESS. If `connect_facility` returned no allocations, the account is the project id the user was given (`block.account_hint` says where they find it).
   - **Recipe, not rule:** if a tool isn't found, adapt (`scontrol show partition` / `qstat -Q`; `module load` first if a binary is missing). A `cold_start` while the login worker warms — just retry.
   - **Gotcha:** partition `timelimit` may read `infinite` because the real cap is per-**QOS** — if walltime matters, also `run_shell("sacctmgr -nP show qos format=Name,MaxWall", shape="login")`.

**2. The spend question — before the first block on a facility, only for what the user hasn't said.** Every spend answer (`needs_confirmation`, `needs_account`) and `connect_facility` carry the block's terms in `block`: its queue and account, each with where it came from, its nodes, walltime and the most node-hours it can bill. Use them:
   - **The user named the queue and the account, or said "defaults" — or they are presets** (`HPC_BRIDGE_PARTITION` / `HPC_BRIDGE_ACCOUNT`; source `env`): state the terms in one line, saying which are presets, and start.
   - **Otherwise ask one question** for what is missing — the account (`account_hint` says where the user finds it) and whether the quoted queue is OK — naming queue, account, size and walltime: *"Start 1 Polaris node in `debug`, up to 15 min, charged to Diaspora?"* (Yes / other queue / other project); account unknown: *"Which ALCF project should Polaris charge (e.g. Diaspora)? I'd use `debug`: 1 node, up to 15 min."*; no account needed: *"Start a node on `main` (up to 2 h, no account needed)?"* **The answer is the spend confirmation:** state the terms in one line and send them in one call, `ensure_endpoint_up(account=…, partition=…, confirm_spend=True)` — don't ask again.
   - **A real choice** gets its options: the **allocation** (e.g. a CPU vs `-gpu` account, each with its balance) and the **partition** (node size + **live idle count** + any caveat: saturated → would queue; a GPU partition needs the `-gpu` account). Put the balance and the rough block cost (≈ nodes × walltime × the facility's SU rate) in the question where the facility shows a balance. Recommend the cheapest/fastest sensible default.
   - **The size is a term too: ask what the work needs.** Where a partition shares nodes, a block can be a *slice* of a node — some cores, their memory, a GPU — billed for what it holds (memory beyond the cores' share usually bills as more cores); a *whole node* bills every core of it whether used or not, and on a busy per-core partition it can wait a long time for a node to come free entirely. When the terms say the size is hpc-bridge's **proposal** (a few cores on a per-core partition), ask whether it is enough — a quick test or a serial script usually is; a parallel or memory-hungry job needs more — and send what the user says as `cores=` / `memory_gb=` / `gpus=` (per node), or `whole_node=True` when the work really needs every core or the whole node's memory. Never put the size in a facility's `scheduler_options` (`--exclusive`, `--mem`, `--gres=gpu`…): it would size the block behind the terms, and it is refused. When the terms say a whole node — the partition hands out only whole nodes, or nothing shows it shares them (parsl's default is the whole node), or the facility's template decides — say so: that is what the block can bill. Where the facility's billing weights are known the terms carry the most the block can cost (`max_charge`, e.g. "at most 4 SU: 8 cores × 0.5 h"): name it.
   - **More than one node** (`nodes=N`) is one shell over the whole allocation, like an `salloc` shell: commands run on the first node, and work reaches the others only through the scheduler's launcher from that shell. The job holds one task slot per node, so ask for the ranks: `srun -N N -n <ranks> …` on Slurm (OpenMPI's `mpiexec` needs `--oversubscribe` or `--map-by` to place more than one rank per node). Say this in the question, and that nodes the work does not use still bill: ask for several nodes only for work that spreads over them (MPI, `srun` steps), never to "go faster" on its own. A facility's own multi-user endpoint is not offered several nodes (its template places its workers). On ONE node, hpc-bridge's worker runs as an `srun` step that holds the block's CPUs, so a user's own `srun` from the shell can wait for them: use `srun --overlap …`.
   - **A remembered account** (your memory, a CLAUDE.md, an earlier session) may be **offered as the suggestion** — never used without asking.
   - **After a reap, a switch or a stop** (`needs_confirmation` saying why): a yes/no question, naming the terms again.

**3. Provision the billed block, confirming spend.** `ensure_endpoint_up(shape="compute", account="<allocation>", partition="<choice>", confirm_spend=True)`. The manager is already up from step 0, so this just kicks the compute block (a Slurm partition or a PBS queue, per the facility's scheduler). The account, partition and size **persist for the session** (later calls reuse them, after a `stop_endpoint` too) until you change them, connect a facility again or tear the endpoint down. The spend acknowledgement covers **one block**: once that block is gone (idle-released, past its walltime, or cancelled), the next call returns `needs_confirmation` with the reason — ask the user again before confirming the new block, and tell them the old one is gone. **A different partition, account or size is a different block too:** the call that changes them returns `needs_confirmation` unless it carries `confirm_spend=True` (ask the user first). Either that answer or, when the call confirmed at once, its own result says what became of the old block — it is not cancelled by the switch: relay it. A first call returning `provisioning` is normal.

**4. Wait for the block, then confirm.** The pilot starts `PENDING` and flips to `RUNNING` once the scheduler gives it a node; watch its state with `run_shell("squeue -u $USER -h -o '%i|%P|%T|%r'", shape="login")` on Slurm, or `run_shell("qstat -u $USER", shape="login")` on PBS (see the scheduler note above) — over the endpoint, no SSH. Once `RUNNING`, call `ensure_endpoint_up(shape="compute")` once to confirm the worker registered. A `PENDING` job spends no SU.

This is a *policy gate*: discovery surfaces the options + the budget, the human picks, and the pick drives provisioning.

- **The spend floor is enforced, not advisory.** A billed `compute` shape **without** `confirm_spend=True` returns `needs_confirmation` and starts **nothing**. Only set `confirm_spend=True` once the user has agreed to the terms (or named them) — it is your acknowledgement on their behalf, not a default to sprinkle on. The confirming call's result carries the same `block` as a receipt: what it started.
- **Gate, not interrogation:** the consequential, cost-bearing choices are gated — the **allocation** (only when there's a real choice), the partition, and the spend confirmation; walltime/nodes are sensible-defaulted. Don't prompt for the unambiguous (a single allocation → just use it, and name it in the spend question).
- **Headless fallback (can't prompt):** stay on `shape="login"` (free, read-only — and submit no batch job from it) rather than spend unattended; only auto-confirm a billed block or job in autonomous mode with an explicit budget signal.

## Running compute work

Once the block is up, run work through `run_shell(shape="compute")`. **Long work is a foreground task, not a detached process.** A command that outruns the sync-wait comes back `phase="running"` with a `task_id` — it was **not** cut; retrieve its result with `poll_task(task_id)` (which returns `running` until it finishes, then `complete` with the full output). The task runs up to the **block walltime** and keeps the block warm the entire time, so it is never idle-released.

**A software environment** for the work is `ensure_endpoint_up(env=…)`: `{"activate": "<shell line>"}` for one the facility already has, `{"requirements": "<requirements.txt text>"}` for one hpc-bridge builds — and `phase="env_building"` means nothing ran: that env is being built on the login node, which is free.

**A `poll_task` result of `failed` saying the task is ORPHANED** means the endpoint behind it went offline or was torn down — the result can never arrive, so stop polling; if that wasn't you, `connect_facility` again and re-run. (A merely cold or relaunching block still reads `running` — keep polling that. A task's time limit counts from when it starts, so one still `running` with no result past its limit may only be queued behind another task or a relaunching block: the notice says so and how to leave it for its shape (a login task does not hold stop, but holds its session and the login worker, so the next login command queues behind it), and polling stays right unless you mean to abandon it.)

**Never background/detach long work** (`setsid`, `nohup … &`, a trailing `&`) to "escape" a timeout — a detached process is *not* a Compute task, so the block idle-releases out from under it and the work dies (issue #21). Run it in the foreground and poll instead.

**Work longer than one block's walltime:** checkpoint it and resume on the next block, or — on a facility hpc-bridge reaches over SSH — run it as a scheduler job with `submit_job` (next section). A batch job is **billed to the user's allocation exactly like a compute block**, wherever it is submitted from. On a compute-only facility (no login shape, no `submit_job`) a hand `sbatch`/`qsub` from inside the block — if the site allows it — needs the same spend confirmation first (allocation, partition, size, walltime), and hpc-bridge neither counts nor cancels it: cancel it yourself (`scancel`/`qdel <jobid>`) when the user wants it stopped. (`srun` inside a block is a step of the block's own job, not a new one.)

**One task per session.** A `session_id` whose task is still running is busy — issue the next command in a **different `session_id`** (or `poll_task` the running one first); two commands can't share one session's cwd/env at once.

## Many independent runs: `run_batch`

**The same command over many inputs is ONE `run_batch`, not a `run_shell` per input.** hpc-bridge keeps the backlog, sends rows as the confirmed block's slots free (one worker always stays for your interactive commands; on a one-worker block an interactive command waits behind the batch's task), and records every row in a durable ledger, so the batch outlives the server.
- **Size the rows as an sbatch array:** `cores` (CPUs per row, as `-c` counts them — a hardware thread where SMT is on), `memory_gb` (per row: a row past it is killed, `why: "memory"`), `gpus` (per row, each its own) and `concurrency` (at most this many at once, as `--array=…%N`). Pick them from the command: a single-threaded tool is 1 CPU; one that reads `OMP_NUM_THREADS` or takes a `-t`/`-j` gets that many cores (pass the same number to its flag). With **no block yet**, the block is derived from them — concurrency × the row, plus one CPU for your interactive commands — and the spend question names it; a call with no size answers `phase="needs_sizing"` with `facts` (the node's CPUs, memory, GPUs and the concurrency each row size gives): **ask the user in those terms**. If nobody knows the size, `pilot=1` runs one row alone with the whole block and stops at `needs_sizing` with a `proposal` (cores from its CPU-seconds ÷ wall, memory 1.25 × its peak) — confirm it with the user, then `run_batch(batch_id=…, cores=…, memory_gb=…)`. On a confirmed block a size that cannot fit is refused with the numbers, and too many at once is capped and said; with no size on a CPU-only block the rows take 1 CPU and the block's share of memory each (said in `sizing.defaulted`), and the first row killed at that default memory pauses the batch at `needs_sizing` with a proposal from that row. Each row is pinned to its own CPUs (`pin=False` to let it roam) with `OMP/MKL/OPENBLAS/NUMEXPR_NUM_THREADS` and `PYTHON_CPU_COUNT` set to its cores, and sees only its own GPUs; a row's own `srun` shares the block's step (`SLURM_OVERLAP`), but its tasks run where Slurm places them, not on the row's CPUs, and outside the row's memory watch. A resize names only what changes (`run_batch(batch_id=…, memory_gb=…)` keeps the rows' cores and GPUs); when the batch also waits for the block's yes, send the size and `confirm_spend=True` once the user agrees. Every result carries its `peak_rss_mb`, `cpu_s` and `nproc`, and `status` names rows that ran over their size. A batch runs on ONE node, at most 32 rows at once: a block of several nodes is refused.
- **The template:** `command` takes `{name}` for each field of a row (`rows=[{"n": 1}, {"n": 2}]`; field names are identifiers), `{row}` for a plain-value row and `{index}` for the row's number. **Write each placeholder bare** — `grep -c {pat} out.txt`, `out="$(basename {f})"` — never inside quotes, a here-document, arithmetic, `[[ ]]`, `${…}` or backticks (refused): each value reaches the command as ONE word, as data (an environment variable, `$HPCB_F_<name>`). That is the whole guarantee: **never hand a value to `eval`, `sh -c`, `ssh` or an interpreter as code** — nor pipe it into one (`echo {x} | sh` is refused), nor put it where `env`/`sudo`/`timeout` read their options — the obvious forms are refused, but a value an inner program parses is code again. A value starting with `-` can be read as an option: put `--` before the placeholder (`rm -- {f}`) or give paths as `./-name` — `run_batch` names such rows. For an inner program, pass the value as an argument (`bash -c '… "$1" …' _ {x}`) or read it from the environment in a here-document with a QUOTED delimiter (`python3 - <<'EOF'` … `os.environ["HPCB_F_x"]`). Any other braces (`${HOME}`, `awk '{print $1}'`) stay as written. Each row runs in the session's cwd and env, read-only; background processes a row starts end with it.
- **`task_walltime_s` is required:** a row is killed at it (exit 124), and a row is only sent while the block has `task_walltime_s` + 30 s of walltime left — a value that cannot fit the block's walltime is refused.
- **Spend is the block's, as for `run_shell`:** an unconfirmed block answers `needs_confirmation` with `block` and records nothing; `confirm_spend=True` confirms ONE block. When the block ends under the batch — its walltime nearly over, a reap, a stop, a server restart, a drain — the batch pauses at `phase="needs_confirmation"` and its `reason` says which. **Ask the user before resuming**: only `run_batch(batch_id=…, confirm_spend=True)` sends more, starting the next block. `status` never resumes it.
- **Results:** `status(id)` counts the rows by state; `detail="failed"` lists the failed and lost ones with their `exit_code`, `detail="page"` every row (`offset`/`limit`); `wait_s` (up to 60) waits until the batch ends, a row fails or is lost, or it pauses — rows that complete are counted, not waited on. `status()` with no id lists every batch, job and envelope in the ledger, active ones first (`facility=`, `active_only=`): a read that starts nothing, flagging an active one whose server or block is gone (`stale`). A row's result carries its exit code, the last 4 kB of its output (`tail`) and `stdout_path`, the file on the facility holding its output (capped at 1 MB per stream; `truncated` says when it was cut) — read that file for the rest. Rows go in the batch's own directory, `<results_dir>/<batch id>/` (by default under the facility's scratch root; `results_dir` in the answers is that directory, so batches may share a `results_dir`); the notice warns when it is under `$HOME`, which a large batch can fill. A row whose results directory cannot be written fails with the cause (`settled_by`), as does one on a disk too full (exit 75).
- **States:** `lost` (its block died under it, on evidence) and `cancelled` rows are not run again unless the batch was started with `idempotent=True` (a lost row then runs again on evidence); `submit_unknown` (the send's answer never came back) holds its slot until its task's result is found — it is never called lost on the service's silence, and never sent twice unless `idempotent`; a row with no result well past its time and no way left to learn its fate (on a compute-only facility; after a restart) is `presumed_lost`, keeps its slot and is never retried.
- **Stopping:** `cancel(id)` (`drain`) admits nothing more and lets the tasks out finish, keeping the backlog to resume; `cancel(id, "abort")` cancels the backlog and kills the tasks out within seconds (exit 143) — when its notice says the marker that tells them was written; when it says it was not (after a restart on a compute-only facility, or on a one-worker block there), the tasks out run to their end. `status="draining"` while any task is still out, `down` once none is — `blocks_left` names every block of ours that can still bill (the session's until `stop_endpoint`; on a compute-only facility the ones a stop left draining). A drain, an abort or a stop also withdraws a yes given for the next block. `stop_endpoint` refuses while a batch's tasks are out, and its notice names the batch: abort it, or let its tasks finish, then stop; while a batch has a submit of unknown fate it answers `draining` naming it (the service may have queued that task): on an SSH-bootstrap facility until the block's config is retired (a stop does that) and its user endpoint has exited with nothing queued — `status` looks; on a compute-only facility for good.
- **Another session or server:** `status` reads a batch another hpc-bridge server runs from the ledger (`owner` names it) but only that server sends its rows; after a restart, the new server's `status` collects what finished meanwhile and asks again before sending more. `poll_task` takes a task's Globus id (`globus_task_id` on a running answer) after a restart too.

## Scheduler jobs and the budget envelope: `submit_job` (SSH facilities)

**`submit_job(command, session_id, …, walltime)` runs work as a scheduler job that outlives any endpoint** — long walltime, arrays, dependencies. It carries the session's cwd and env (the session you set up with `run_shell`), is written to a frozen `job.sh` under the facility's scratch root, and is tracked in hpc-bridge's ledger across servers. Size it as a block (`partition`, `account`, `nodes`, `cores`, `memory_gb`, `gpus`, `whole_node`); `array="0-19%4"` is 20 tasks, at most 4 at once, and `{index}` in the command is each task's index (written bare, as in `run_batch`); `depends_on=[job ids]` waits for them. A compute-only facility has no status or cancel channel for a job: `submit_job` refuses there (on ALCF, a campaign of tasks on one block — `run_batch` — is the equivalent).
- **The envelope:** every job runs under a budget the user approves ONCE: a cap (in the facility's billing units), a deadline (24 h unless the user says otherwise, at most 168 h; every Slurm job carries it as `--deadline`, so none runs past it; on PBS it is the server's to enforce), optionally `max_jobs` (array tasks count), allowed accounts/partitions, and a site backstop. The first `submit_job` answers `needs_confirmation` with `terms` and the `envelope` it would open — nothing is submitted. **Name to the user the job's worst case** (`terms.worst_case`: EVERY array task × its size × its walltime — never the throttle's few — and never less than the queue's minimum charge where the catalog knows one), the cap, the deadline, and the honest limit in `terms.binds`: the envelope binds only what hpc-bridge starts, and `site_backstop` is "none" unless the user names one (an sbank suballocation, a Slurm `GrpTRESMins`). Their yes is the same call with `confirm_spend=True` (and `envelope={cap, deadline_hours, …}` when they set it). The proposed cap also covers jobs of the user's already in the queue that hpc-bridge did not start (named in it — if one is not theirs to count, `exclude_jobs`); if those change before the yes, the yes is answered with the proposal again — relay the new figure. After that, a job that fits is admitted at once.
- **Exhausted:** a job that does not fit what is left answers `needs_confirmation`, reason `envelope_exhausted`, naming what still bills. Ask the user — raise the cap, or wait — and **never split or shrink the work to slip under it**. Exhausted is not stopped: the jobs in flight run on.
- **The meter:** `status("job-…")` and `status("env-…")` read the scheduler once each: `charged` (billing × elapsed) and `committed` (what it can still bill: a running job's remaining walltime, a queued one's full walltime). A job the accounting database does not list is held at its full walltime until it does. A job PENDING under a site limit (its reason an association or QOS limit, such as a GrpTRESMins backstop) will not start until that limit changes: tell the user rather than wait it out. Jobs of the user's that hpc-bridge did not start (a script's own `sbatch`, a subprocess) are counted and named; when the user says one is not theirs to count, pass `exclude_jobs=[its id]` with their yes and it is never counted again. The session's own compute block, confirmed before the envelope opened, is counted too and named as such: it bills the same allocation, so it is not one to exclude.
- **Another session** — a new chat, or a restarted server — asks again before admitting anything (`envelope_new_session`, naming what remains); `HPC_BRIDGE_ENVELOPE_MAX`, the operator's ceiling, bounds the sum of open envelopes per facility and account.
- **A hand `sbatch`/`qsub` while the envelope is open** answers `needs_confirmation` and runs nothing (`login_shell` refuses it outright, and a `run_batch` template that submits jobs is refused: use `submit_job` with `array=`). On the user's yes, `run_shell(…, confirm_spend=True)` runs it as it is; the jobs that appeared while it ran are adopted after the fact (`jobs` in the answer, with job- ids: counted against the envelope at their full request) with NO envelope deadline applied — they run to their own walltime. If they put the envelope over its cap, it admits nothing more; the answer says by how much — tell the user. If one of them is not from that command, `exclude_jobs` with the user's yes stops counting it. hpc-bridge never cancels them on its own: the stop asks about them by name, and `cancel("job-…", "abort")` ends one when the user says so.
- **Ending them:** `cancel("job-…", "abort")` cancels a job (`drain`: only its pending array tasks); `cancel("env-…", "drain")` admits nothing more, `"abort"` cancels every job of the envelope. `draining` while the scheduler still lists one, `down` once none is.

## The endpoint handoff: `export_handoff`

**`export_handoff(user_endpoint_config, expires_hours=24)` hands an orchestrator (the consumer) an endpoint and a config it validated.** Give the consumer's config in the facility template's own key names (Polaris: `queue`, `account`, `walltime`, `nodes_per_block`, `max_blocks`, `min_blocks`, `max_workers_per_node`, `available_accelerators`, `scheduler_options`, `worker_init`). The facility's defaults fill the rest. A key the template does not use, or its schema refuses, is refused by name rather than dropped: remove it, or ask the user. `scheduler_options` may carry only harmless directives (a job name, mail, `-l filesystems=…`); one that sets the nodes, time, queue, account, GPUs, an array or the output path is refused, so set those through the config's own keys. `worker_init` is the consumer's own code, and it runs as shell in every block of the pool.
- **The terms first.** The first call answers `needs_confirmation` with `terms`, and nothing is sent. **Name to the user both figures in `terms.unit`:**
  - `canary_worst_case`: the one billed canary that validates exactly this config;
  - `worst_case`: what the consumer's pool can bill until the record expires, which is `max_blocks` blocks at once for the whole window.

  Also name `terms.binds`: `enforced_by: "uec-bounds-only"` means that once the consumer holds the record, hpc-bridge neither polices that endpoint nor stops it at the expiry. Their yes is the same call with `confirm_spend=True`. The answer is `validating` while the canary's block starts: call again with the same config to collect it (nothing more is sent), until `exported` gives the `record` and its `path`.
- **On a facility multi-user endpoint `min_blocks` must be 0.** A pool that keeps a block warm cannot be ended from outside (parsl replaces a cancelled block, and nothing can stop a facility's user endpoint), so it is refused; nothing is asked or sent.
- **Relay `record.release`:** stop submitting with that config; with nothing queued its blocks idle-release; a block can be cancelled sooner with the scheduler's cancel it names, and with `min_blocks` 0 nothing replaces it.
- **The record names no consumer and holds data, not shell.** The consumer maps `endpoint.manager_id`, `user_endpoint_config`, `terms.nodes_per_block` and `facility.system` to its own settings, quoting each value in any shell file it writes.
- **A stop on an endpoint hpc-bridge stood up asks first while a handoff of it is unexpired.** `stop_endpoint(handoffs="keep")` releases only this session's block and leaves the consumer's pool running (`draining`, naming it). `handoffs="cancel"` ends the consumer's blocks too. A teardown always ends the consumer's pool. On a facility endpoint the stop only names the handoff.

## Stopping

**Jobs of ours that can still bill make `stop_endpoint` ask first** — `needs_confirmation`, naming each job (`jobs`: its scheduler id, state and what it can still bill), and nothing is cancelled or released. Ask the user: `stop_endpoint(jobs="cancel")` cancels them too (and closes their envelope; `down` only once the scheduler lists none of them), `stop_endpoint(jobs="keep")` releases only the endpoint's blocks and leaves them running under their envelope and deadline — its `draining` is the final word, naming them and how to end them. Either way nothing new is admitted after a stop; a later `submit_job` asks for a new envelope.

`stop_endpoint` means **stop spending**, not tear the endpoint down: it cancels the billed compute block over the login endpoint (AMQP, no SSH) via the scheduler's own cancel command (`scancel` on Slurm, `qdel` on PBS) — the behaviour is identical, only the underlying command differs — and **leaves the login-node endpoint online** for reuse. **Read the status, don't assume:** `status="down"` means nothing of ours is left billing: the cancel was *confirmed* (or there was nothing to cancel — the scheduler rejected the submission, so no block was created), and no check of hpc-bridge's is still queued. A `down` can also say the Globus Compute service still lists a check as queued: its own user endpoint went into bad state and shut down, so it can never run — that is a confirmed stop; relay it, nothing more to call. hpc-bridge's check (the small probe it sends to see whether a block is up) is a task: while it is queued, the endpoint can start a block to run it, even after a stop cancelled one. `status="draining"` means **spend is not confirmed stopped**, and the notice says why — the login release channel was cold; a scheduler command failed, or refused to cancel a job; the cancel was sent but has not finished; or a check is still queued (the notice names it, and a pilot job that **ran and died** before running it, with its exit status — idle-release does not end that, the endpoint is not idle while a task waits). On `draining`, call `stop_endpoint` again when the notice says: each call cancels what it finds and looks again. If a check stays queued call after call — or the notice says this endpoint was set up by an earlier hpc-bridge, where stopping cannot end it — removing the endpoint ends it: `teardown_endpoint`, the user's call. A `connect_facility` to another facility does not end it either; its answer says when one may still be queued on the endpoint it left. (Exception: on a **compute-only facility** no cancel is issued at all and `draining` is final — see that section; the notice says so explicitly.) Don't tell the user spending stopped until you've seen `down`. The endpoint stays up either way, so reconnecting later (`connect_facility`/`ensure_endpoint_up`) is **zero-SSH**; a quick `run_shell(shape="login")` after a stop just reuses the still-online endpoint.

**`stop_endpoint` refuses while a task is still running on the block** (status `up`, naming the task): releasing the block would not end the task — the endpoint would relaunch a block for it and spend would continue. Do what the notice says: `poll_task` it to completion, then stop. To abandon it on an SSH-bootstrap facility, `teardown_endpoint` removes everything. On a compute-only facility nothing can end it early: stop waits until it finishes, or until it has had no result well past its time limit and is presumed lost (the notice says when, and that it is then abandoned). A cancelled `run_shell` (the client cancelled the call, e.g. the user interrupted it) does not stop its command: the command keeps running on the block as a task the notice names, and stop refuses the same way. So does a command whose result hpc-bridge lost on its own side while the service says it is still running (the notice names its task id; `poll_task` cannot return it): call stop again once it has had time to finish, or `teardown_endpoint` ends it.

**Don't tear the login endpoint down.** It's *designed* to stay online after `stop_endpoint` — a free login-node process (no allocation, no SU), and staying up is exactly what makes the next reconnect zero-SSH. There's nothing to clean up, and `run_shell` will just re-provision one if you kill it (so don't try to `setsid`/`nohup` a stop — that races the auto-revive). If the user **explicitly insists** on removing it entirely, that one case is `teardown_endpoint` (gce stop + delete over SSH); after it, don't `run_shell` (that re-provisions a fresh endpoint). It can answer `tearing_down` — the login-node ops take a few minutes on a slow filesystem — then call it again in about a minute to confirm `down`, and call nothing else meanwhile. On a one-time-code facility it may first ask for a code (`complete_preauth`), then wants calling again. Its final notice says exactly what was removed, including whether the shared SSH connection was closed — report that, don't infer it.

## When to use `login_shell` (raw SSH) instead

`login_shell` runs on the login node over a **fresh SSH connection** — reserve it for:

- the **cold start** where no endpoint exists yet and you specifically *don't* want to stand one up (a quick one-off peek), or
- a **fallback** if the `login` shape can't come up.

On an MFA facility **every `login_shell` may trigger a re-auth**, so for the provisioning flow above prefer the endpoint path (`run_shell(shape="login")`), which authenticates once at bootstrap and then runs over the network.
